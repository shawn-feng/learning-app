## 修复：汇总轮被误报「无法连接服务端」（commit `e872602`，prompt 提交异步化）

### 实证（读珊珊 jsonl 尾部）
09:40:03 调 summarize_conversation → **09:43:13 服务端 toolResult「已总结…写入 daily」（isError=False，服务端成功）**。耗时 3 分 10 秒 > 客户端 promptChild 的 2 分钟超时 → `serverFetch` 的 catch 把 `AbortSignal.timeout` 超时与真断连混报为「无法连接服务端」。

### 修复（两层）
1. **prompt 提交异步化**：`submitChildPrompt` / `submitParentPrompt` 启动整轮后立即返回 ok；busy/结束/错误全在异步任务里管理并经 SSE（turn_end/error）推送。渲染层忙碌态本就由 `pi:reply_end` 驱动，长工具轮不再受客户端 HTTP 超时约束。并发守卫仍由服务端 busy（409）兜底。
2. **超时文案区分**（`server-client.ts` describeFetchError）：`TimeoutError/AbortError` → 「服务端响应超时（N 秒）——长任务通常仍在后台执行，请稍候查看结果，勿重复提交」；其余才报「无法连接服务端」。三处 catch 全改。

### 教训
「无法连接服务端」曾是一切 fetch 异常（含超时）的统一文案——**错误文案吞掉异常类型是这次误诊的直接原因**；若不是读 jsonl 看到服务端 toolResult 成功，会朝「服务端崩溃/网络」方向白查。冒烟断言已适配异步化语义（提交即返回 200 + 轮询事件流）。

### 备注
- summarize 3 分 10 秒本身偏慢（mimo + 多轮 kb 工具），后续可优化（如限制单轮 kb 调用次数），非本次范围。
- 客户端需重启生效（server-client.ts 改动）。

## 修复：工具调用在客户端不显示（commit `4bb9bce`，SSE 桥事件顺序 bug）

### 实证（读珊珊 jsonl）
服务端侧工具调用全部正常（09:58 parent_content / 10:01 kb_update + kb_insert 均成功写库），但客户端聊天无任何工具调用气泡，只见到最终总结。

### 根因（桥上线即存在，此前被超时误报等问题掩盖）
SDK 事件顺序 = assistant 消息 message_end（可能带 toolCall）→ tool_start/end → 下一条消息。桥在**每条** message_end 立即发 pi:reply → 渲染层 handleReply 转正工作气泡（workingIdRef=null）→ 后续 tool_start/tool_end/thinking 被 patchWorking 全部丢弃（无气泡可挂）。

### 修复（对齐旧同步实现的回发顺序）
桥内轮文本缓冲 turnTextBuffers：message_end 只累积文本（thinking 补发保留）；user_message 清残留；turn_end/agent_end 逐条回发 pi:reply（第一条替换工作气泡保留 tools/thinking，后续追加）+ reply_end；error 清缓冲。最终呈现 = 旧 ISSUE-016 语义：工具调用挂第一个气泡，多段文本各自成气泡。

### 教训
SDK 的 message_end ≠ 轮次结束（一个轮有多条 assistant 消息）；「回复回发时机」必须以 turn_end/agent_end 为准。单测新增工具轮回归（tool 事件必须先于第一条 reply），桥语义测试改为累积制（24 项全过）。客户端需重启生效。
