## ISSUE-133 第二轮：把「参数被整串 JSON 序列化」从偶发定性为「模型在特定参数形状上的固有习惯」

用户补充关键线索——**`where` 正常（对象）、`rows` 无论传数组还是对象都变成字符串**，怀疑框架层有问题。
据此翻本机会话 jsonl（`server/data/agent-sessions/**`，20 会话 / 550 次工具调用 / 771 处 `"model"` 标记）量化核对：

| 参数 | 形状 | 调用 | 被写成 JSON 字符串 |
|---|---|---|---|
| `parent_upsert_course_content.items` | 数组套对象（深、长） | 69 | **12（17%）** |
| `parent_db_write.rows` | `anyOf[数组, 对象]` | — | 同型（用户现场） |

| `parent_exam_plan_create.courses` | 标量数组 | 37 | 0 |
| `parent_study_plan_create.days` | 数组套对象（短） | 7 | 0 |
| `parent_upsert_course_content.topic/title` | 标量 | 70/70 | 0 |

- 模型 = `mimo-tokenplan/mimo-v2.5`（该家长 `app_settings.defaultModel`，三个模型位全是它）。
- `items` 历史失败：09-14/15 连续 12 次 `items.0: must be object`，其中一场**重试 6 次照旧**——
  报错只给一句 schema 文案，模型没有可用线索。
- **反证框架无关**：09-18 同一模型调 `parent_db_write` 时 `rows` 就是**真数组**并成功落库；
  链路复核：`openai-completions.js:1099` 原样透传 `tool.parameters`、只 `parseStreamingJson` 一次、
  `utils/json-parse.js` 是忠实解析器（JSON.parse → 字符串字面量修复 → partial-json 兜底）、
  `utils/typebox-helpers.js` 只是 enum 辅助。⇒ **字符串来自模型自己的输出**。
- 结论：触发条件 =「深层嵌套 + 长内容」的复合参数；`anyOf` 联合类型是额外放大器；
  扁平 map / 标量数组从不出问题（这也解释了 `where` 好 / `rows` 坏）。

### 18:15 设计「三个 `*_plan_list` 字段可选化改造」→ 写入 §3.2（设计稿，未动产品代码）

**设计要点（三条原则 + 两参数 + 取数统一 + 两档返回）**：
1. **原则**：① **不动窗口**（`start_at='' OR ≤当天` 与 `due_at='' OR ≥当天` + from/to 一字不改，这是 list 存在唯一理由）；② **不另立列口径**——`fields` 白名单**复用 `childKbReadableRegistry()`**（三张计划表**已逐列登记**，`child_db_read` 的列校验正是拿它当白名单）⇒ 零新增登记、避免两套口径；③ **默认零回归**（不传新参数 = 今天的人读清单，token 不变）。
2. **参数**：每个 list 加 `fields?: string[]`（列投影，未登记列直接报错并列出可读列）+ `full?: boolean`（= 全登记列）；都省略 → 现状。
3. **取数一律 `SELECT *`**（现在 study/exam 手写列、life 全取，三处不一致；统一后"取了没打印"的坑消失，列裁剪在返回层做）。
4. **返回两档**：默认档 = 现在的 text（不变）；明细档（传了 fields/full）= **紧凑 JSON**，**表头只出现一次 + 行是数组**（`{"columns":[...],"rows":[[...]]}`）——对比 `child_db_read` 每行重复列名（~550 字符/行），6 列降到 ~80–150 字符/行，**行数越多省越多**；结构化内容放 `text`（模型读 text），`details` 不动。
5. **上限**：保留 120 行 + 加字符预算（照 read 的 40k），超限**截断并明说**（不静默）。
6. **三个待定细节**：`id` 明细档给**全 id**（默认档仍 8 位）／`status` 明细档给**原始值**（`started` 中间态否则永不可见）／`parent_id`/`child_id` **照注册表给**。
7. **工作量**：抽共用 helper `projectRows(...)` + 三个 list 各接一行；**工具描述**补用法（同源、调用时必看，先例=`child_mistake_log`）。**参数还原无需额外处理**——`fields: Type.Array(...)` 已被 `tool-kit.ts` 的 `prepareArguments`（ISSUE-134）统一还原。
8. **改造后边界**：字段能力与 `child_db_read` **对齐**、过滤能力仍互补 ⇒ §3.1 列的那些缺口（B6 分数规则 / F4 结果概要 / 考核范围 / `due_at`）**工具层直接消失**，不再依赖提示词教模型绕道。
9. 顺带（可选、不属本次）：三 list 合并为 `child_plan_list(type, …)`（28→26 工具）——会改工具名与场景引用，**后置**。

### 20:00 核实 `kb_query(progress)` 的产生方式 → 是 `topic_progress` SQL 视图现算（未改任何代码）

用户问「progress 是怎么出来的？」→ 全链路核实（`worker/kb-tools.ts` → `routes/db.ts` → `db/kb.ts`）。

- **不是落库字段、也不是定时任务算的**，是**孩子库里一个 SQL 视图 `topic_progress`**（`db/kb.ts:456-473`，建表随 `openKb` 执行），每次查询现算。读出口 `kb.progress.list` = `SELECT * FROM topic_progress ORDER BY topic`（`routes/db.ts:315-323`）。
- 数据源 = `courses` 表（主键 `(topic,title)`，一行=一门课）：`total`=行数；`learned`=`status='✅'` 行数；`next`=同主题第一个 `status!='✅'` 的 title（`ORDER BY sort_order, title LIMIT 1`）；`updated`=`MAX(last_review)`（排除 `''`/`'-'`）。
- 三点值得记住：① **分母是课程数、不是掌握度**——`learned/total` 与 `courses` 的 `mastery_*` 四列无关（掌握是另一套）；② `next` 是"第一个没上完的课"，无推荐/掌握判断，也不过滤停用课（courses **没有** `active`/`deleted` 列）；③ **有两个同名易混视图**：`topic_progress`（主题级，源 `courses.status`）vs `course_progress`（课程级，源 `exam_course_results`+`study_plans`，给 lastExamRate/lastExamAt/lastLearnedAt）。
- **⚠️ 已确认的坑**：`topic_progress` 用 `CREATE VIEW IF NOT EXISTS`（`kb.ts:534`）→ **对老库已存在的视图是空操作，改定义必须显式 DROP 重建**（`course_progress` 就是先 `DROP` 再 `CREATE`，`kb.ts:480-481`）。别以为改了字符串就生效。
- `topics.progress` 列已删（09-18 库域分工），真源就是这个视图。视图建在孩子库 → 进度天然按孩子隔离。
