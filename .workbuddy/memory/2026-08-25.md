## 家长登录 fetch failed 真正根因 + 服务端可配化修复（2026-08-25 18:xx）
- **现象**：打包后的 app 家长登录报 "fetch failed"（用户删除旧包要求重打）。
- **真正根因（推翻之前方向）**：打包产物里 `auth-manager.login` 被 rollup 内联成**直接 `await fetch(...)`**，`cloudFetch`/`cloud-net.ts` 整个被优化掉、根本没进包——所以之前改 cloud-net.ts 对登录报错**毫无作用**。登录用的是**全局 fetch**，目标 `getCloudApiBase()` = `https://www.aixuexihao.top/api/auth/login`。"fetch failed" = **运行程序的那台机器连不上 www.aixuexihao.top**（防火墙/离线/或端点指错）。已实测：构建机（192.168.1.201）用 node fetch 能连上云（返回 401，服务端是好的），所以问题在「用户那台机器 ↔ 云端」这一跳。
- **修复（服务端地址可配化，一劳永逸）**：① `config.ts`：`getCloudApiBase` 增加内存覆盖 + 持久化到 `userData/cloud-api-base.json`（重启保留），新增 `setCloudApiBase(url)`；② `ipc-handlers.ts`：新增 `auth:setServer`，`auth:login/register` 接受 `serverUrl?` 并调用 `setCloudApiBase`，新增 `formatAuthError` 把网络错误转成「无法连接服务端 <base>（fetch failed）。请确认地址正确 + 运行机可访问」；③ `preload.ts`：`authSetServer` + `authLogin/Register` 透传 `serverUrl`；④ `ParentLogin.tsx`：新增「服务端地址」输入框（留空=默认云端）。这样无论账号在云端还是本地 pi-web，用户都能自己填地址连上。
- **远程构建依赖不同步的坑（重要）**：只同步改动文件会导致构建失败。本次踩两个：① `electron/lib/delivery.ts`（ipc-handlers 里 `await import("./delivery")`）远程缺失 → 报错 `Could not resolve "./delivery"`；② 远程 `node_modules` 缺 `lucide-react`（本地最近加的依赖，远程只装了当时子集）→ renderer 构建 `Rollup failed to resolve import "lucide-react"`。**教训**：本地有改动后重打，务必**整目录重同步 `electron/ src/ templates/` + 配置文件**，并 `npm install lucide-react --legacy-peer-deps` 补齐可能缺失的依赖；否则 `rm -rf out dist` 后 rollup 全量重编会暴露所有不同步。
- **重打结果**：0.1.0 deb(138M)+AppImage(184M) 构建 DIST_EXIT=0，产物含 `无法连接服务端`/`auth:setServer`/`authSetServer`/`服务端地址`，已拉回 `dist-ubuntu/`。
- **未决**：若用户账号实际在本地 pi-web（按项目约定「家长账户写在本地 pi-web :8000，暂不连远程」），需在登录页填对应地址（如 http://<pi-web-ip>:8000）才能登录；若确为云端但运行机无外网，则需换能联网的机器安装。

## ⚠️ 修正：cloud-net fetch 栈选型（2026-08-25 19:5x）
- **之前误判**：上一轮日志写「electron.net.fetch 报 fetch failed、Node 全局 fetch 反而能连」——那只是**构建机（192.168.1.201）**的特例，不能作为普遍结论。
- **新事实（dev 机器）**：用户 `npm run dev` 报 `无法连接云端服务（https://www.aixuexihao.top/api/license）：fetch failed`，但**本机浏览器能访问该地址**。根因 = 纯 Node 全局 fetch 在**企业代理 / 自签（MITM）证书**环境下失败（Node 不读系统代理、也不信任系统证书库里的企业 CA）；而浏览器（Chromium 栈）信任。
- **正确选型（已改）**：`cloud-net.ts` 改为**优先 `electron.net.fetch`（Chromium 网络栈）**，Node 全局 fetch 仅兜底。原因：`electron.net.fetch` 与浏览器**同栈**——遵循系统代理 + 读取系统证书库，本机浏览器能通的地址它必能通。这正是 dev 机器 + 打包机（若走系统代理）都该用的一路。
- **复用铁律**：Electron 主进程里凡涉及「访问外部 HTTPS 云端」，**默认用 `electron.net.fetch` 而非 Node 全局 `fetch`**，除非明确不需要代理/证书兼容。本机浏览器能开、应用内 fetch failed 的诡异差异，90% 是代理/证书问题，直接切 `electron.net.fetch`。
- 本地 `npm run build` 通过；远程整同步重打 0.1.0（DIST_EXIT=0），deb(138M)+AppImage(184M) 已拉回 dist-ubuntu/。
