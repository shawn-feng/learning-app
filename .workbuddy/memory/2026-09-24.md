## 15:10 ISSUE-147：评估「工具调另一个 agent」是否 pi 里的最优范式（用户追问）

- **缘起**：用户问「网页工具其实调用的是一个编程 agent，调用另一个 agent，pi 是否有更好的方案，比用工具好的方案？」
- **核实方式**：逐条读 pi-coding-agent **0.84.1** 源码 + 官方 docs/examples（不猜）。
- **结论 1（范式没错）**：pi **官方刻意不做 sub-agent**（`README.md:500`「**No sub-agents.** There's many ways to do this. Spawn pi instances via tmux, or build your own with extensions, or install a package」；`docs/usage.md:303` 同口径）。
  而其**唯一参考实现 `examples/extensions/subagent/` 本身就是一个工具**（`docs/extensions.md:2970`：`registerTool` + `exec`）⇒ **「用工具调子 agent」就是 pi 官方范式**，不存在"更高层的官方替代通道"。
- **结论 2（SDK 无委派原语）**：`createAgentSession` 选项（`dist/core/sdk.d.ts:10-54`）**无任何 subagent 字段**；`AgentSessionRuntime`（`agent-session-runtime.d.ts:44`）只有 `/new` `/resume` `/fork`（会话分叉，非委派）。能用的零件只有 `subscribe`(:276) / `onUpdate` / `steer·followUp·abort`(:371/374/431) / 官方 subagent 示例 / 原生 Skills。
- **结论 3（真差距＝四个机制）**：官方 subagent 做了、本项目没做——
  ① 子进程 stdout JSONL 逐行解析回传（官方 `index.ts:379`）↔ 本项目编程会话 **0 处 `subscribe`**；
  ② `onUpdate` 每次事件后回报（`:314-317`）↔ **全仓 0 处**（唯一命中 `display-tool.ts:47` 未使用的 `_onUpdate`）；
  ③ `signal`→`killProc`（`:400-408`）↔ abort 不传播到嵌套会话；
  ④ agent 定义外置（markdown frontmatter 配 `model`/`tools`）↔ 硬编码在 `buildProgrammingPrompt()` 26 行 + 代码写死 `["read","write","edit"]`。
  官方还额外支持 **parallel（8 任务/4 并发）+ chain（`{previous}`）**，本项目单次串行。
- **结论 4（不换子进程）**：服务端是 esbuild **单文件** `server/dist/server.cjs`（`docs/PACKAGING.md:87`），pi 已内联 → spawn 需单独分发 pi CLI+node_modules；且模型 runtime 是 `getWorkerRuntime` **从家长 app_settings 动态读**，跨进程要重建凭据链 ⇒ 性价比不成立。
- **推荐（待拍板，未改代码）**：**路线 B 进程内补齐四机制**（照抄现成样板 `parent-registry.ts:240` 的 `attachStream`）——一举修掉 ISSUE-146 的 240s 误杀 + 「黑洞 11 分钟」；
