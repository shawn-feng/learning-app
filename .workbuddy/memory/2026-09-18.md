## 设计讨论（续）：四表关联查询 + 通用实体存储定调
- 用户问：主题表/课程表/知识点表/题库表 这四个表的关联查询在通用实体存储里怎么做？
- 关键事实：这四表在现有代码已是**真关系表**且有 JOIN——`topics`(kb.ts/parent-lib.ts)、`courses`(topic+uuid+status)、`knowledge_points`(course_uuid 外键, UNIQUE(course_uuid,name))、`question_bank`+桥`course_knowledge_questions`(course_id/knowledge_point_id/question_id 复合主键)。现有 `listCourseContent`(ckq JOIN kp JOIN qb)、`listTopicKnowledgePoints`(kp JOIN courses)、`course_progress` 视图均为 JOIN。
- **定调（用户已认同方向）**：不要把这四表扁平化进 `entities(ns,data_json)` 一张 JSON 表——多跳关联查询(主题→课程→知识点→题)在 JSON 里要应用层手搓 JOIN，且丢失 UNIQUE/PK 约束与现有视图。
- 正确架构 = **通用实体 API 做 facade + 存储按性质分流**：
  - 工具无关操作(修 ISSUE-110 盲区) → 统一 `listEntity/readEntity/queryEntity/updateEntity/appendEntity` 五个原语，前端/agent 永远走这层，不感知背后存储。
  - 灵活 schema → 仅用于**用户自定义场景**(习惯打卡/自定义考核等)，才进 `entities(ns,data_json)`。
  - 关联查询(四表) → **保持关系表**，API 背后对 course/knowledge_point/question 等 namespace 直接生成 SQL JOIN（如 queryEntity('question',{topic}) 内部展开成 topics JOIN courses JOIN ckq JOIN question_bank）。
- 一句话：通用 API 是门面，背后异构存储；强关联核心保持关系表，只有家长自定义低频场景才用 JSON 实体表。Markdown 方案被否定（对"灵活+工具无关"无独特贡献，反引入文件系统坑）。

## 排查：`parent_db_read` 查「论语学而篇第一章 教学方法/教学文案」耗时 221s（用户报障）
- 数据源：`server/data/agent-sessions/86a84278-…/parent-data/2026-09-18T10-31-45-464Z_…jsonl`（47 行）。该问 19:27:23→19:31:04 本地，**221.2s**。

- **用户追问「为什么会有列名错？为什么还需要 describe？」→ 定位到设计缺口（重要）**：
  - 事实：数据管理 agent 的 prompt **只有表名、没有列名**；`parent_db_read` 的 JSON Schema 里 `table` 是裸 `Type.String()`、`columns` 是 `Type.Array(Type.String())`，**无任何枚举**；工具描述只写「先用 parent_db_describe 看表名与可用列」。→ 模型第 1 次调用时**结构性只能猜列名**（它猜 `display_name` 是想取主题展示名，真实列叫 `name`）。
  - `parent_db_describe` **不带 table 时只回表清单（720 字符，不含任何列）**，拿列必须逐表再调 → describe 实为 **N+1 往返**（#28 拿 topics、#30 拿 courses）。
  - 设计原话（9/18 讨论）是「注册表整体数据驱动，API 运行时读，单一真源、**自动生成 prompt 工具描述**」——前半段（describe/校验/派生只读面读同一份）已实现，**后半段「自动生成进 prompt/schema」根本没实现**。describe 因此不是设计必需品，而是「元数据没进 prompt」的补丁。

  - 建议新增 F7 注册表紧凑清单常驻 prompt + F8 `table` 参数加 enum + F9 describe 降级为「写场景/动态注册兜底」。
- **用户否决 F8（describe 支持一次多表），理由「关联查询应该是注册表的功能」——接受，F8 撤回，改定 F10**：
  - 用户论点成立：F8 是「让模型把多张表列清单一次拉回来、在脑子里手搓 JOIN」，等于把引擎该做的 JOIN 推给模型（N 次往返 + 每一跳信息都进上下文 + 易漏跳）。正确方向是让**注册表承载关系、引擎生成 JOIN**。
  - **现状恰恰相反（源码证据）**：① `TableSpec.refChecks`（唯一的关系声明）只在**写侧**，`parentReadableRegistry()` 逐字段映射时**只带 table/label/desc/columns，把 refChecks 丢掉了**（`db-channel.ts:674-690`）；② `ReadableTableSpec`（L489-494）**没有任何关系字段**；③ 真正的多跳 JOIN **硬编码在领域模块**里——`assess-content.ts:189`（kp↔courses）、`:330-331`（ckq↔kp↔qb）、`:415-416`（courses↔ckq↔kp）、`kb.ts:302/305`（exam_plan_courses↔courses↔exam_plans），靠专用工具暴露；④ 全仓**无 `joins`/named-path 概念**（grep 确认）。

  - **F10 定义**：注册表新增 `refs`（refChecks 泛化、读侧可见）+ `paths`（命名路径：hop 链 + 可过滤列 + 可返回列）；读工具新增 `path` 参数（**只允许注册过的路径，不允许模型自由拼 JOIN**，与「无自由 SQL」同一安全姿态）。示例 `{path:"topic_questions", where:{"courses.topic":"lunyu"}, columns:["question_bank.id","question_bank.behavior"], limit:20}` 一次拿到「lunyu 下全部题」——实测该路径口径 = **3576 题 / 489 课**（现在要 agent 4 次分步 read 自己在上下文里拼）。

## 评估：当前实现是否符合「namespace 注册表 + 通用 API」原设计（用户提问）
- 用户问：设计 namespace 注册表做通用 API 的**目的就是不让 agent 再写 SQL**，让我回顾方案并评估当前实现是否符合设计。
- **设计契约（4 条，来自 9/18 讨论 + ISSUE-105）**：① agent 永不写 SQL（只给实体/操作/数据）；② 注册表承载**实体类的关系查询**——新增一个查询=新增一个 namespace 配置、零代码；③ namespace **进 prompt**（agent 知道有哪些实体与关系）；④ 灵活 schema＝注册新 namespace（Tier1 人写 DDL+注册／Tier2 设计器 agent 调 `defineNamespace` 写 registry 表，零 DDL 零发版）；⑤ 5 原语 list/read/query/update/append，filter 走 **SQL 下沉**。
- **审计结论：只有 ① 完全达标，②③④ 基本未落地，⑤ 合并简化**。当前实现 = **ISSUE-105「方案 B」加长版**（通用行级 CRUD + 只读面），而不是用户后来提出的 namespace 关系查询方案——方案 B 原文就写明「不能 JOIN、不能聚合、不能改表结构」。
- **新增可复用工具 `server/probe-registry-drift.ts`**（`npm run probe:registry-drift`，有漂移 exit 1，报告写 `server/registry-drift.txt`）：逐表比对注册表声明列 vs 库内真实 schema。**首跑即见系统性漂移**：
  - **家长库**（51 个，代码注册表统一作用，按库去重）：`topics` 缺 `method_spec`；**`courses` 缺 `uuid`**；`question_bank` 缺 `id/created_at/updated_at`；`knowledge_points` 缺 `id`。→ **通用 API 内部断链**：`knowledge_points.course_uuid` 要求 courses.uuid，但 courses 的 uuid 没登记 → 读不回来、也查不到；`question_bank.id` 同理（挂载桥要它）。
  - **孩子库**（415 个，取最大库比对）：**`topics` 注册表声明了库里不存在的 `assess_method` → 该表用默认全列读必然报错**（实测 `SELECT name, topic_key, method, assess_method FROM topics` → `OperationalError: no such column: assess_method`），是必现 bug；另有 14 张表大量列未登记（`study_plans` 12/22、`exam_plans` 12/23、`points_ledger` 8/15、`courses` 6/13…）。
  - **未被注册表覆盖的表**：家长库 `meta`（预期，迁移标记）；孩子库 **`meta, tags(93 行), child_todo_stats(4 行), todo_items(85 行)`** ← 新场景没跟进注册，正说明「加表=改代码发版」而非「注册一行」。
- 关键判断：漂移的**根因不是疏漏，而是架构**——注册表是**手写 TS 常量数组**（`parentLibTableRegistry()` 返回字面量）而非数据驱动表；且 `childKbReadableRegistry()` 是手写、`parentReadableRegistry()` 才是派生，两份真源必然分叉。设计原话「注册表整体数据驱动、API 运行时读、自动生成 prompt 工具描述」这半句从未实现。
- **F10（path 查询）不违背原设计**：path 是**注册在注册表里的命名路径**，agent 只能选路径名、不能拼 JOIN，与「不给自由 SQL」同一姿态；它正是补上「②」的那一半。
- 会话 doc 修正：ISSUE-105 的 kb 路径写错（`data/parents/<pid>/kb/<cid>/kb.sqlite` → 实际 `data/kb/<parentId>/<childId>.sqlite`）。
