## 调研：benefit-auth 如何管理「家长账户有效期」，客户端拿到的和上游一致吗

用户问：「server 端要去 benefit-auth 公网服务校验家长账户有效期，这个有效期是多少？app 客户端从 server 端拿到的和 benefit-auth 一样吗？benefit-auth 如何管理有效期？」

**结论一：不存在固定时长，有效期是从权益算出来的；本账号是永久。**
- 生效端点：`benefit-auth/app/routers/legacy.py` `GET /api/account/license`（learning-server 的认证上游，2026-10-08 起）。
- 算法（`_compute_expiry`，legacy.py:64）：遍历该 user 的 `entitlements`（`status != 'revoked'`），对每条 `{"type":"vip_days","days":N}`：到期 = `granted_at` 按 **Asia/Shanghai** 落到日 + N 天，取当天 **23:59:59+08**；多条取 **max（不叠加）**；无权益 → `expires_at=now`、`is_expired=true`。
- `special_permanent_users`（settings 表，字符串包含匹配）→ `2099-12-31T00:00:00+00:00`。
- 生产实测（ECS 只读）：
  - `test@qq.com`（benefit user `b0736e0d…`，映射旧 parent `86a84278…`）= **永久 2099**；201 缓存与上游 **逐字段一致**（`parent_id/email/plan/max_children=4/features/starts_at/expires_at/status/is_expired`）。
  - 另一账号「闻闻来读书」（`a4106dba…`）：2 条 vip_days（10-08、10-14 各一次）→ **2026-10-21 23:59:59+08** 到期。
  - 库内 2 user / 6 权益（2×vip_days 7 天 + 4×points 10）。
- 注意两个「7 天」不是一回事：**vip_days 每次 7 天**（任务奖励）≠ **server 自签 session JWT 的 7 天 TTL**（`server/src/config.ts` DEFAULT_TTL_DAYS=7）——ISSUE-187 撞的是后者。

**结论二：客户端拿到的=上游原值（透传），差异只在降级缓存。**
- server `/auth/login|douyin` 与 `/auth/license` 都直接 `upstreamLicense()`（`server/src/auth/proxy.ts:92`）→ 原样存 `parents.license_json`、原样回客户端（`routes/auth.ts:51/281`）；上游不可达 → 回 `parents.license_json` 缓存 + `degraded:true`（routes/auth.ts:294），客户端 `fetchLicense` **不判 degraded**，照旧当权威。
- `is_expired` 是 benefit-auth **取数那一刻**算的；客户端只在启动/任务门禁轮询时刷新，长开 app 期间本地快照可能过期。
- server 只验 session JWT，**不校验 license 是否过期**（全仓 `is_expired` 仅出现在类型定义）——过期账号仍能登录/调用，靠客户端 `checkAuth` 的 `is_expired` 或 401 才踢（ISSUE-160 遗留口径未变）。

**结论三：benefit-auth 的管理机制。**
1. 数据：`tasks`（`reward_config`，例 `{"type":"vip_days","days":7}`）、`task_instances`（claimed/submitted/granted/rejected/expired）、`entitlements`（active/used/revoked + `granted_at`）、`settings.special_permanent_users`（手动维护，值里带备注）。
2. 每日任务：ECS `/etc/cron.d/benefit-daily-task` **每天 00:10** 调 `POST /api/admin/daily-task`（`routers/admin.py:151`）→ 建当日一条「N月N日 · 官方视频互动任务」（vip_days 7、`max_times_per_user=1`、00:00~23:59:59+08），并同步创建抖音经营任务活动（点赞/完播/评论，账号维度；转发走人工审核）。
3. 发放三条路：用户点验证 `me.py` `direct-verify`/`check`（真查抖音 `open.business.task_verify`）→ `_grant_entitlement`（me.py:492）；`poller.py` 每 60s 自动扫（`_grant_if_needed`:151）；人工审核 `/api/admin/review`（admin.py:250）。
4. 撤销：权益 `status='revoked'` 即不计入；任务 rejected 不发放。
5. 老机制（已废）：cloud-service 时代注册送 **30 天**订阅（`cloud_license.py` 的 `compat_subscriptions`，`now+days` 滚动）——现在 `/api/license` 是 **410**（`deprecated.py`），该文件未挂载，仅历史。

**发现的小问题（未改，待拍板）**
- ⚠️ `_compute_expiry` 把 SQLite `CURRENT_TIMESTAMP`（naive **UTC**）当 **系统本地时区**解释（`.astimezone(TZ)`），而 ECS 时区是 **CST(+08)**（`timedatectl` 实测）→ 北京时间 **00:00–07:59** 完成的奖励（= UTC 16:00–23:59 前一天）会算**早一天**、少 1 天；每日任务 cron 00:10，用户一完成就中招。修法：解析后先 `replace(tzinfo=timezone.utc)` 再转 +08（poller 写的 `+00:00` 带时区、不受影响）。
- 文档漂移：`server/src/routes/auth.ts:119` 注释仍写「云端在 /api/license 查询时自动延长（sync_benefit_entitlements）」——那是已下线的 Cloud 路径；现为 `/api/account/license` 按权益实时算。
- `features` 形状不一致：legacy 端点返回数组 `["learning"]`，server 类型声明是 string（仅类型层，不影响使用）。
