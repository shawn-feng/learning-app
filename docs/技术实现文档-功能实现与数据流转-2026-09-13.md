## 0. 架构与数据真源总览

### 0.1 客户端 / 服务端拆分（**定案：必须切服务端，客户端永不再有 agent**）

- **所有 AI agent 运行在服务端**：家长会话、家长内容会话、孩子会话（main / scene / course:*）、考核出题判分、编程 agent、每日总结 worker agent，全部在 `server/src/agent`、`server/src/worker` 内执行，由服务端持有会话与业务库。
- **客户端（Electron）只负责**：渲染 UI、采集本地输入（麦克风 / 键盘 / 文件）、承载资料页桥（PiBridge）、本地 ASR/TTS provider 直连第三方、本地定时（课程提醒 / 定时备份）与配置缓存；对话经 `electron/lib/server-agent-client.ts` 的 **SSE 客户端**（`fetch` + `ReadableStream`，Node 主进程无 `EventSource`）连服务端，再把服务端事件翻译回渲染层既有的 `pi:*` 通道（渲染层契约不变）。
- **服务端 agent 交互路由**：孩子 `GET /api/v1/agent/:childId/stream`（SSE）+ `POST /api/v1/agent/:childId/prompt` + `POST /events`（页面事件上行）+ `GET /history` + `POST /reset` + `POST /abort`（中止当前一轮，ISSUE-095）+ `POST /page-result`（受控操作回执）；家长 `GET /api/v1/parent-agent/stream`（SSE）+ `POST /prompt` + `POST /abort`（同 ISSUE-095）+ `POST /reset`。SSE 支持 `Last-Event-ID` 重放，避免弱网重连丢事件。
- **agent 中止（ISSUE-095，2026-09-14）**：客户端「停止」按钮 → 主进程 `pi:abort`（不再 no-op）→ `abortChildAgent` / `abortParentAgent`（`server-agent-client.ts`）→ 服务端 `POST /agent/:childId/abort` / `POST /parent-agent/abort` → 注册表 `abortSession` / `abortParentSession` 调 SDK 原生 `session.abort()`（中止当前操作并等待 agent idle）。`pi:abort` 的 childId 语义：`"parent"`/`"parent-content"` = 家长会话，否则为孩子 id；孩子 abort 的 `session` 省略时中止该孩子全部会话（main/scene/course:*）中 busy 的一轮。中止后 submit 的 finally 清 `busy` 并经 SSE 推 `turn_end` → 前端 `pi:reply_end` 解禁忙碌态（前端 handleStop 无改动）。
- **不再有"能力探测 / 兼容旧服务端"的过渡逻辑**：客户端不做"服务端是否支持 X 才启用 Y"的判定（原 `/version` features 门控作废，见 §2.5 与 ISSUE-088）。

## 1. 登录、许可与孩子管理（§2.1–2.2、§3.2）

### 1.1 实现过程（**无 agent 参与**）
- **前置：配置服务端地址**：客户端必须先保存服务端地址（通用设置页）。未配置时 `checkAuth` 直接判定为未登录（不进入家庭主页），避免用本地缓存凭证绕过服务端。
- **家长云端登录**：`ParentLogin` 页 → 主进程 `auth-manager.login` → `POST /api/v1/auth/login`（注册走 `POST /api/v1/auth/register`）→ `routes/auth.ts` 的 `authenticate` → `auth/proxy.ts` 转发公网认证服务（`/api/auth/login`）。拿到 `{ cloud_token, parent_id }` 后再请求公网 `/api/license` 取 `license_json` → upsert `parents`（**冲突键为 `id` = 公网 `parent_id`**，非按 email 查重）→ `signSession` 签 JWT 下发。响应体为 `{ session_token, license }`；**`cloud_token` 仅存服务端，不下发客户端**。全流程无任何 LLM / agent 调用。
- **许可信息**：客户端把 `license`（含 `plan / max_children / features / starts_at / expires_at / status / is_expired`）连同 `session_token` 缓存到本地 `license.json`。`GET /api/v1/auth/license` 可随时刷新：服务端用 `parents.cloud_token` 向公网重取 license 并回写 `license_json`；公网 401 → 客户端强制重登；公网不可达 → 返回本地缓存 `license_json`（`degraded: true`）。`checkAuth` 在本地凭证未过期且云端不可达时离线放行，云端明确判定过期 / token 失效则清除凭证强制登出。
- **孩子数量上限**：`license.max_children` 的校验在**客户端主进程** `child:add`——先经 `/auth/license` 向云端确认真实上限（防改本地 `license.json` 绕过），达到上限返回「已达孩子数量上限」。**服务端 `POST /children` 不做上限校验**。
- **添加/编辑/删除孩子**：UI 表单 → 主进程 → REST 写 `children` 表（`POST /api/v1/children`、`PATCH /api/v1/children/:id`、`DELETE /api/v1/children/:id`），**无 agent**。
- **孩子密码**：密码以 **bcrypt 哈希存于服务端 `children.profile_json.passwordHash`**（2026-08-30 起多设备共享），登录由 `POST /api/v1/children/auth` 在**服务端**做 `bcrypt.compare` 校验；客户端本地 `data/children/<childId>/profile.json` 另缓存一份哈希，仅在服务端不可用 / 未登录时回退本地校验。`PATCH /children/:id` 对 `passwordHash` 有事故防护：**无 `forcePassword` 标志、或哈希不是合法 bcrypt 形状时忽略该字段**，防止旧 / 空哈希覆盖真实密码。密码重置由家长在详情页显式触发（带 `forcePassword`）。
- **删除孩子**：`DELETE /api/v1/children/:id` 仅 `DELETE FROM children`（归属校验 `id + parent_id`）；客户端同时递归删除本地 `data/children/<childId>/` 目录。**服务端该孩子的其余数据一律不清理**（已知缺口，见 §17）：孩子库 `kb/<parentId>/<childId>.sqlite`、会话目录 `agent-sessions/<parentId>/<childId>-<slot>/`、`files` 表行与 `data/files/` 附件，以及 `session_messages` / `worker_state` / `study_plan_items` / 孩子库考核结果四表（`exam_plan_courses` / `exam_course_results` / `knowledge_point_records` / `speech_assessments`） 等所有带 `child_id` 的行。（注：`materials` 表与 `materials/` 目录是**家长维度**，不随孩子删除。）

### 1.2 数据流转
```
前置：客户端保存服务端地址（未配置 → 判定未登录）
家长表单 → POST /auth/login → 公网认证(cloud_token,parent_id) → 公网 /api/license
        → upsert parents(id,email,plan,cloud_token,license_json) → 签 JWT(session_token)
        → 客户端缓存 license.json(license + token)
家长表单 → POST/GET/PATCH/DELETE /children → children(id,parent_id,name,profile_json,created_at,updated_at)
孩子密码 → bcrypt 哈希 → children.profile_json.passwordHash（服务端校验优先）
                       └→ 本地 data/children/<childId>/profile.json 缓存（离线回退）
```

### 1.3 数据结构（全局库 `server.sqlite`）
```sql
parents( id TEXT PK, email TEXT NOT NULL, plan TEXT, cloud_token TEXT,
          license_json TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL );
children( id TEXT PK, parent_id TEXT NOT NULL, name TEXT NOT NULL,
          created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
          profile_json TEXT );   -- 头像/年龄/年级/兴趣/AI 名/aiEmoji/aiPersonality/passwordHash
settings( key TEXT PK, value_json TEXT NOT NULL DEFAULT '{}', updated TEXT );
```
> 说明：`children.profile_json` 不在建表语句里，而是旧库迁移时 `ALTER TABLE children ADD COLUMN profile_json TEXT` 补上的（2026-08-30 孩子详情 + 密码哈希上云）。`profile_json.passwordHash` 为 bcrypt 哈希，是服务端密码校验的唯一真源。

登录、许可、孩子管理**均无 agent 参与**，由 REST 直接落库（全局库 `server.sqlite`）：

| 工具 / 路由 | 库 | 表 | 读取字段 | 写入字段 | 挂载情况 |

## 2. 模型与系统设置（§2.3、§3.10）

### 2.1 实现过程（**无 agent 参与写；agent 仅读取注入**）
- **存储模型**：所有家长级配置都写主库 `settings` 表，**键名按家长隔离** `key = "{parentId}:{配置名}"`（2026-08-30 起，模型与 key 都跟家长账号，不做全家长共用）。配置名只有三个：`auth`（模型 API 密钥封套）、`app_settings`（默认/编程/视觉模型、TTS 等）、`scheduler_config`（定时任务与课程表）。
- **写入路径（两条，均纯 REST，无 agent）**：
  1. **`POST /api/v1/config/set`**（通用单键写）：`{ key, value }` → `isAuthKey` 时 `encryptJson` 加密、其余 `JSON.stringify` → `INSERT ... ON CONFLICT(key) DO UPDATE` → `bumpConfigRevision`（`meta.config_revision` 全局自增）。客户端「保存设置」走这里（`pushConfig`）。
  2. **`POST /api/v1/models/apikey` / `POST /api/v1/models/app_settings`**（设置页专用）：前者把 `{ provider: { type:"api_key", key } }` 合并进 `auth` 封套后加密落库；后者对 `app_settings` 做**读-改-写合并**（只更新传入字段）。**收口到服务端的原因**：合并逻辑若放客户端，两设备并发改 key 会互相覆盖。
- **加密**：`auth` 键落盘前 `AES-256-GCM`（封套 `{v,iv,tag,data}`）；密钥取自 `SERVER_SECRET` 环境变量（sha256 派生，≥16 字符）或首启随机生成 `<dataDir>/.secret`（32 字节 hex）。读取时 `decryptJson`（失败回退原样的兼容分支）。
- **下发与轮询（revision 机制）**：`settings` 任一写入都会 `bumpConfigRevision`（全局 revision，家长 A 改配置 B 也会拉一次全量，但只拿到自己的键，无害）。客户端每 2 分钟轮询 `GET /api/v1/config/revision`，revision 与本地 `cache/config-revision.json` 不一致（或本地 `auth.json` 缺失）才拉 `GET /api/v1/config`；**登录成功后强制全量拉一次**（`syncOnce(true)`）。`GET /config` 只返回 `{parentId}:` 前缀的键，`auth` 会**解密回原始对象**再下发（多设备密钥同步环依赖此行为，故不做过滤）。
- **落地为本地文件（读取方无感）**：拉到的 key 按映射写回本地 JSON——`app_settings`→`app-settings.json`、`scheduler_config`→`scheduler-config.json`、`auth`→`auth.json`，并做**防覆盖合并**：`app_settings`/`auth` 浅合并（本地独有字段保留）；`scheduler_config` 顶层浅合并 + **children 按 childId 字段级深合并**，且 `classTimes/classTemplates/classWeek` 服务端为空而本地非空时保留本地（防 ISSUE-053/059 的课程表被回拉清空）。
- **补齐缺失密钥**：每次拉取后执行「只补缺、不覆盖」——本地有、服务端缺的 `auth` provider 条目与 `defaultModel/programmingModel/visionModel` 字段合并补传，避免服务端 worker 报「No API key」。
- **Agent 提示词（系统内部维护）**：提示词存服务端 `agents.sqlite`（`<dataDir>/agents.sqlite`，全局，`scope/ref` 区分家长/孩子），表 `prompts`（当前用户版本，`PK(scope,ref)`）与 `prompt_history`（旧版，最多回看 50 条）。**ISSUE-083 后已移除用户端查看 / 编辑入口**（原 `AgentPromptEditor` 组件、家长端「AI 提示词」按钮、孩子详情页提示词 tab 均已删除），仅保留 db-op `agents.save` 供系统内部 / 运维写入。**这是数据写入，不是 agent 执行**；开会话时由服务端 `getAgentPrompt` 读取注入，agent 本身不写提示词。客户端只保留**只读缓存** `data/cache/agents-cache.json`（不持有业务库）。
- **agent 读取设置与选模型**：会话创建时 `ensureEntry` 调 `readParentSettings` 取 `auth`（解密）+ `app_settings` + `scheduler_config` → `pickWorkerModel(runtime, appSettings)` 决定本次会话模型。同一入口被多处复用：家长会话、孩子会话、考核引擎、`summarize_conversation`（kb-summary）、programming agent、`POST /models/check`（建运行时真实探测密钥）、worker 定时任务（`recording` 等）。**ISSUE-126 起（2026-09-21）**：孩子/家长交互会话在**每轮提交前**还会经 `server/src/agent/model-sync.ts` 的 `syncSessionModel` 重读 `app_settings` 对比默认模型，变更则 SDK `session.setModel()` **原地热切换**（会话历史/工具/上下文全保留，不销毁重建；setModel 自带新 provider 的 key 校验，失败则本轮不发送并把原因回给前端）。**错误可见化**：`attachStream` 的 `message_end` 分支检查 `stopReason === "error"`（SDK 对模型 API 失败不发 error 事件，只记带 `errorMessage` 的空 assistant 消息）→ 转发 `error` 事件（`friendlyModelError` 翻译成可读文案）；客户端 `reply_end` 空回复兜底（Learn 主/场景 + ParentChatPanel）不让你永远「等待模型返回」。

### 2.2 数据流转
```
设置页 → POST /config/set（或 /models/app_settings、/models/apikey）
       → settings["<parentId>:auth"|":app_settings"|":scheduler_config"]（auth 加密落盘）→ revision+1
客户端每 2min → GET /config/revision（比对本地 cache/config-revision.json）
                └ 变化/登录首拉 → GET /config（仅本家长键，auth 解密下发）
                                  → 写回本地 app-settings.json / scheduler-config.json / auth.json（防覆盖合并）
                                  → 本地有服务端缺的 key/模型字段 → 反向补传 /config/set
下次会话 ensureEntry → readParentSettings(auth+app_settings+scheduler_config) → pickWorkerModel → 调 LLM
每轮提交前（ISSUE-126）→ syncSessionModel 重读默认模型，变更则 session.setModel 原地热切换 → 调 LLM
模型 API 失败（ISSUE-126）→ SDK 记 stopReason:"error" 空消息 → attachStream 转 error 事件（friendlyModelError）→ 前端 ⚠️
提示词（系统内部 db-op agents.save，无用户 UI 入口）→ agents.sqlite.prompts(scope,ref,content) → 开会话时 getAgentPrompt 注入
```

### 3.5 家长库 ↔ 孩子库的课程关联与同步（**无定时同步**；2026-09-21，ISSUE-123）

> 库域分工（2026-09-18）后两个库各管一半：**家长库 = 课程结构与教学内容的真源**；**孩子库 `courses` = 该孩子的进度 + 显示引用**（教学字段副本已删）。两者**没有任何定时同步**，唯一自动写入口是「分配时」一次性写入（`kb.courses.upsert`）。

- **关联锚点两层**：① `courses.topic_key` = 真引用（孩子库 `topics.topic_key` → 家长库 `topics.topic_key`）；② `courses.uuid` = 家长库 `courses.uuid` 的分配时冻结副本（`resolveCourseUuid` 现查、查不到存 `""`）。主键仍是 **(topic, title) 显示名对**（不是 uuid）。
- **uuid 的定位**：它是后补的引用列（`ALTER TABLE ADD COLUMN uuid` + 存量回填 + 唯一索引），**不取代名字身份**；产品语义全程按名字寻址（考核 `scope_json.courses`、资料路径、计划列表都是名字）。换 uuid 主键属 ISSUE-123 的「方案 B」，未做。
- **⚠️ 改名必须保 uuid**：`parent_upsert_course` 是 `ON CONFLICT(topic,title)` upsert → **改 title = 新建一行/新 uuid、旧行残留**，孩子库那条进度就永久对不上（R1）。改名只能走 **`parent_rename_course`**（原地 UPDATE + 联动孩子库）。
- **漂移风险清单（ISSUE-123）**：R1 家长库改名/重建 → 孩子库孤儿行；R2 家长库新加课 → 孩子库没有（考核创建报「课程在孩子库里不存在」，`parent-plans.ts` 按**孩子库**校验）；R3 `resolveCourseUuid` 原按 **title 单字段全局** 兜底 → 跨主题重名课静默连错 uuid（**2026-09-21 已收窄为同一主题内匹配**，并支持 topic 传中文名）。
- **手动同步动作**：`parent_sync_courses_to_child`（按 uuid 三态，见 §3.4）。**⚠️ 同步范围＝该孩子「已分配的主题」**（2026-09-21 修正）：孩子能否看到某课完全由 `kb.topics`（主题分配）决定，未分配主题的课写进孩子库孩子也看不到，且日后一分配会一次性冒出上百门没分配过的课 → 所以未分配主题**整体跳过**（返回里列明主题与门数）、`topic` 参数落到未分配主题**直接拒绝**、孩子一个主题都没分配**拒绝执行**、补 uuid 也只限范围内。`parent_rename_course` 不受此限（只按 uuid 改已存在的行，不新建行、不扩范围）。**名字寻址路径全量清单**（改名的影响面：教学上下文 `session-registry.ts:371/385`、考核校验 `parent-plans.ts`/`plan-tools.ts`/`exam-retake.ts`/`exam.ts` 四处、进度回写 `db.ts:688+` 等）见 `ISSUES/ISSUE-123.md`。
- **仍未解**：改名后**已生成考核计划的 `scope_json.courses` 里存的是旧课程名** → 旧计划取题会失败；当前只在 `parent_rename_course` 的返回里提醒家长核对，未自动改写计划。

### 3.6 家长聊天附件的读取链路（2026-09-21，ISSUE-124）

> 背景：家长 agent 跑在服务端，**读不到家长电脑上的文件**。旧实现把附件标记里的本机路径（`parents/<pid>/uploads/x.jpg`）当材料相对路径去查 → 永远「材料不存在」，现场 agent 只能让家长改用文字。

- **落盘 + 上送**（客户端主进程 `file:save_upload_parent`，`electron/lib/ipc-handlers.ts`）：写完本机 `data/parents/<parentId>/uploads/<ts>-<name>` 后，**顺带** `POST /api/v1/files/upload`（multipart；服务端按 session parent 归属，见 `server/src/routes/files.ts`）→ 磁盘 `<dataDir>/files/<parentId>/<uuid><ext>` + `files` 表行。IPC 返回 `{ path(本机相对路径，用于本机打开/预览), ref(`files/<id>`，服务端可读引用), uploadError(上送失败时的原因) }`；失败不阻断本机落盘，只在输入框下方提示。
- **标记**（渲染层，`src/lib/attachment-ref.ts` → `attachmentMarker`）：`【附件图片：名字|引用】` / `【附件文件：名字|引用】`，**引用优先 `ref`**，无 ref（老客户端 / 上送失败）退回本机 `parents/<pid>/uploads/…`。Web shim 同协议：`saveParentUpload` → `/files/upload`，引用 = 裸 file id（不带前缀）。
- **读取**（`server/src/agent/upload-ref.ts` → `resolveAttachmentRef`，被 `parent_read_image` / `parent_read_upload` 共用）三类引用：
  1. 裸 uuid / `files/<id>` → 查 `files` 表（`WHERE id=? AND parent_id=?`）→ `<dataDir>/files/<parentId>/<stored_path>`；
  2. `files/<x>`（不带 pid）/`files/<自己pid>/<stored>` → 直接按磁盘布局解析（先按当前家长目录找）；
  3. `uploads/<x>` / `parents/<pid>/uploads/<x>` → 补成 `parents/<parentId>/uploads/<x>`（**只有服务端 dataDir 就是那份数据的同机部署才命中**）。
- **安全红线**：① 引用里的 pid 必须等于当前登录家长，命中别的家长目录 → `forbidden` 拒绝；② 一切路径经 `resolveWithin` 沙箱校验，越界直接抛错；③ 材料库与上传区仍是两个隔离区域（`materials/<parentId>/…` 只走材料工具，上传区不进材料索引）。
- **读不到时的口径**（`missingRemoteHint`）：明确告诉 agent 去请家长「升级客户端后重新发送」或「用文字/截图说明」，并**禁止**再试 materials/uploads/parents 路径——现场就是这么绕圈失败的。
- **遗留**：孩子聊天附件同款缺口（孩子侧无读工具、客户端也不上送服务端）见 ISSUE-125。

### 4.1 Agent 操作（家长 `parent` / `parent-content` 会话，写资料磁盘）
- **会话与 prompt**：`buildServerParentPrompt` 的「课程学习资料（唯一真源）」段写明：资料在服务端、按主题目录组织（如 `lunyu/materials/lesson-01.html`）；整理资料必须用这些工具，不要用本地文件工具改真源——`parent_list_materials` 先看清现状（整理前必做）、`parent_read_material` 读正文、`parent_move_material` 移动/改名、`parent_put_material` 写入/覆盖、`parent_delete_material` **默认只演练**（返回将删清单，须先复述并取得家长同意，再带 `confirm=true` 真删）、`parent_read_image` 读教材扫描页/截图；同一段还写明「家长聊天上传的图片/文件」的标记与读法（`parent_read_image` / `parent_read_upload`，见 §3.6，ISSUE-124）。
- **挂载工具**（实际 return 数组内）：`parent_list_materials` / `parent_read_material` / `parent_put_material` / `parent_move_material` / `parent_delete_material` / `parent_read_image` / `parent_read_upload`（ISSUE-124，读聊天附件） / `parent_read_child_conversation`（ISSUE-102，读孩子对话逐字稿，只读）/ `parent_build_material`（编程 agent 工具）。
- **孩子对话读取（ISSUE-102，2026-09-15）**：`parent_read_child_conversation` 把「家长对话回顾」的读链路（`indexAgentSessionsIntoDb` 增量索引 → `querySessionMessages` 取逐字稿）封装为家长 agent 工具。
  - 参数：`child`（孩子姓名，`resolveConvoChild` 精确匹配 + 归属校验，同 `assertChildOwned` 口径）、`date`（缺省今天 / `YYYY-MM-DD` / `all`）、`days`（all 时最近 N 天，默认 3、上限 7）。
  - 输出：`孩子名：…` / `AI 伙伴名（profile_json.aiName，缺省「饺子」）：…`（assistant 附本轮工具调用名），单条 600 字符、总量 16000 字符截断；无记录时列出有记录的日期。
  - **隐私边界变更**：原基线「家长 agent 只读孩子数据 summary、不触碰原始对话」被本需求**授权扩张**为「可经只读工具读取原始对话」——仍严格只读（无任何写孩子会话的能力）+ 归属校验 + 按天/限量读取（防上下文与 token 爆炸）。prompt（`buildServerParentPrompt` 新增「孩子的对话记录（只读，家长已授权）」段）同时要求向家长汇报时概括要点、不复述原文。
- **处理逻辑与落盘（关键：磁盘 + 索引表双写）**：
  - `parent_put_material`：内容 ≤**2MB**（超出报错），写 `materials/<parentId>/<相对路径>`，**同时 upsert 主库 `materials` 索引表**，并追加 activity-log。
  - `parent_move_material`：真源内移动/改名，实现顺序刻意是「先写新 → 再删旧」（最坏留副本，不丢数据），目标已存在则拒绝；同步维护索引。
  - `parent_delete_material`：默认 dryRun 只回清单；`confirm=true` 才删文件 + 索引行。
  - `parent_list_materials`：**先 `scanMaterials` 扫盘同步索引，再查 `materials` 表**列出清单（可按 `topic` / `relPrefix` 过滤）。
  - `parent_read_material`：只读文本类（html/md/txt/css/js/json 等），超 **200KB 截断**；音视频/图片等二进制只回元数据（类型 + 大小）。
  - `parent_build_material`（编程 agent）：`outputPath` 以 `materials/` 开头 → 落 `materials/<parentId>/…`；否则落家长工作区（`workspaces/<parentId>/parent/`）；**只允许 `.html`/`.htm`**；写完校验文件存在且 **≥100B**，否则报错（防"模型声称写完但没落盘"）。注意：该路径由编程子会话直接写盘，**不经 `upsertMaterialFile`**，故索引要等下一次扫描/`/materials/index` 才收录。
- **数据生产及处理**：家长 agent 生成的资料落 `materials/<parentId>/<topic>/…`；课程行的 `html_path` 指向该相对路径，孩子端据此展示（见 §4.3）。

### 4.2 UI 上传（**无 agent 参与**）
- 入口：`MaterialManagerModal.tsx` / `TopicDetail.tsx` → `window.api.parentUploadMaterial(topicDir, subDir?)` → preload → IPC `parent:uploadMaterial`。
- 主进程弹**系统文件选择对话框（可多选）**，扩展名白名单：`html/htm/md/pdf/jpg/jpeg/png/webp/mp3/mp4/webm/ogg/wav/m4a/aac/flac`；选定后逐个 `copyMaterialIntoParent` 上传到服务端 → `POST /api/v1/materials/upload`（写磁盘 + `upsertMaterialFile` 写 `materials` 索引）；第二个参数 `subDir` 用于指定子目录（如 `media`）。

### 4.3 孩子端渲染与 PiBridge（**无 agent 参与**）
- **文档通道（asset 协议）**：iframe 顶层加载真实 URL `asset://local/parent/<parentId>/<topic>/<file>?doc=1` → 协议层回调 `serveMaterialDocument`（`electron/lib/material-doc.ts`）：
  1. 拉原始 html（经服务端），若含 `<meta http-equiv="refresh">` 则跟随**相对跳转**（最多 8 跳、禁止越出 materials 根、只跟 `.html/.htm`）；
  2. `rewriteMaterialHtmlForRender`：相对资源改写为 `asset://`（静态）或 `media://`（音视频），并注入 `<base href="media://local/parent/<parentId>/<fileDir>/">`；
  3. `injectBridge`（`src/lib/page-bridge.ts`）：注入 **PiBridge SDK** + `capture=manual` 判定 + 资料字号（`?font=`）；返回 `text/html`。选真实 URL 文档而非 dataURL/srcDoc，是为了让**页面正文 `<script>` 随正常导航执行**（ISSUE-061 的根治）。
- **资源协议**：`media://` / `asset://` 均由协议层代理到服务端 `GET /api/v1/materials/content/:id`（`id = base64url(相对 materials 根的路径)`），**无本地缓存、远程直取**。URL 里的 `parentId` 只是占位——服务端按 session token 的 `parent_id` 路由，客户端不据此取路径（故 `material-doc.ts` 传 `DEFAULT_PARENT_ID` 不影响正确性）。扩展名白名单分两套：`media://` 只允许音视频，`asset://` 允许 css/js/html/图片/字体/json/txt —— **音视频必须走 `media://`**，走 asset 会 403。
- **无显式消毒**：链路只有「跟随跳转 → rewrite → 注桥」，**没有 HTML 消毒/净化**（原文档"HTML 经消毒"的说法不成立；缺口见 §17 #9）。视频须 **H.264**（HEVC/H.265 在 Linux Chromium 无解码器，ISSUE-056）。
- **与 agent 的交互**：资料页经 PiBridge 上行事件（点读发音、提交答案、语音交互、`scene.*`）→ 客户端 → `POST /api/v1/agent/:childId/events` → 服务端 agent 注入下一轮上下文；受控下行经 SSE `page_cmd` → `MaterialsPanel.appCmd` → 页面 `PiBridge.on(...)` 执行并回执 `POST /api/v1/agent/:childId/page-result`（当前客户端 `page_cmd` 分发存在断点，见 §11 与 §17）。

### 5.2 自动完成与顺延（worker 判定逻辑，**非 agent、非 LLM**）

全部在服务端 worker 的 `worker/plan-domain.ts` 内执行，对外入口是导出的 **`runPlanStat`（三域判定 → 到期 carry → 归属日统计 → 积分结算）** 与 **`expandRecurrences`（重复计划展开）**；下表提到的 `applySignals` / `expireAndCarry` / `applyExamAttempts` 都是该文件内的**内部函数**（不单独导出）。

| 域 | 完成信号（写什么算完成） | 判定 SQL 口径 | 顺延（carry） |
|---|---|---|---|
| **学习** | **`daily_entries` 中 `block='学习'` 的记录**（title 精确等于课程名，日期落在计划 `[start_at, due_at]` 窗口内）→ `study_plans.status='done'`、`done_at=<该记录日> 12:00:00`、`result='学习完成'`；并把该条 daily 回填 `plan_id` + `plan_outcome='done'`（仅当 `plan_id` 为空，匹配不到就跳过、不造记录） | `SELECT id, course_name, start_at, due_at FROM study_plans WHERE status='pending' AND active=1`，再按 `course_name` 关联 `daily_entries`。**2026-09-11 起不再读 `courses.last_review`**（该字段无确定性写入方，旧口径判不出完成，ISSUE-076） | ✅ 到期未完成 → `missed` + 复制新行到当天（`origin='carry'`、`carry_from=<原行 id>`、窗口=当天） |
| **生活** | `daily_entries` 中 `plan_id != '' AND plan_outcome='done'` 的行（由 recording agent 写）→ `life_plans.status='done'`、`done_at=<今天> 12:00:00`、`result='生活完成（记录判定）'` | `SELECT DISTINCT plan_id FROM daily_entries WHERE plan_id != '' AND plan_outcome='done'`，再 `UPDATE ... WHERE id=? AND status='pending'` | ✅ 同上（`study_plans` + `life_plans` 两张表都在 carry 范围内） |
| **考核** | 提交端点 `POST /exam/attempts` → `persistExamResult()` **直写孩子库三层**（`exam_plan_courses` / `exam_course_results` / `knowledge_point_records`）+ `speech_assessments` + `exam_plans.status='done'/attempt_id/score/done_at` | `applyExamAttempts` 只做**单库幂等兜底**（补概要行 + 补 done_at，`DO NOTHING` 不覆盖已完成数据） | ❌ **不顺延**：考核到期未完成只置 `missed`，不复制新行（错过由家长重排；2026-09-11 拍板修正，此前误把 `exam_plans` 纳入顺延） |

- **重复计划展开（`expandRecurrences`，plan tick 先跑）**：读 `plan_recurrences WHERE enabled=1 AND (last_expanded_date='' OR last_expanded_date<今天)`；`rule='daily'` 每天命中、`'weekly'` 按 `weekday` 命中；命中则按 `payload_json` 生成当天的 `life_plans` 或 `study_plans` 行（`origin='recurrence'`、`recurrence_id=<规则 id>`）；超过 `end_date` 则把规则 `enabled=0`。
- **结算**：`applySignals` 后由 `settleRewards` 按 `reward_configs` 分档计入 `reward_daily_stats` / `points_ledger` / `points_balance`（分母只算 `active=1 AND count_in_rate=1`，`cancelled` 不计）。

> - **`exam_plans`（孩子库 `kb/<cid>.sqlite`）** = **考核计划**：出现在"今日计划 / 我的计划"里的计划行，三种来源——① **固定档**：每日/每周是**配置项**（settings `exam_fixed:<parentId>`，家长设置页维护），worker 每天（plan tick）检查配置、为当天生成（幂等，`ensureTodayExamPlans`，`kind='fixed'`/`origin='config'`）；② **自定义**：家长对话 / 管理面板**直接写入**（`kind='custom'`）；③ **重考**：提交钩子按 `retake` 标准生成（`origin='retake'`，确定性 id `retake_<原计划id>`）。**它不是场次**。
> - **考核结果（孩子库四表）**：`exam_plan_courses`（逐题明细）/ `exam_course_results`（每课概要）/ `knowledge_point_records`（知识点情况）/ `speech_assessments`（题级口语评测）。一次提交由 `POST /exam/attempts` → `server/src/exam-results.ts:persistExamResult()` 一次写全；`exam_plans` 行同时被打上 `done + attempt_id + score + done_at`。**主库 `exam_attempts` 已于 2026-09-23 废弃（DROP）**。
> - ⚠️ **列归属易错点（2026-09-23 线上 500 教训）**：`topic_key` 列只在 `exam_plan_courses` / `exam_course_results` / `knowledge_point_records` / `courses` / `topics` 上，**`exam_plans` 没有**（它只有 id/parent_id/child_id/title/creator/kind/freq/scope_json/origin/recurrence_id/start_at/due_at/status/attempt_id/score/result/done_at/retake/task_type/count_in_rate/points/active/created_at/updated_at）；`speech_assessments` 也没有。写 SQL 时按表核对列名——0.5.6 的 `GET /exam/attempts/:childId` 就是误 select 了 `exam_plans.topic_key` 导致 500（修复见 ISSUE-135 §11.5；路由 handler 的 SQL 现已由 `test/issue135-exam-routes.test.ts` 覆盖）。
> ⚠️ **`exam_schedules` 排期表已取消（2026-09-14）**：原「排期配置 → 展开成场次」两层机制废除，固定档改配置项 + 每日生成、自定义直写计划；`db.ts` 里已 `DROP TABLE`。历史文档中「排期/排期配置」字样均按本条理解。

- **排考核（直接写 `exam_plans`）**：家长 agent 通过 `parent_exam_plan_create` / `parent_exam_plan_list` / `parent_exam_plan_cancel` 三个工具（§5.4）创建/查看/取消自定义考核计划（写孩子库 `exam_plans`，`kind='custom'`，`scope = {topics:[], courses:[精确课程名], note, methodSpec?}`；`methodSpec` 可选，用于本次覆盖考核方法，见 §6.4）。固定档（daily/weekly）不需要 agent——它是**配置项**，由 worker 每天检查配置生成当天考核计划（`ensureTodayExamPlans`），GET 考核计划列表时也会幂等补跑。
  - **档位限制**：固定档只剩 `daily` / `weekly`——`monthly` / `halfyear` / `yearly` 已于 2026-09-09 下线（GET 配置时返回 400 并提示改自定义档）。
  - **自定义档必须给精确课程名**：`scope.courses` 为空直接 400；2026-09-09 起**废弃了「规则文本 → 选课 LLM」两段式**（ISSUE-054），课程范围由家长 agent 在对话中解析确定。
  - **「本次考核方法覆盖」现状**：**读取侧已实现**——`server/src/assess-selection.ts` 的 `attachStructuredQuestions(db, childId, courses, override)` 支持计划级 `scope.methodSpec = { require:{知识点uuid或名:题数}, exclude:[...], recitePass:90 }`，优先于主题级方法；**主题级**可通过 `POST /api/v1/assess/method-spec` 写 `topics.method_spec`（按 `perChild[childId]` 存，含 `require/exclude/rules.recitePass`）。**写入入口已补（2026-09-14）**：`parent_exam_plan_create` 支持可选 `methodSpec` 参数，写入 `exam_plans.scope_json`，开考时经 `GET /exam/config` 传给 `attachStructuredQuestions` 生效。
- **出题 / 判分（内存会话，不落盘）**：服务端 `createExamSession` 用 **内存会话**（`SessionManager.inMemory()`，不落盘、不注入项目 prompt、`tools:[]`），纯 LLM 文本。**prompt 常量与组装函数都在 `server/src/agent/exam-engine.ts`**：
  - **出题（2026-09-14 定案后：计划即契约，无结构化/非结构化之分）**：**考核计划生成时即完整约定出题参数**——`exam_plans.scope_json.courses = [{title, kps:[{name,count}]}]`（考哪些课程、每课考哪些知识点、各几题；由 `buildPlanSpecEntries` 在工具/面板/worker 生成计划时展开写入，默认按主题 method_spec 过滤、计划级 methodSpec 可覆盖；课程没有挂知识点/题库题 → **拒绝创建计划**）。出题环节 `GET /exam/config` 只按约定用 `attachPlanQuestions` 从题库抽题（speech 行为→rq 背诵题带 refText；generic→q 带 scoringText/options），**不再走 LLM 出题**（`/exam/agent/generate` 出题链路已无调用方；判分 `/exam/agent/grade` 仍用 LLM）。旧格式 scope（字符串课程名 + methodSpec）在 config 路由现场懒迁移展开。worker `ensureTodayExamPlans` 生成固定计划时同样展开约定写入 scope（无内容课程跳过并记日志，全无内容则不生成计划）。
  - **关键约束**：**结构化课程**（题库已挂题，即 `course_knowledge_questions` 有记录）**不进 LLM 出题**，由 `attachStructuredQuestions` 直接按知识点从题库抽题（见下）；**只有非结构化课程**（无挂题）才走上面的 LLM 出题。
  - **判分（两套名字，别混）**：
    - `SCORING_SYSTEM_PROMPT`（`exam-engine.ts`）= 判分**会话的系统提示**；`buildScorePrompt(scoringPrompt, attempt, i)`（`exam-engine.ts`）= **逐题** mini prompt（基础口径 + 单题题目 + 孩子 ASR 回答）；逐题**并发上限 3**。
    - `SCORING_PROMPT`（含 `{{TODAY}}` 占位）+ `buildScoringPrompt()`（**`routes/exam.ts` 定义**）= 下发给客户端的判分口径文本；由 `routes/exam-agent.ts` 下发，**不接受客户端传入**（唯一真源，注入服务端当天日期）。
- **结构化直出细节（`assess-selection.ts`）**：按 `topics.method_spec` 的 `perChild[childId] ?? default` 取 `require / exclude / rules.recitePass`；`exclude` 过滤知识点、`require` 非空则只考命中项、每知识点池内**随机抽 ≤require 道**（缺题跳过，**不 LLM 临时命题**）；speech 行为题（`behavior` 以 `speech` 开头）**排最前**并下发 `refText=题库 answer`、`questionType='cn_recitation'`、`recitePass`（默认 90，答题端不显示原文）；选择题下发 `options` + `correctKey`/`answerText` 供规则判分；`qid` 跨课连续编号（`rqN` 背诵 / `qN` 文字题）。
- **数据获取**：出题/判分前由 `fetchCoursesWithKnowledgePoints`（`routes/exam.ts` 导出，`exam-agent.ts` 复用）读家长库知识点详情 / 主题考核方法 / 背诵语料，非客户端拼装。
- **数据生产及处理**：出题 JSON 写审计 `exam-audit/{childId}/{YYYYMMDD}.jsonl`（select/generate/score 三类事件；prompt 原文仅在 `EXAM_AUDIT_PROMPTS=1` 时落盘）；判分产出 `perQuestion{pointGot,correct,aiComment}` + `overall`；孩子端 `ExamView.tsx` → `examSubmit` → `submitExamAttempt` → `POST /exam/attempts` 经 `persistExamResult()` 直写**孩子库三层 + 评测存档**（`exam_plan_courses` / `exam_course_results` / `knowledge_point_records` / `speech_assessments`），并置考核计划 `done`；错题（未满分）同步进 `mistake_book`。

### 6.2 题型与评测（**发音评测无 agent**）

三种题型及其判分方式（与说明书 §4.8 的"答题方式/判分"表一致）：

| 题型 | 下发字段（`assess-selection.ts` / 出题链） | 判分 | 是否经 LLM |
|---|---|---|---|
| **背诵 / 朗读** | `behavior` 以 `speech` 开头 → `assessMethod='speech'`、`questionType='cn_recitation'`、`refText=<题库 answer 或背诵语料>`、`recitePass`（默认 90，主题/排期可覆盖）；**答题端不显示原文** | 录音上传 → **服务端发音评测引擎**（`server/src/assessment/`，腾讯智聆 / 阿里声希双 provider，凭证 AES-256-GCM 存 `assessment_config`）→ 总分 ≥ `recitePass` 才算通过 | ❌ 不经 LLM |
| **选择题** | 题库带 `options` → 下发 `options` + `correctKey` + `answerText` | `judgeChoice`（`agent/exam-engine.ts`）**本地规则判分优先**（孩子说"选B"或念出正确项即满分），无需 LLM | ❌（规则） |
| **问答 / 口述** | 文字题下发 `scoringText`（由题库 `answer` + `scoring` 压成"参考答案 / 评分维度 / 特殊情况"文本，供判分锚定，不作渲染） | LLM 逐题判分（`buildScorePrompt` + `SCORING_SYSTEM_PROMPT`，并发上限 3） | ✅ |

- **掌握度口径（与说明书 §3.5.3 一致）**：孩子库视图 `course_progress` 提供 `lastExamRate` = **最近一次已完成考核的得分率**、`lastExamAt` = 最近考核时间、`lastLearnedAt` = 最近学习时间。**2026-09-23 ISSUE-135 P0-a 改数据源**：三个聚合全部改读 `exam_course_results`（单表直读，不再按逐题明细 GROUP BY，也不再跨库读主库 attempts）。另新增课程级掌握叙述四列（`mastery_level` / `mastery_desc` / `teaching_advice` / `mastery_updated_at`），由每日分析任务（P4）写入；**课程详情页仍不展示掌握度与逐题记录**，统一在「考核记录」页看。

## 7. 积分奖励体系（§3.6）

### 7.1 实现过程（**无 agent 参与**，服务端 worker 纯规则计算）
- **每日结算**：`scheduler.ts` 的 `runStatTick` 遍历所有家长/孩子 → `plan-domain.ts` 的 `runPlanStat` → 四个纯确定性步骤：`applySignals`（读计划三表 + `daily_entries` 判定 done/missed）、`applyExamAttempts`（**单库兜底**：给有明细的已完成考核补齐 `exam_course_results`）、`expireAndCarry`（到期复制新行）、`settleRewards`（读 `reward_configs` → 算完成率/得分率 → `matchTier` 评档 → 幂等写 `reward_daily_stats` → `points_ledger` → 重算 `points_balance`）。**全程 SQL + 数学规则，无 LLM**。（考核得分率 = 优先 `exam_course_results`，缺行回退 `exam_plan_courses`，两级都在同一孩子库文件内。）
- **分档**：默认待办 4 档、考核 4 档，家长可改（`reward_configs.todo_tiers_json`/`exam_tiers_json`）。门控：加分项解锁需必须完成项目标率达标。
- **兑换（缺口）**：`redemption_items`/`redemption_requests` 闭环未完整落地（见 §17）。

### 7.2 数据流转
```
worker.runStatTick → 计划三表 + 孩子库考核结果（明细/概要/知识点）
   ├─ 待办完成率 = 已完成 / (count_in_rate=1 且未取消)
   └─ 考核得分率 = Σ得分 / Σ满分
→ reward_daily_stats → points_ledger(幂等) → points_balance
兑换: redemption_requests(pending→approved→fulfilled) → 扣 points_balance
```

### 7.3 数据结构（孩子库 `kb/<id>.sqlite`）
```sql
reward_configs( child_id TEXT PK, todo_tiers_json TEXT, exam_tiers_json TEXT,
   todo_gate_parent_min_rate REAL DEFAULT 1.0, exam_gate_parent_min_score REAL DEFAULT 0.9,
   child_no_deduct INT DEFAULT 1, optional_points INT DEFAULT 5, updated TEXT );
reward_daily_stats( child_id, date, source, owner,
   required_total INT, required_done INT, optional_done INT, missed_count INT,
   cancelled_count INT, rate REAL, tier TEXT, gate_ok INT, points_awarded INT,
   settled_at, updated, PRIMARY KEY(child_id,date,source,owner) );
points_ledger( id TEXT PK, child_id, ts, biz_date, type, amount INT,
   balance_after INT, reason_code, reason TEXT, rate REAL, meta_json TEXT,
   source_table, source_id, operator DEFAULT 'system', created_at );
points_balance( child_id TEXT PK, balance INT, updated TEXT );
redemption_items( id TEXT PK, child_id, name, cost INT, kind DEFAULT 'inapp',
   payload_json TEXT, enabled INT, updated );
redemption_requests( id TEXT PK, child_id, item_id, custom_desc, cost INT,
   status DEFAULT 'pending', parent_id, fulfilled_at, created_at );
```

### 7.4 孩子端"我的积分"（**无 agent 参与**）
- `TodoModal.tsx` 的"我的积分"标签页经 `window.api.todoGet`/`todoStatsList`/`rewardGet` 直接读取余额+流水+门控，**不经任何 agent 会话，无积分相关 agent 工具**。积分由结算 worker 写入，孩子侧只读展示。

### 7.5 工具说明（数据库读写）

## 9. 每日记录与对话回顾（§3.8）

### 9.1 Agent 操作（recording worker ephemeral agent 会话）
- **会话与 prompt**：worker 唯一注册任务 `recordingTask`。`runRecordingSummary`：先取当天对话文本 → `createWorkerEphemeralSession`（来自 `@pi/agent-core`，模型 `pickWorkerModel`）→ 系统提示 `RECORDING_SYSTEM_PROMPT`（`packages/agent-core/src/prompts/recording-prompt.ts`）+ 业务 `RECORDING_PROMPT` → 工具 `["kb_query","kb_insert","kb_update"]` + `createWorkerKbTools` → `session.prompt` → 写入孩子库。
- **处理逻辑**：以当天会话 + 计划三表为证据，由 agent 抽取总结，批量 `kb_insert/kb_update`。
- **数据获取**：当天会话文本 + 计划三表 + 已有 daily/生活计划（`buildProvidedContextLite`）。
- **数据生产及处理**：写 `daily_entries`（date/block/title/raw/tags，可附 `plan_id`/`plan_outcome`）与孩子库进度/生活事件。

#### 9.1.1 当天对话如何获取（`readServerDailyConversation`）
recording 取「当天对话」是**服务端直接从磁盘会话文件读取并合并**，不经过任何家长/孩子端接口，核心步骤：

1. **确定日期窗口**：入参 `date`（YYYY-MM-DD）→ 转为当天 00:00 起、24 小时止的时间区间 `[start, end)`；只统计落在该窗口内的消息。

2. **唯一来源目录**：`data/agent-sessions/<parentId>/<childId>-<slot>/`（9/12 迁移后客户端不再同步会话，所有孩子对话真实落盘于此，`slot = main / scene / course-*`）。扫描 `<agentRoot>` 下以 `<childId>-` 开头的子目录（每个 slot 一个目录）。

3. **递归收集 `.jsonl` 文件**：对该目录树递归扫描，取出所有 `.jsonl` 会话日志文件。

4. **逐行过滤消息**：对每个 jsonl 逐行解析 JSON，仅保留：
   - `type === "message"` 且带 `message` 体的行；
   - `timestamp` 落在 `[start, end)` 日期窗口内；
   - `role ∈ {user, assistant}`（忽略 system / tool 等）。
   并提取其中的 `text` 文本分段。

5. **排序与格式化**：按时间戳升序排序，拼成纯文本——`孩子: <text>`（user）/ `饺子: <text>`（assistant），逐条以空行分隔返回。

> 当天该目录树没有命中窗口内的消息时，返回**空串**，recording 据此直接 `skip`（不写 daily、不计跑）。同函数也被 agent 的 `summarize_conversation` 工具复用，保证「定时录制」与「按需回顾」走同一套对话读取逻辑。

### 9.2 对话回顾（**无 agent 参与**）

家长「对话回顾」页读取的逐字稿来自主库 `server.sqlite` 的 `session_messages` 表（主键 `child_id/file/line_index`）。该表**不是**由 agent 写入，而是服务端回看索引 `indexAgentSessionsIntoDb`（`db/sessions.ts`）维护，机制如下：

1. **扫描来源**：`data/agent-sessions/<parentId>/<childId>-<slot>/*.jsonl`——与 §9.1.1 同源，是 9/12 迁移后孩子对话的唯一落盘真源（旧架构的客户端 `POST /sessions/:childId/sync` 同步通道已彻底移除，不再存在）。
2. **游标去重**：以 `session_files` 表（主键 `child_id/file`）记录每个 jsonl 文件已索引到的 `line_count`；每次只处理游标之后的**新增行**，避免重复索引。
3. **逐行解析**：复用 `indexMessageLine`——只收 `type=message` 且 `role ∈ {user, assistant}` 的行（忽略 `system`/`tool`），提取 `text` 与 `tool_calls`，按 `timestamp` 折算 `ts` 与按本地时区的 `date`；空文本且无工具调用的行跳过。
4. **幂等落库**：`INSERT OR REPLACE INTO session_messages`（主键冲突即覆盖，重复索引安全）。

**触发时机**：家长端每次请求回顾时，路由 `GET /sessions/:childId/dates` 与 `GET /sessions/:childId?date=YYYY-MM-DD` 会**先调用 `indexAgentSessionsIntoDb`** 把最新会话增量写入 `session_messages`，再查表返回——即「读时索引」，保证回顾页实时反映服务端落盘的对话。

> 与 §9.1 的区别：recording（每日记录）读的是 `agent-sessions/*.jsonl` 原始文件（`readServerDailyConversation`），**不经过** `session_messages`；而「对话回顾」读的是索引后的 `session_messages` 表。两条路径同源、互不依赖。

家长端按日期/分类/标签/标题筛选逐字稿；仅「逐字稿导出端点」一项待补（见 §17 #9），**对话回顾本身已闭环**。

### 9.3 数据结构
```sql
-- 孩子库
daily_entries( date TEXT, block TEXT, title TEXT, raw TEXT, tags TEXT DEFAULT '',
   plan_id TEXT, plan_outcome TEXT, PRIMARY KEY(date,block,title) );
-- 全局库
session_messages( child_id, file, line_index, ts INT, date TEXT, role,
   text TEXT, tool_calls TEXT, PRIMARY KEY(child_id,file,line_index) );
session_files( child_id, file, synced_bytes, line_count, updated,
   PRIMARY KEY(child_id,file) );
```

每日记录写入全部在**孩子库 `kb/<id>.sqlite`**，由 recording worker 的 ephemeral agent 会话经工具落库：

| 工具 | 库 | 表 | 读取字段 | 写入字段 | 挂载情况 |

### 9.5 Token 用量统计（ISSUE-129，2026-09-21）

家长端「Token 用量」面板（Dashboard `tokens` 视图，`TokenStatsPanel`）展示**按日期 × 渠道 × 会话**的 token 消耗。

- **口径（用户拍板）**：**模型返回字段原样直传**——每条 assistant 消息的 `usage`（input / cacheRead / cacheWrite / output / reasoning / totalTokens / cost）逐条入库并带模型名；不做本地 system prompt / 工具 token 归因估算，不对账 input 与 cacheRead 的包含关系；token-plan 包月 cost=0（前端显示「-」，主显 token）。
- **数据来源**：`data/agent-sessions/<pid>/<slot>/**/*.jsonl` 中每条 assistant 消息自带的 `usage`（pi-ai Usage）。扫描器 `scanTokenUsageIntoDb`（`db/token-usage.ts`）按文件游标（`token_usage_files` 表）增量解析，`INSERT OR REPLACE`（主键 `parent_id/session_file/entry_id`）幂等，**可回填全部历史**。
- **scope 归属**：slot=`parent*` → `parent`（含 家长助手/资料助手 parent-content；~~数据助手 parent-data~~ 已退场）；`<childId>-main` → `child`；`-scene` → `scene`；`-course-*` → `course`（child_id 按家长 children 表归属解析，未知 slot 归 child/空 child_id 兜底）。
- **已知边界**：考核出题/判分、recording 等 `SessionManager.inMemory()` ephemeral 会话**不落盘、扫不到**（后续如需可挂事件钩子，见 ISSUE-129）。
- **触发时机**：读时扫描——三个查询路由在返回前先跑增量扫描，刚发生的轮次即时可见。
- **API**（家长 JWT）：
  - `GET /api/v1/token-usage/days?from=&to=&scope=` → 按日期×渠道聚合（`{days:[{date,scope,child_id,rounds,input,cache_read,cache_write,output,reasoning,total_tokens,cost}]}`）
  - `GET /api/v1/token-usage/sessions?date=&scope=` → 某天按会话聚合（含 `models`（热切换逗号串）、`first_ts/last_ts`）
  - `GET /api/v1/token-usage/dates` → 有数据的日期列表
- **客户端链路**：Electron `preload.tokenUsageDays/tokenUsageSessions` → IPC `tokenUsage:days|sessions` → `serverFetch`；Web shim 同名方法（`web/src/shim/domains/sessions.ts`）走 `http()`。渲染层 `TokenStatsPanel` 两级视图：日期分组头（当日合计）→ 渠道行；点某天展开会话明细（会话短 ID/模型/时段/各字段）。
- **旧实现清理**：客户端 `electron/lib/token-stats.ts`（ISSUE-010，agent 上移后写入链路已断）连同 `token:summary`/`token:log` IPC 与 `getTokenSummary/getTokenList` preload 方法一并删除。

## 11. 英语场景课（§4.4）

### 11.1 Agent 操作（孩子 `scene` 会话）

#### 11.1.1 场景课学习后的 daily 写入（由 recording worker 完成，非 scene 会话本身）
**scene 会话不写库**：§11.1 已强调，scene 会话工具收窄为 `display_content + scene_command + get_date`，**不挂载任何 kb 工具**，演出全程不产生 daily 记录。因此「场景课学完 → 写 daily」不是由 scene 会话直接完成的，而是走**统一的 recording 定时任务**（与所有对话型学习一致）：

1. **会话落盘**：场景课对话持久化在 `data/agent-sessions/<pid>/<cid>-scene/*.jsonl`（slot=scene），与其它孩子会话同源（9/12 迁移后客户端不再同步，无 `data/sessions/<pid>/<cid>/` 镜像）。
2. **recording 读取**：`recording` worker 到点触发 `runRecordingSummary` → `readServerDailyConversation` 直接读「scene 会话」当天对话文本（见 §9.1.1，来源仅 agent-sessions）。
3. **recording LLM 抽学习总结**：ephemeral 会话按 `RECORDING_PROMPT` §3「提取学习总结 → 写 daily【学习】区块」，把场景课对话提炼成 `daily_entries` 行：`block='学习'`、`title=<courses 表中精确课程名>`、`content='### 课程名 + 字段行'`（标题须精确匹配 courses 表，否则 `kb.daily_entries.insertMany` 校验报错）；并 `kb_update` 把该课 `courses.status→✅`、`last_review=当天`、`review_count+1`。
4. **stat 回写计划**：随后 `stat`/plan-domain 的 `applySignals` 读 `daily_entries WHERE block='学习' AND title=课程名`，把落在计划窗口内的 `study_plans` 行置 `done`，并把 `plan_id/plan_outcome='done'` 回填到这条 daily 学习记录（见 §8 计划域判定）。

> 换言之：场景课的学习记录与「普通课程对话」走**同一套 recording 写 daily 机制**——区别仅在对话来源是 scene 会话而非 main/course 会话；scene 会话本身只负责演出与互动，不落库。

### 11.2 当前缺陷（英语场景课不可用，ISSUE-090）
`electron/lib/server-agent-client.ts` 的 `translateAgentEvent` **没有 `page_cmd` 分支**，default 直接 `return null`；执行器 `handlePageExec`/`MaterialsPanel.scene`/`appCmd` 只认旧 `pi:page:exec` 通道（服务端模式不被触发）→ **scene_command 的 move/act/show/highlight/update 被丢弃，仅 `say` 台词经 `extractSceneLines` 从 toolCall 提取经 `scene:reply` 送达字幕**。即"台词有、动作无"，且 `page-result` 回执链随之失效。修复方向见 **ISSUE-090**。末段发音测评走服务端引擎（`/assessment/assess`），不经 scene 会话。

## 12. 定时任务（§5.4）

### 12.1 Agent 参与情况（部分）
- **每日记录总结 = recording**：经 ephemeral agent 会话（见 §9），**有 agent**。
- **自动新建会话**：配置链路完整——`buildEffectiveChildConfig` 解析 `auto_new_session`（`task-runs.ts`）→ `resolveChildConfig` 并入调度（`scheduler.ts`）；但 `registerTask` **仅有 recordingTask**，**无 `auto_new_session` 的 WorkerTask 实现** → worker 永不按 `hour/minute` 开新会话（**缺口**）。
- **到点未运行补执行**：`runWorkerCatchUp`（`scheduler.ts`）重试未跑时间点，仅调已注册任务，纯重试、**无 agent**。

## 13. 跨端音频 / 评测（§3.5.5、§4.5、§5.3）

### 13.1 实现过程（**无 agent 参与**）
- **ASR（语音转写）**：客户端本地（千问 token-plan 等），不走云端业务服务。
- **发音评测（服务端计算，2026-09-13 由 Electron 主进程迁移至服务端）**：客户端把录音经 `/files/upload` 上传拿到 `fileId` 后，调用 `POST /api/v1/assessment/assess`（携带 `audioFileId`）→ 服务端从 `files` 表取回音频字节、用系统 `ffmpeg` 转 16k 单声道 wav、按服务端 `assessment_config` 配置分发到**双 provider**：腾讯智聆（`tencent-soe`，WebSocket 流式）、阿里声希（`aliyun-ssecp`，直连 `api.cloud.ssapi.cn`）→ 维度分经 `toSpeechAssessment` 映射后回传。凭证（腾讯 appId/secretId/secretKey、阿里 appKey/appSecret）统一收归服务端 `assessment_config` 表（AES-256-GCM 加密），Electron 本地 `assessment-config.json` 已废弃。
- **口语评测落库（2026-09-13 Plan A 接上；2026-09-23 ISSUE-135 D13 搬到孩子库）**：`POST /exam/attempts` 提交时，服务端遍历 `perQuestion`，对带 `speech` 结果的口语题写入**孩子库** `speech_assessments`（补 `plan_id` / `course_uuid` / `question_id`，与明细按 `(plan_id,course_uuid,question_id)` 关联；同一题多行 = 多次评测）；录音引用同时落在明细行 `audio_file_id`（「听原音」走它）。原主库表（含 `exam_attempt_id`）已 DROP。详见 §13.3。
