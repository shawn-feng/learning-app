## 0. 先还欠账：`parent_kb_bind` 到底是什么

**一句话**：把「某几条已经发布的口径」**挂到某一节课上**。

**为什么需要它**：孩子上「第一课 夏商周」时，如果每次都要现场去库里查，就可能**查不到 / 查歪 / 忘了查**。挂上以后，孩子一进这节课的会话，这几条口径**就已经在它的系统提示里了**——不用查、不会漏。

**它引起的连锁变化只有一处**：`server/src/agent/session-registry.ts:410-417` 那个 `lines` 数组多一行。

```
        孩子点开「第一课 夏商周」
                 ↓
  session-registry.ts:382  courseContextBlock()   ← 按课程名读课程上下文
                 ↓
      :403  读家长库 courses（✅ 已有）
      🆕    读 kb_entry_links 里这节课绑了哪些条目
                 ↓
      :410  拼成几行文本（✅ 已有这个数组）
      🆕    多拼一行「- 本课知识条目（回答以这些为准）：1. … 2. …」
                 ↓
  prompt.ts:59  `## 本次课程` 段塞进 system prompt（✅ 已有）
                 ↓
        孩子看到的会话里，这几条口径已经在手上
```

**它写哪张表**：`kb_entry_links`（🆕），三个字段：`entry_id`（哪条口径）+ `topic`（哪个主题）+ `course`（哪节课）。

**它为什么不是 P1**：讨论稿 §11 已定 P1 不含课程绑定——因为**聊天侧（线路二）不依赖它**，先把"孩子随时问、agent 有据可答"跑通，再打通"上课自动带"（P2）。所以本文把它排在 P2。

## 2. 五个动作，逐个走查（例子：秦汉以前的历史）

### 动作 1 · 家长把资料传上去 —— ✅ 现在就有，只补一个扩展名

| | |
|---|---|
| **大白话** | 家长在「文件区」进到 `preqin` 主题，选文件上传。视频/音频会自动进 `media/` 子目录 |
| **落盘位置** | `workspaces/<parentId>/materials/preqin/…`（✅ `server/src/db/materials.ts:47` 的 `materialsRoot()`） |
| **要改的地方** | 🆕 **上传白名单缺 `.txt`**：`web/src/shim/domains/parent.ts:573` 的 `accept` 只列了 16 种扩展名，`.txt` 不在里面 → 家长那个 `先秦史话.txt` **在选择框里是灰的**。P1 把 `.txt` 加进去（一行改动） |

> **注意区分两个地方**（这一点很容易搞混）：
> - **「文件区」上传** → 进 `materials/`，是**资料真源**，能被 `parent_kb_save` 挂到条目上；
> - **聊天框里的附件** → 进 `files/` 通道（`server/src/agent/parent-tools.ts:1239` 的 `parent_read_upload`），**不是资料库**，而且 pdf/word **明确读不了**（`parent-tools.ts:1276`）。
> ⇒ 家长"把 PDF 拖进聊天框"这个最自然的动作，**目前既进不了资料库、也读不出内容**。这是 P3 入库管道要解决的头号摩擦。

### 动作 2 · 家长说"以后照这个口径" —— 🆕 新增工具 `parent_kb_save`

家长原话：
> 「preqin 这个主题我放了 4 份东西。以后小满问先秦的事就按这个口径。甲骨文那个跟她说：『我们能读懂商朝人的字，靠的就是甲骨文』。夏朝那个，别让她以为夏朝一定是有的，也别说不存在。」

**agent 内部做四件事**：

| 步 | 调用 | 说明 |
|---|---|---|
| 1 | `parent_list_materials({ topic: "preqin" })` | ✅ 已有（`server/src/agent/parent-tools.ts:192`）。**先列再问**是既有纪律 |
| 2 | 自己判断归属 | 哪份文件配哪条口径（这是模型的活，不需要工具） |
| 3 | 🆕 `parent_kb_save({ entries: [...], assets: [...] })` | 一次落多条目 + 多资产 |
| 4 | 回话 | 「我整理了 5 条草稿，**都没发布给孩子**，你确认哪几条能给她看？」 |

**这一步写进表里的字段（以"甲骨文"这条为例）**：

| 表 | 字段 | 值 | 为什么是这个值 |
|---|---|---|---|
| `kb_entries` | `title` | `甲骨文` | 条目名，也是精确命中的第一顺位 |
| `kb_entries` | `aliases` | `甲骨文,卜辞,商朝文字` | 孩子换一种说法问也能命中 |
| `kb_entries` | **`summary`** | 商朝人把占卜结果刻在龟甲和兽骨上…（家长那句话 + agent 从文件补的客观事实） | ★**这是"回答依据"，权威层** |
| `kb_entries` | `body` | 空（P1 留空；P3 由提取管道填） | P1 不注入 `body`，避免上下文灌爆 |
| `kb_entries` | `kind` | `card` | `doc`/`media`/`card`/`qa` 四选一 |
| `kb_entries` | `usage` | `想在屏幕上给她看拓片时展示；讲到"为什么刻在骨头上"时用` | ★"什么时候用"比"内容摘要"更值钱 |
| `kb_entries` | **`visibility`** | **`parent`** | ★根定案 3：默认只家长可见 |
| `kb_entries` | `share` | `all` | 多孩子时改成 `<childId>` |
| `kb_entries` | **`status`** | **`draft`** | ★根定案 3：上传/提取产物**恒为草稿** |
| `kb_entries` | `origin` | `manual` | `manual`/`upload`/`extracted`/`generated` |
| `kb_entry_assets` | `path` | `preqin/media/甲骨文-卜辞拓片.jpg` | 与 ✅ `courses.html_path` **同语义**（材料真源相对路径） |
| `kb_entry_assets` | `role` | `image` | `html`/`pdf`/`video`/`audio`/`image`/`file` |

> **为什么 `summary` 和 `body` 分开**：`summary` 是**回答的依据**（几十到几百字，进检索结果）；`body` 是**可选长文**（P3 提取产物，几百 KB 都可能有）。P1 的 `kb_lookup` **只返回 `summary`**——这样"只按库里的说"才真的是"按一段家长认过的话说"，而不是按一篇没审过的机器提取文本说。

### 动作 3 · 家长确认"前四条可以" —— 🆕 新增工具 `parent_kb_publish`

家长原话：
> 「前四条都可以给她看。教师用书那个先别放。」

| 步 | 调用 | 效果 |
|---|---|---|
| 1 | 🆕 `parent_kb_list({ status: "draft" })` | 列出草稿（家长刚才已经看到清单，这里是 agent 自己核对 id） |
| 2 | 🆕 `parent_kb_publish({ entry_ids: [4 个 id], visibility: "child" })` | 4 条变成 `status='published'` + `visibility='child'` |
| 3 | — | 「教师用书摘录」那条**什么都不做**，继续 `draft` + `parent` |

**这一道门是硬机制，不是话术**：`kb_lookup` 的 SQL `WHERE` 里写死 `status='published' AND visibility='child'`（见 §4.4），草稿和 parent-only 条目**在 SQL 层就取不出来**——不依赖模型自觉，也不依赖提示词约束。

### 动作 4 · 孩子在聊天里问 —— 🆕 新增工具 `kb_lookup`

| | |
|---|---|
| **大白话** | 孩子问「甲骨文是什么」，agent 先拿这句话去库里查，查到就照着说，查不到就分情况老实交代 |
| **工具** | 🆕 `kb_lookup({ query: "甲骨文", high_risk: false })` |
| **谁调用** | 只有**孩子 agent**。家长侧没有这把工具（家长要看条目用 `parent_kb_list`） |
| **数据来源** | 只读 `parents/<parentId>/parent.sqlite` 的 `kb_entries` + `kb_entry_assets` |

**工具返回什么**（设计形态，`summary` 全文 + 出处 + 可展示资产，**不含猜测**）：

```
命中 1 条（标题精确）：
- 甲骨文 ｜ 出处：家长知识库 preqin ｜ 依据：家长口径（可直接引用）
  商朝人把占卜结果刻在龟甲和兽骨上，这就是甲骨文，是目前能看到最早的成体系汉字。
  1899 年发现于河南安阳小屯村（商朝晚期都城殷墟）。能读懂商朝人的字，靠的就是它。
  用法：想在屏幕上给她看拓片时展示。
  可展示：preqin/media/甲骨文-卜辞拓片.jpg（图片）
  注意：以上是这条口径的全部内容——超出这些的具体数字、人名、引文一律不要补。
```

最后那句「注意」是**刻意的**：`kb_lookup` 的返回值本身就是"引用纪律"的载体。只靠提示词说"别编"，实测压不住；把"这条口径到此为止"写进工具结果，模型才会照着边界走。

**查不到时返回什么**（分两种）：

```
【普通】库里没有命中「古埃及金字塔怎么建的」。
（这是一般常识类问题，可以按你的一般了解回答，但要先告诉孩子"这是我自己的一般了解"。）

【高风险】库里没有命中「人是女娲造的吗」。
⚠️ 本话题已判定为「需要家长口径」（生命起源/神话），**不要给出结论**。
请告诉孩子你会先去问爸爸妈妈，本次提问已记入家长的待补充清单（kb_gaps）。
```

**高风险怎么判定**：两层。
1. **模型自己传 `high_risk: true`**（孩子提示词里教它什么时候传）；
2. 🆕 **代码兜底关键词表**（服务端写死，出现在 `query` 里就强制按高风险处理）：
   `神 / 上帝 / 宗教 / 佛 / 菩萨 / 女娲 / 造人 / 死 / 去世 / 自杀 / 身体 / 亲嘴 / 结婚 / 生孩子 / 从哪来 / 钱 / 工资 / 离婚 / 吵架 / 打我 / 同学 / 欺负 / 好坏 / 好人坏人`
   > 关键词表**必然不全**，所以它是**兜底**不是主判据——主判据是模型 + 提示词。两层同时存在，是因为漏一次就是一次事故（宁可比对多记一条 `kb_gaps`，让家长自己划掉）。

3. 只绑 `visibility='child'` 的条目——否则等于绕过可见性门控。

## 3. 表结构（真实 DDL 草案）

**放哪**：`parents/<parentId>/parent.sqlite`。**怎么建表**：跟现有三张旁表一个模式——新建一个幂等的 `ensureKbEntriesSchema(db)`，在 `server/src/db/parent-lib.ts:63` 的 `ensureEmbeddingsSchema(db)` 后面加一行调用。**每个家长的库在下次打开时自动长出这几张表，不需要版本号、不需要迁移脚本。**

> 注意：现有 `topics` / `courses` 表**都没有 `parent_id` 列**（因为一个文件就是一个家长的库）。新表**照样不加**，保持一致。

```sql
-- 条目：回答的寻址单元，也是"家长口径"的载体
CREATE TABLE IF NOT EXISTS kb_entries (
  id          TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  aliases     TEXT NOT NULL DEFAULT '',      -- 逗号分隔，如 '甲骨文,卜辞,商朝文字'
  summary     TEXT NOT NULL DEFAULT '',      -- ★权威层：检索返回、回答依据
  body        TEXT NOT NULL DEFAULT '',      -- P1 留空；P3 由提取管道填，P1 不注入
  kind        TEXT NOT NULL DEFAULT 'card',  -- doc | media | card | qa
  tags        TEXT NOT NULL DEFAULT '',
  usage       TEXT NOT NULL DEFAULT '',      -- 什么时候给孩子看/讲、有什么要注意的
  visibility  TEXT NOT NULL DEFAULT 'parent',-- child | parent        ★默认 parent
  share       TEXT NOT NULL DEFAULT 'all',   -- all | <childId>
  status      TEXT NOT NULL DEFAULT 'draft', -- draft | published | archived  ★默认 draft
  origin      TEXT NOT NULL DEFAULT 'manual',-- manual | upload | extracted | generated
  created_at  TEXT NOT NULL DEFAULT '',
  updated_at  TEXT NOT NULL DEFAULT ''
);
-- 孩子侧检索走这条索引（等值三列 + share）
CREATE INDEX IF NOT EXISTS idx_kb_entries_lookup ON kb_entries(status, visibility, share);

-- 条目 ↔ 文件（一条可挂多份；path 语义同 ✅ courses.html_path）
CREATE TABLE IF NOT EXISTS kb_entry_assets (
  entry_id  TEXT NOT NULL,
  path      TEXT NOT NULL,                   -- 材料真源相对路径，如 preqin/media/甲骨文-卜辞拓片.jpg
  role      TEXT NOT NULL DEFAULT 'file',    -- html | pdf | video | audio | image | file
  seq       INTEGER NOT NULL DEFAULT 0,
  title     TEXT NOT NULL DEFAULT '',
  PRIMARY KEY (entry_id, path)
);

-- 条目 ↔ 课程（P2：线路一的寻址；补齐 ✅ courses.html_path 只能挂 1 份的缺口）
CREATE TABLE IF NOT EXISTS kb_entry_links (
  entry_id  TEXT NOT NULL,
  topic     TEXT NOT NULL,                   -- topic_key，如 preqin
  course    TEXT NOT NULL,                   -- 课程名，如 第一课 夏商周
  seq       INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (entry_id, topic, course)
);
CREATE INDEX IF NOT EXISTS idx_kb_links_course ON kb_entry_links(topic, course);

-- 缺口队列：孩子问了、库里没有
CREATE TABLE IF NOT EXISTS kb_gaps (
  id         TEXT PRIMARY KEY,
  child_id   TEXT NOT NULL,
  question   TEXT NOT NULL,
  hits_json  TEXT NOT NULL DEFAULT '[]',     -- 当时命中了什么（多半是 []），供家长判断
  high_risk  INTEGER NOT NULL DEFAULT 0,     -- 0/1（SQLite 无 bool）
  count      INTEGER NOT NULL DEFAULT 1,     -- 同一问题反复问 → 累加，不新增行
  asked_at   TEXT NOT NULL DEFAULT '',
  status     TEXT NOT NULL DEFAULT 'open',   -- open | resolved | ignored
  entry_id   TEXT NOT NULL DEFAULT ''        -- 家长补的条目 id（闭环后回填）
);
CREATE INDEX IF NOT EXISTS idx_kb_gaps_open ON kb_gaps(child_id, status, asked_at);
```

**P1 不建的**：`kb_entry_chunks`（文本化产物，P3 随提取管道一起建）。

**为什么这不算"又建镜像表"**（讨论稿 §4 已论证，这里给可核对的形式）：
`kb_entries` **不存"文件是否存在"**——`kb_entry_assets.path` 只是一个字符串，任何"文件在不在"的判断仍然走 ✅ `resolveMaterialFile()`（`server/src/db/materials.ts:160`，新根优先、旧根兜底）。`summary`/`usage` 这些字段**磁盘上本来就不存在**，是家长新写的，不是文件清单的副本。所以不变式是：**索引缺行 ≠ 文件不存在**。

## 4. 工具定义（真实代码草案）

### 4.1 家长侧三把（`server/src/agent/parent-kb-tools.ts`，🆕 新文件）

按 ✅ 现有模式：`parent-tools.ts` 导出 `createParentAgentTools(deps)` + `PARENT_AGENT_TOOL_NAMES`；新文件照抄这个形状。工具内部统一用 ✅ `defineTool`（`server/src/agent/tool-kit.ts:225`）和 ✅ `openParentLib`。

```ts
// server/src/agent/parent-kb-tools.ts（🆕 新文件，草案）
import { Type } from "typebox";
import { defineTool } from "./tool-kit.js";
import { openParentLib } from "../db/parent-lib.js";
import { saveKbEntries, listKbEntries, publishKbEntries, bindEntryToCourse } from "../db/kb-entries.js";

const ok = (text: string) => ({ content: [{ type: "text" as const, text }], details: {} });

export interface ParentKbToolDeps { dataDir: string; parentId: string; }

export function createParentKbTools(deps: ParentKbToolDeps) {
  // ── ① 落草稿 ──────────────────────────────────────────────
  const saveTool = defineTool({
    name: "parent_kb_save",                       // 🆕
    label: "记录一条家长口径（草稿）",
```

**`searchKbForChild` 的真实 SQL（安全过滤在这一层，不在提示词）**：

```sql
SELECT id, title, aliases, summary, usage, kind
FROM kb_entries
WHERE status = 'published'
  AND visibility = 'child'
  AND (share = 'all' OR share = ?)          -- ? = childId
```

然后**在 JS 里**做匹配（家族级只有 10²~10³ 条，全取出来匹配最稳，也避免在 SQL 里跟中文逗号分隔串较劲）：
① `title` 完全相同 → ② `aliases` 按 `,`/`，` 切分后任一项完全相同 → ③ `title` 包含 query 或 query 包含 `title` → ④ 取前 5 条。

> **`share = ?` 传 `childId`**，所以哥哥的条目妹妹查不到——这条也在 SQL 里。

## 9. 要你拍板的三件事

**① `display_content` 的媒体支持，要不要从 P2 提到 P1？**

现在 `server/src/agent/display-tool.ts:50` 一句 `/\.html?$/i` 把 jpg/mp3/mp4 全挡在外面。但后端 `/api/v1/materials/p/:token/*`（`server/src/routes/materials-doc.ts`）**已经支持任意 MIME + Range**——所以这是**纯前端白名单**问题，改动极小。

- **提到 P1**：秦汉这个例子里"给孩子看甲骨文拓片"当场就成立，产品体验完整；
- **留在 P2**：P1 只能说「我这里有这张图，等妈妈在的时候给你看」，孩子体感打折。

**我建议提到 P1 尾巴。**

**② `summary` 由谁写？**

讨论稿 §0.2 留的未决项。三个选项：
- (a) **只让家长说，agent 只做整理**（最准，但家长得多说几句）；
- (b) agent 从 `title` + 文件内容**拟草稿摘要**，家长改（省事，但家长可能不看就发布）；
- (c) 混合：**默认 (a)；只有当家长说"你看着写"时才走 (b)，且草稿必须标注「这是 AI 拟的，还没经你确认」**。

**我建议 (c)。** 因为 (b) 的风险正好是这个方案要防的：**没经家长确认的机器文本，一旦进了 `summary`，就成了"权威依据"**——比模型幻觉更危险，因为它有"家长知识库"的名义。

**③ 高风险关键词表放哪？**

放在 `child-kb-tools.ts` 里写死（简单），还是放到家长可编辑的技能/配置里（灵活，但家长可能删空）？

**我建议写死在代码里**，理由同讨论稿 §9 的口径：**门控类判断必须在代码里，不能靠配置或提示词**。家长要扩展只能通过"多写几条条目"，不能通过删关键词来放松。
