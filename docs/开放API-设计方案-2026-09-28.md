## 1. 背景与目标

让每个账号（家长）能生成**一个** API Key，第三方系统（第一个是 ESP32-S3 硬件）凭 Key 调用
learning-server 上的 agent，能力与 app 内聊天框**完全一致**：

- 传文字；传图片 / 文本文件 / 音频等附件；
- 读到 agent 的**思考过程**（thinking）与**工具调用**（tool calls）；
- 会话连续性、每日新建、跨端可见等行为与 app 内聊天框一致。

职责边界：本方案只覆盖 server 端（Fastify）与 app 端（Electron/Web）的改造；ESP32-S3 固件
如何录音、如何联网由硬件团队按第 8 节的契约自行实现。

## 3. 关键决策（含理由）

1. **API 会话 = 复用孩子的主会话**（不新开独立会话槽）。
   与 app"功能一样"的最直接实现：ESP32 发的消息和 app 聊天框在同一条会话里，app 端能实时看到
   硬件对话（stream-hub 多订阅者天然支持）；跨天新建、token 统计、历史回放全部免费复用。
   代价：同一孩子同一时刻只允许一轮（busy 409），app 与硬件互相挤占——这正是"同一上下文不交错"
   的既有红线，第三方按 409 退避重试即可。独立 `session=hardware` 槽明确**不做**（与 2026-09-25
   会话收敛决策一致；真有需求走 /reset 或未来再加）。
2. **同步聚合模式优先，流式模式其次**。ESP32-S3 内存小、解析 SSE 成本高；主力接口
   `POST /open/agent/chat` 复用 `runTurn`（微信桥/飞书同源）：响应是 **chunked NDJSON 快照流**——
   先推若干 `progress` 行（thinking/tools/text 累积快照，与飞书进度卡片同源同节流思路），最后一行
   `final` 终态。朴素客户端等连接关闭后取**最后一行**即普通同步 API；想看进度的客户端逐行读即可。
   SSE 流式作为第二形态（delta 级逐字 + Last-Event-ID 断线重放），协议与 app 完全相同。
3. **一键一账号**：`api_keys` 表对 `(parent_id) WHERE revoked_at IS NULL` 建部分唯一索引；
   "重新生成" = 吊销旧键 + 建新键；库里只存 sha256。
4. **附件走既有 files 通道 + 既有标记格式**：agent 侧解析（upload-ref / vision）零改动；
   API 收结构化 `attachments[]` 由路由组装标记，第三方不必知道标记语法。
5. **默认绑定孩子**：生成 Key 时在设置页选一个孩子作为默认对话对象；请求可用 `child_id` 覆盖
   （仍做归属校验）。ESP32 不用管 childId。
6. **安全基线**：LAN 明文 HTTP 可接受（201 是家庭内网），API Key 全程走 header；
   若未来暴露公网，必须在前面加 TLS（nginx 443），文档里写死这条红线。
   Key 比较用 `crypto.timingSafeEqual`；日志只打 prefix。

## 4. API 规格

统一前缀 `/api/v1`。两组路由：

- **管理组（家长 JWT 鉴权，app 设置页用）**：`/api/v1/apikeys`
- **开放组（API Key 鉴权，第三方用）**：`/api/v1/open/*`

### 4.1 Key 管理组

| 方法/路径 | 说明 |
|---|---|
| `GET /api/v1/apikeys` | 查询当前 Key（`{key: {prefix, child_id, label, created_at, last_used_at, request_count} \| null}`） |
| `POST /api/v1/apikeys` | 生成（已有有效 Key 时 409）。body: `{child_id?, label?}`。**响应一次性返回完整 Key**，此后只显示 prefix |
| `DELETE /api/v1/apikeys` | 吊销（第三方立即 401）；可再生成新键 |

Key 格式：`laxk_` + 32 字节随机 base64url（43 字符）。落库存 `sha256(key)`，展示用前 12 位 prefix。

### 4.2 开放组鉴权

两个 header 任选其一（ESP32 用哪个都行）：

```
Authorization: Bearer laxk_xxxx
X-API-Key: laxk_xxxx
```

无 Key / 吊销 → 401；child_id 不归属 → 403。

### 4.3 同步对话（ESP32-S3 主力接口）

```
POST /api/v1/open/agent/chat
{
  "text": "这道题怎么算？",
  "attachments": [
    { "kind": "image", "name": "math.jpg", "ref": "files/<id>" },
    { "kind": "audio", "name": "rec.wav",  "ref": "files/<id>" }
  ],
  "child_id": "可选，缺省用 Key 绑定的孩子",
  "caps": "mic",              // 可选，能力协商，语义同 app 的 stream?caps=
  "tts": true,                // 可选，开启则服务端合成回复音频随 final 行下发（edge-tts，免费零配置）
  "voice": "zh-CN-XiaoxiaoNeural", // 可选，TTS 音色 id；缺省按文本语种自动选（中文晓晓/英文 Sonia）
  "tts_rate": 48000,          // 可选，TTS 输出采样率——传入即输出 16bit 单声道 WAV（设备固定编解码配置直喂）；缺省 24kHz MP3
  "timeout_ms": 240000        // 可选，默认 240s
}
```

行为：组装 `text + 附件标记`（每个附件一行 `【附件图片：math.jpg|files/<id>】`，与
`src/lib/attachment-ref.ts` 的格式逐字一致）→ `submitChildPrompt(...)` → `runTurn` 聚合
（自 `routes/wechat.ts` 提为公共模块 `agent/turn-runner.ts`，飞书渠道已在复用）→ 应答。

**应答 = chunked NDJSON 快照流**（`Content-Type: application/x-ndjson`，同一连接先推进度、最后推终态）：

```
{"type":"progress","thinking":"先看题目条件…","tools":[{"name":"kb_lookup","done":false}],"text":""}
{"type":"progress","thinking":"…","tools":[{"name":"kb_lookup","done":true,"error":false}],"text":"这道题…"}
{"type":"final","ok":true,"reply":"最终文本","thinking":"完整思考","tools":[…],"duration_ms":8213}
```

- **progress 行 = 累积快照（不是增量）**，字段与飞书进度卡片完全同源（`runTurn` 的 `onProgress`
  回调，飞书拿同一份快照去更新消息卡片，节流 ~2.6s）。本路由服务端节流 ≥1s 一条；工具
  开始/结束、错误立即补发。设备只认最新一行：显示"思考中 / 正在查资料 / 作答中"。
- **final 行 = 终态**：成功含 reply/thinking/tools/duration_ms；接口超时
  `{"type":"final","ok":true,"timed_out":true,"reply":"部分回复"}`；一轮内出错
  `{"type":"final","ok":false,"error":"…"}`（含看门狗判挂死后 abort 的情况）。
  **tts 开启时**追加：`audio: {ref, url, mime:"audio/mpeg", size, voice}`（24kHz 单声道 MP3，
  经 `GET /open/files/:id` 下载）；TTS 失败不吞文本回复，`audio_error` 说明原因。
- **两种消费姿势都成立**（选 NDJSON 而非 SSE 的原因就在这）：
  1. 朴素客户端——等连接关闭后整体读 body，取最后一行就是终态，等价于普通同步 API；
  2. 进度客户端——逐行读，实时展示思考/工具状态（与飞书卡片同效果）。
- `409` busy / `429` 限流等提交期错误仍是普通 JSON（流未开始即拒绝）。

**长请求语义（即长连接，2026-09-30 重申）**：本接口是一次可能持续**数十秒到数分钟**的长 HTTP 请求——
服务端先订阅 stream-hub 再提交，**持有连接直到本轮结束才应答**（NDJSON 最后一行 final），不是"提交后
轮询"，也不是"秒回"。第三方发出后阻塞读响应，设备侧 HTTP 读超时必须 ≥ `timeout_ms` + 余量（下表第三行）；
HTTP 库的默认短超时会在服务端仍在处理时提前断流（实测：设备 10~15s 读超时 vs 单轮 15.4s → 断流）。

一轮可能持续数十秒到数分钟，超时防线三层，第三方最长等待有上界：

| 层 | 参数 | 行为 |
|---|---|---|
| 会话看门狗（服务端已有） | 无工具时静默 240s → 判挂死；单工具 30min 硬上限 | abort 本轮 → error 事件 → **等待中的请求立刻收到 final 行**，不存在"agent 挂了请求永远不回" |
| 接口超时（runTurn） | `timeout_ms`，默认 240s | 到点写入 final 行（部分回复 + `timed_out:true`）并关闭 |
| 设备侧 HTTP 超时（建议） | timeout_ms + 10~20s | 兜住网络黑洞；到点按本次调用失败处理 |

`timed_out:true` ≠ 本轮失败——可能是一个合法长工具仍在跑（网页生成实测中位 321s、最长 654s，
接口超时先到）。设备后续动作：`GET /open/agent/status` 查 `busy`，仍为 true 则继续周期查询
（**不要**重发消息，必 409），或 `POST /abort` 收拾重来。

### 4.4 语音消息（录音直发：ASR 转录 → 对话 → 可选 TTS）

```
POST /api/v1/open/agent/voice?child_id=可选&tts=true&timeout_ms=可选
                         &fmt=可选&sample_rate=可选&channels=可选&tts_rate=可选
X-API-Key: $KEY
Content-Type: audio/wav            # 裸流：body 即音频字节；multipart 亦可（file 字段 + 同名参数字段）
<音频二进制>
```

服务端流程：音频 → **ffmpeg 转 16k 单声道 wav**（**输入采样率随意**——转码统一到 16k，ASR 侧不看设备采样率）
→ **ASR 转录**（复用家长端语音配置，qwen/MiMo 多通道回退，兜底 key 读 auth 封套——ISSUE-165 基建）
→ 以转录文本发起一轮对话（与 app 内语音输入同语义）→ tts 开启时合成回复音频（`tts_rate` 同 4.3）。

**输入格式参数**（ESP32 采样率/编解码器约束的解法，2026-09-29 追加）：

| 参数 | 说明 |
|---|---|
| `fmt` | `wav`（缺省，自描述格式按内容探测）或 `pcm`（**裸 PCM** s16le 小端无文件头，嵌入式直传） |
| `sample_rate` | 录音采样率；`fmt=pcm` 必填（缺省报 400），自描述格式读文件头 |
| `channels` | 声道数，缺省 1 |

**设备端零重配置（推荐：全 16k，2026-09-30 定案）**：ESP32 的"录音 16k / 播放 48k 不能共存"约束 → 设备编解码器固定 **16k** 一档：录音 16k 裸 PCM 直传（`fmt=pcm&sample_rate=16000`），回复 `tts_rate=16000` 拉 16k WAV 直喂 I2S，**全程零重配置**，且上传体积只有 48k 的 1/3（32KB/s），实测 15.9s 录音端到端从 ~7.0s 降到 ≈5.3s；固件还能省掉 MP3 解码库（此前"全 48k"方案为备选：播放频响更宽但上传 3 倍体积）。ASR 侧零质量损失（服务端本来就统一转 16k）；TTS 侧 24k→16k 仅截 8kHz 以上高频，小喇叭播放不可闻。转码成本全部收在服务端。

- **与"上传的音频文件"的区分**（红线）：本端点的音频是**一句消息本身**，服务端对它做 ASR；
  给 agent 传"音频文件"仍走 `/open/files/upload` + `attachments(kind=audio)`，仅存档引用不转录。
- **ASR 阶段失败（流未开始）= 普通 JSON 错误**：`400` 音频缺失/过短/未启用语音输入/没有识别到语音/
  `fmt=pcm` 缺 sample_rate、`502` 语音服务全失败（含未装 ffmpeg）。对话阶段才进入 NDJSON 流（协议同 4.3）。
- final 行额外字段：`transcript`（ASR 文本）、`audio`/`audio_error`（语义同 4.3，含 `sample_rate`）。
- 原始录音经 files 通道存档（best effort），可用 `GET /open/files/:id` 回放。

### 4.5 流式对话（与 app 内聊天框同协议）

与 4.3 的分工：SSE 给 **delta 级**逐字事件（与 app 完全同协议）且支持 Last-Event-ID 断线重放；
4.3 的 progress 行是秒级**快照**。要逐字回放/弱网重连选 SSE，只求"知道在干嘛 + 拿最终答案"用 4.3。

- `POST /api/v1/open/agent/prompt` —— 提交一轮（body 同 4.3，立即返回 `{ok:true}`，增量走 SSE）
- `GET  /api/v1/open/agent/stream?caps=mic` —— SSE 事件流（Last-Event-ID 重放同 app）

SSE 事件（第三方可见的思考/工具过程就在这里）：

| event | data | 说明 |
|---|---|---|
| `hello` | `{childId, caps, ts}` | 建连应答，含当前事件游标 |
| `user_message` | `{text, pageEvents}` | 输入回显（含附件标记） |
| `thinking_delta` | `{delta}` | 思考过程增量 |
| `text_delta` | `{delta}` | 回答文本增量 |
| `tool_start` | `{toolCallId, toolName, args}` | 工具调用开始（含参数） |
| `tool_progress` | `{toolCallId, toolName, progress}` | 长工具进度文本 |
| `tool_end` | `{toolCallId, toolName, isError, result}` | 工具结束（含完整结果） |
| `message_end` | `{message}` | 单条 assistant 消息完成（content blocks 原样） |
| `agent_end` / `turn_end` | `{}` | 轮次/回合收口（`turn_end` 是一轮的可靠终点） |
| `error` | `{message}` | 错误 |

### 4.6 其余开放端点

| 方法/路径 | 说明 |
|---|---|
| `POST /api/v1/open/agent/abort` | 中止当前一轮（同 app 的 /abort） |
| `GET  /api/v1/open/agent/status` | 当前会话状态 `{busy: boolean}`——设备接口超时/重启后判断"上一轮还在跑吗"，决定继续查还是 abort |
| `GET  /api/v1/open/agent/history?limit=50` | 当前会话历史（role/content/timestamp，content 含 thinking 与 tool 块——第三方回放全靠它） |
| `POST /api/v1/open/files/upload` | 附件上传，**两种形态**：标准 multipart（`file` 字段）；或 ESP32 友好的裸流 `?filename=rec.wav&kind=audio` + 原始 body。响应 `{file:{id,...}, ref:"files/<id>", marker:"【附件音频：rec.wav|files/<id>】"}` |
| `GET  /api/v1/open/files/:id` | 文件下载（TTS 回复音频 / 设备上传附件回放）。API Key 鉴权 + 归属校验；流式返回，Content-Type/Length 齐全 |

附件约束沿用服务端现状：图片 png/jpg/jpeg/webp/gif/bmp；文本类 txt/md/csv/json/... 由
`upload-ref.ts` 的扩展名表裁决；大小暂沿用 multipart 无上限（裸流形态加 50MB 上限）。

### 4.7 错误码约定

`401` Key 无效/吊销 · `403` child 不归属 · `409` 会话忙（退避重试）· `429` 限流触发 ·
`502` 一轮失败 / 语音服务失败（含未装 ffmpeg）· `504` 同步模式超时（详见响应体 timed_out）。
语音消息的 ASR 阶段错误在流开始前以普通 JSON 返回（400/502），语义见 4.4。

## 5. 数据库变更

`server/src/db.ts` 按幂等惯例加一张表：

```sql
CREATE TABLE IF NOT EXISTS api_keys (
  id TEXT PRIMARY KEY,
  parent_id TEXT NOT NULL,
  key_hash TEXT NOT NULL,            -- sha256 hex
  prefix TEXT NOT NULL,              -- 展示前缀（前12位）
  child_id TEXT NOT NULL DEFAULT '', -- 默认对话孩子
  label TEXT NOT NULL DEFAULT '',
  last_used_at TEXT,
  request_count INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  revoked_at TEXT
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_api_keys_active
  ON api_keys(parent_id) WHERE revoked_at IS NULL;   -- 一账号一有效键
```

## 8. 对 ESP32-S3 硬件团队的契约（我方只提供这些）

> 正式接入文档：**`docs/开放API-接入指南.md`**（接口参考 / 错误处理 / 自检清单，以此为准）。

1. **推荐调用流（语音对话，全 16k 零编解码器重配置，2026-09-30 定案）**：设备编解码器固定 16kHz 一档 → 录音 16k 裸 PCM
   `POST /open/agent/voice?fmt=pcm&sample_rate=16000&tts=true&tts_rate=16000` → 读 final 行
   `transcript/reply` → 从 `audio.url` 下载 16k WAV 直喂 I2S（免 MP3 解码库）。**图文问答**：
   `POST /open/files/raw` 拿 `ref` → `POST /open/agent/chat`（带 attachments）→ 拿 `reply`；
   需要"开口播报"就在 chat 上加 `tts:true`（`tts_rate=16000` 同理）。
2. **要思考/工具过程**：同步模式的 `progress` 行已含快照级 thinking/tools（与飞书进度卡片同源）；
   要逐字 delta 与断线重放才上 SSE 流式（4.5），或轮询 `history` 回放。
3. **音频建议**：录音采样率随意（服务端统一转 16k 做 ASR，**单条上限 ≈8 分钟**——云端 ASR 的
   data-uri 20MB 硬限制）；裸 PCM 直传需带 `fmt=pcm&sample_rate=`；TTS 回复按 `tts_rate` 给 WAV
   （16k 直喂/免解码）或缺省 24kHz MP3（软解），**201 部署必须装 ffmpeg**。
4. **超时与重试**：一轮默认 240s；`409` 退避 2s 重试（app 或另一设备正在对话）；收到
   `timed_out:true` 后**不要**重发——先 `GET /open/agent/status` 看 `busy`，true 则周期查询直至
   false（那一轮其实还在跑），或 `abort` 后重来；断线重连走 `Last-Event-ID`（流式）或 `history`
   补齐（同步）。
5. **地址**：`http://192.168.1.201:8788`（家庭 LAN）。明文 HTTP 是当前部署形态的已知前提，
   硬件侧不得把 Key 固化进出厂固件全量镜像（走配网时下发/本地存储）。
6. **语音账号前提**：账号需在 设置 → 语音配置 启用语音输入并配置 ASR 凭证（qwen/MiMo 任一通道），
   否则 `/open/agent/voice` 返回 400"语音输入未启用"。TTS（edge-tts）免费零配置无需账号侧操作。
