## 0. 一句话结论

| 维度 | 结论 |
|---|---|
| **能满足需要吗** | **主线能满足，且超出所需**。孩子端 12 个场景里，10 个已被 agent 工具完整覆盖，2 个靠客户端 UI/REST 旁路完成（提醒、考核发起）。 |
| **有冗余吗** | **有明显冗余**：28 个工具里 **至少 9 处职责重叠或重复注册**，核心是「`kb_*` 三件套 + `child_*_plan_list` 三个 + `child_db_*` 三件套」三套读写通道**并行覆盖同一批表**。 |
| **最该先做的三件事** | ① 删掉重复注册的 `get_date`（确定性隐患）；② 收敛读面（`kb_query` 与 `child_db_read` 二选一，或明确分工）；③ 收回孩子对 `courses` 的写权（越权 + 数据污染）。 |
| **最大缺口** | 孩子在**对话里**无法创建提醒、无法让 agent 推非 HTML 资料（音视频）、没有"我现在考一下 / 我上次考得怎样"的专用通道——都得离开对话去点 UI。 |

## 第二部分 · 孩子 agent 工具现状盘点

### 2.1 实际注册清单（`session-registry.ts:209-235`）

**main / course 会话（28 项，带 material-panel 能力）**：

| 组 | 工具 | 来源文件 |
|---|---|---|
| 工作区文件 | `read` `write` `edit` `ls` | `fs-tools.ts` |
| 时间 | `get_date` | ⚠️ **两份定义**：`worker/kb-tools.ts:101` + `session-registry.ts:104` |
| 家长库读 | `parent_content` | `plan-tools.ts:139` |
| 会话记录 | `summarize_conversation` | `kb-summary-tool.ts` |
| 资料展示 | `display_content` | `display-tool.ts` |
| 页面操作 | `page_action` `page_inspect` `scene_command`（仅 material-panel） | `page-tools.ts` |
| 互动页生成 | `create_html_lesson` | `programming-agent.ts:260` |
| 旧 kb 三件套 | `kb_query` `kb_insert` `kb_update` | `worker/kb-tools.ts` |
| 计划（9 个） | `child_{study,exam,life}_plan_{create,list,update}` | `plan-tools.ts` |
| 受控数据通道（4 个） | `child_db_describe` `child_db_read` `child_db_write` `child_mistake_log` | `child-db-tools.ts` |

**scene 会话（3 项）**：`display_content` + `scene_command` + `get_date`（无 kb / fs / plan / db / summarize）

### 2.2 三套读写通道的实际覆盖（这是冗余的根源）

| 数据面 | 旧通道 | 计划专用通道 | 通用通道（child_db_*） |
|---|---|---|---|
| `daily_entries` | `kb_query(daily)` / `kb_insert(daily)` / `kb_update(daily)` | — | `child_db_read` / `child_db_write` |
| `topics` / `courses` / `tags` | `kb_query(topics/progress/course/tags)`；`kb_insert(course)` / `kb_update(course)` | — | `child_db_read`（只读） |
| `study_plans` | （`kb_query` 读不到） | `child_study_plan_list/create/update` | `child_db_read` |
| `exam_plans` | — | `child_exam_plan_list/create/update` | `child_db_read` |
| `life_plans` | — | `child_life_plan_list/create/update` | `child_db_read` |
| 其余 17 张表（考核结果三层、掌握、积分、兑换、重复规则、错题本…） | — | — | `child_db_read`（全表只读） |
| `mistake_book` | — | — | `child_mistake_log`（写）+ `child_db_read`（读） |

> 一句话：**同一批数据，最多三条路都能到**。而 system prompt 里同时向模型介绍了 `kb_*` 与 `child_db_*` 两套（`prompt.ts:44-45` + 注入的表清单块），模型每次都要自己选——这正是"该用哪套"的执行漂移来源。

## 第三部分 · 满足度评估

### 3.1 覆盖矩阵

| 场景 | 覆盖 | 说明 |
|---|---|---|
| S1 今日计划 | ✅ 完整 | 三个 list 工具带"今日窗口"语义，prompt 明确要求先查 |
| S2 学一门课 | ✅ 完整 | 链路闭环：`parent_content` → `display_content` → `kb_insert`/`kb_update` |
| S3/S4 漏洞沉淀 | ✅ 完整 | `child_mistake_log` 描述里把"何时记/不要记"写得很细，工程上很扎实 |
| S5 学情自省 | ⚠️ 可用但无引导 | 成绩要在 `child_db_read` 里自己拼 `exam_plan_courses` + `exam_course_results`；prompt 没有教模型"问分数去读这几张表" |
| S6 积分 | ⚠️ 可用但与 UI 脱节 | 能力有（只读积分表），但孩子端积分 UI 在别处，对话里问得少、模型也不知道该优先用哪条 |
| S7 兑换 | ✅ 完整 | 白名单写 + 服务端强制覆盖 `child_id`，安全设计到位 |
| S8/S9 自建计划 | ✅ 完整 | 三类计划都能建/改，且严格限制 `creator='child'` |
| S10 互动页 | ✅ 完整 | `create_html_lesson` 产出 → `display_content` 展示 |
| S11 场景课 | ✅ 完整（工具层） | 工具面已收窄，符合"演出会话不该干别的事"的设计 |
| S12 提醒 | ❌ 缺口 | 对话里说了没用，只能去 UI |
| S13 当场考核 | ❌ 缺口（有意的可能） | 考核被设计成独立页 + 无工具，孩子不能"让 AI 考我一下" |
| S14 音视频资料 | ⚠️ 半缺口 | `display_content` 硬校验 `.html/.htm`（`display-tool.ts:50`），媒体只能内嵌 HTML |

### 3.2 结论

**满足度：主线（学习引导 + 记录 + 计划 + 资料）已经满足，且属于「超配」**——孩子端 12 个场景，10 个有工具覆盖，其中 3 个还是"多通道覆盖"。真正的缺口只有 3 处，且都是**产品取舍问题而非能力问题**：

1. **S12 提醒**：孩子在对话里表达"提醒我…"是很自然的语言行为，却必须离开对话去点按钮，体验断裂最明显。
2. **S13 当场考核**：如果产品上就是要"考核必须进考核页、AI 不能随口考"，那这是**有意的边界**，需要在 prompt 里写清楚（现在没写，模型可能会试图"口头出题"而绕过考核体系）。
3. **S14 媒体资料**：如果家长资料库里大量是 mp4/mp3，agent 永远推不到面板，只能靠孩子自己点左侧列表。

## 第五部分 · 建议动作（分三期）

### 一期：低风险清理（不改变能力，只减面）
1. **R1** 合并 `get_date` 为一份。
2. **R4** 下线 `child_db_describe`（信息已在 prompt 注入）。
3. **R3** 收回 `kb_insert(course)` / `kb_update(course)` 的写权（保留只读查询）。
4. **R7** `child_mistake_log` 只留 `log`。
5. **R8** 评估 `summarize_conversation` 是否下线（或改为只读）。

> 一期做完，工具数从 28 → 约 21，且**孩子的表达能力一项不减**。

### 二期：收敛读/写通道（需要一次设计决策）
6. **R2** 定一个 `daily_entries` 的**唯一写通道**（建议 `child_db_write`），另一条改语义糖或下线。
7. **R5** 定读面分工：要么 `child_db_read` 唯一，把 `progress`/`course` 语义迁过去；要么明确写进 prompt"表数据用 A、进度/语义找课用 B"。

### 三期：补缺口（要产品先拍）
8. **S12** 加提醒能力（复用 `POST /scheduler/reminders` 的语义，或给 agent 一个 `child_reminder_create`）。
9. **S14** 放开 `display_content` 对媒体类型的支持（或提供"媒体资料清单 + 展示"两步）。
10. **S13** 明确写进 prompt：考核只能经考核页发起，AI 不得口头出题（**把边界写清也是一种满足**）。
11. **S5/S6** 在 prompt 里补"问分数/积分该查哪张表"，或各给一个专用只读工具，避免模型在 20 张表里瞎逛。

## 待讨论 / 需拍板的点

1. **考核是否允许"对话内发起"**？S13 是有意留白还是遗漏？（影响 prompt 写法）
2. **`daily_entries` 的唯一写通道选哪个**？注册表（约束强、通用）还是 kb 的语义糖（描述强、带标题解析）？
3. **孩子的"读自己数据"能力要不要收**？现在 23 张表全表只读，孩子问什么都能查得到（含积分流水、兑换规则）；对"孩子该知道多少自己的数据"需要产品口径。
4. **`summarize_conversation` 的去留**：它是 recording 的触发器，留在孩子手里等于给了孩子"重跑一次每日总结"的按钮。
