## 0. 一句话结论

家长端共梳理出 **37 个场景**，归入 **6 个场景域**。以场景为轴对齐工具与提示词后，五条主线结论：

1. **家长 agent 只有"一个助手 + 一个下游"**：`家长助手`（parent / parent-content **共用一份提示词、一套工具**）、以及**它的下游** `编程 agent`（不是会话，是被 `parent_build_material` 触达）。原来的第二人格 `数据管理助手`（parent-data，独立基底 + 独立工具）**已退场并删净代码**——它只是通用数据 API 的试验田，而**通用 API 不再使用**（§3.2）。
2. ~~**家长提示词是"一份写死的基底"，没有可改层**~~ → **✅ 2026-09-25（P5）已补上**：现在与孩子端同构——①常驻层（写死）/ **②家长自定义层（按场景覆盖口径，设置 →「场景口径」）** / ③运行时注入；红线、工具面与参数语义仍在代码里（§2）。
3. **主线能满足，但"能说"多于"讲清"**：37 条里 **24 条有工具可用**、**10 条天然属于界面 · 3 条属于系统自动**；**11 条"工具能查到、话说不清"**（A1 B3 C6 D1 D5 E5 E6 E8 F2 F3 F4）——**这 11 条正是"按场景写口径"的主场**，其中 **D1/D5/F2/F3 已随 P4 补齐专用工具与口径**，**F4 仍连工具都没有**（回归）。
4. **最扎眼的不是缺工具，是"有专属读数通道、却没有专属工具"**——这条**已按孩子端模板修完**（P4 补三个业务语言只读工具 + P6 拆掉通用通道）：
   - 家长版现在有 `parent_child_exam_report` / `parent_child_mastery_report` / `parent_child_points_report`，与孩子端三个工具同构；
   - ⇒ 家长问「这次考核哪几题错了、为什么」走的是**自带口径的报告工具**，不再逐表拉行（域 D 讨论）。
5. **有一处"文档承诺、实现没有"，属回归**：用户说明书 §3.7 写明家长助手覆盖「**配置管理（Control）**：查看/修改配置（默认模型、资料上限、定时任务、孩子档案）」，但**全仓没有任何一个配置读写工具挂给家长 agent**——模型、资料上限、TTS、定时任务配置**一件都改不了**，家长必须自己点「设置」。孩子版的 H1 提醒是同一类问题（界面文案承诺了对话能力），**建议同样按回归处理**（域 F 讨论）。

> **读法**：**"说得好不好"看提示词，"能不能做到"看工具，"点得到点不到"看界面**——这三句口诀对家长端同样成立，只是家长端**第三句的比重最大**（界面已相当完整，缺的是对话出口）。

## 1. 梳理口径（五条规则）

1. **场景 = 一次「有触发 + 有期望结果」的最小交互单元。** 触发可以是家长说一句话、点一个入口，也可以是一个到点的自动动作。
2. **一个功能可能承载多个场景，一个场景也可能横跨多个界面**。本文按**家长的行为**切，不按功能模块切（所以"排学习计划 / 排考核 / 排生活计划"是同一个域的相邻行，而不是三个模块）。
3. **形态** = 家长用哪种方式表达：**对话**（说给 AI 听）/ **界面**（去点去看）/ **系统**（不经过家长，自己发生）。
4. **每条场景都要回答三件事**：这个场景**用哪些工具**、**用哪些提示词**、**提示词怎么管**。工具名以 §3 台账为准。
5. **提示词与工具的状态标记**（与孩子版同一套符号）：
   - **✅ 已具备** / **❌ 缺** / **⚠ 缺口径或方向相反** / **— 无需**；
   - 提示词落点：**① 写死（谁都改不了）/ ② 家长自定义层 / ③ 运行时自动注入**。

### 1.2 家长侧的"会话地形"（先看懂这张图，后面的表才不会读错）

| 会话 | 入口 | 提示词 | 工具面 | 一句话定位 |
|---|---|---|---|---|
| **`parent`**（家长助手） | 工作台**右栏常驻聊天**（所有页面都在） | `buildServerParentPrompt`（常驻层）+ 8 个**按需加载的场景技能**；**家长可按场景覆盖口径**（P5） | **23 个家长工具 + 计划域 18 + 3 把专用报告**（`PARENT_AGENT_TOOL_NAMES` 已去掉通用三件） | **运营助手**：建课、排计划、管资料、答疑、出报表 |
| **`parent-content`**（资料助手） | 「主题编辑器」里生成/改内容时的**左栏聊天** | **同上（同一份，不是独立 prompt）** | **同上（同一套）** | 只是**换了个会话 key 与落盘目录**（避免主题编辑的上下文污染主会话）；会话落盘 `agent-sessions/<pid>/parent-content/` |

> 2. **侧栏「🗃️ 数据管理」那一格已经删除**：`parent-data` 会话（第二人格 + 通用数据 API 四件）**已退场并删净代码**（`ISSUE-144` P6）——它只是通用 API 的试验田，而通用 API 不再使用。**执行结果见 §3.2**。

## 2. 提示词如何管理（家长版：只有①，没有②③）

> 本节是**所有域共用**的机制。各域讨论小节**只写增量**。

### 2.1 孩子 vs 家长：提示词三层机制一览

| 层 | 孩子端 | 家长端 | 入口 |
|---|---|---|---|
| **① 基底** | `buildServerChildPrompt` + 场景课独立一份 | `buildServerParentPrompt`（常驻层，代码里的基底；`buildServerDataAgentPrompt` 已随数据管理助手**删净**） | **都写死在程序里，谁都改不了** |
| **② 家长自定义层** | ✅ **有**（按孩子存、留 50 版、可回滚；`getAgentPrompt(dataDir,"child",childId)`） | ✅ **有**（2026-09-25 P5 补上：**按场景**覆盖口径，设置 →「场景口径」；库内键 `skill:<家长id>:<技能名>`，留 50 版、可回退） | 家长：`SceneSkillSettings` → IPC `agents:skillList` / `agents*` → 服务端 `agents.sqlite`；**改完要新会话才生效**（技能正文读过一次就固定） |
| **③ 运行时自动注入** | 日期时间 / 孩子姓名 / 课程上下文 / 数据表清单 / 错题摘要 | **只有三项**：家长 id、今天、工作区路径（P6 起**不再注入两库表/列/路径清单**——那张清单只会诱导模型绕过场景专用工具） | 系统自动，**不需要人写** |

⇒ **判断一个家长提示词需求的落点**：家长端现在有 **①②③ 三个格子**（P5 补上了 ②）。凡是由**数据/配置决定**的（孩子姓名、模型池、统计口径），正确落点是 **③ 自动注入**；凡是**表达口径与边界**（怎么汇报、要不要复述、偏好什么说法），**优先落 ②**（家长自己就能改，不必改代码发版）；只有**红线类**（不许碰什么、必须走哪条路）才留在 ①。

> ⚠️ **两点必须记住**：① **改完要开新会话**（技能正文在会话里 `load_skill` 读过一次就固定了，改库不会回头改写已进上下文的消息）；② **改不出红线**——铁律、工具白名单、参数语义来自代码，覆盖版生效时服务端还会**追加「不可覆盖条款」**，保存时另有红线关键词校验（§8 #1）。

### 2.4 三个容易混的边界

1. **工具清单不由提示词决定，也不由家长决定**——服务端建会话时按**会话类型**装配（§3.1）；家长**改不了工具面**（既不能加也不能删），这与孩子端一致。
2. **`parent-content` 与 `parent` 共用一份提示词、一套工具**——但**会话历史彼此独立**（同一句话在右栏说和在主题编辑器里说，上下文不一样）。
3. **家长助手的"下游"不是家长 agent**：`parent_build_material` 拉起的是**编程 agent**（另一份提示词、另一套工具），它产出的文件**不是它自己写的**——汇报时要按"资料已生成"说，不要编造生成过程。

#### 域 A 讨论（2026-09-24）

> **讨论起点**：孩子档案是家长"第一件要做的事"，工具够不够、提示词说清了没有？
> **核对结论**：**工具 3 个够用，提示词几乎空白；而且"建号引导"这条最自然的对话场景是零覆盖的。**

**一、工具侧：够，且边界刻意收紧**

| 能做 | 不能做（工具层直接拒绝并指向界面） |
|---|---|
| 加孩子（姓名 + AI 伙伴名/头像/性格 + 年龄/年级/兴趣） | **设 / 重置密码**（认证红线） |
| 改档案（含改名） | **删孩子**（不可逆，会连带清本地空间） |
| 列名单 | 改订阅 / 许可 |

#### 域 B 讨论（2026-09-24）

> **讨论起点**：课程是**全系统真源**（孩子学什么、考什么全靠它），家长 agent 在这一点上够不够？

**一、为什么这一域反而做得最好（推论）**

因为它**踩过坑**：改名曾经用 upsert 导致"旧行残留 + 孩子进度永久对不上"（R1），同步曾经越界写入未分配主题（孩子看不到、日后一次性冒出上百门课）。**踩过坑的地方才会有提示词**——这条经验值得推广到还没踩过的域（尤其域 D）。

**二、工具侧的两个"设计亮点"**

1. **改名与 upsert 被拆成两个工具**，并在提示词里写死"改名绝不能用 upsert"——**用具名工具承载"唯一正确入口"**，比写十条注意事项都有效；
2. **同步工具不越界**：不代分配、不改进度、不删行（家长库已删的只列出来交家长决定）——**"报告而不执行"的克制**，是 agent 设计的正面样板。

**三、缺口：`html_path` 的"真实性"没人保证**

|---|---|
| 家长对 agent 说「这门课用 `lunyu/lesson-01.html`」 | agent 直接写进课程行 |
| 该文件**不存在** | **没有任何工具会校验** |
| 后果 | 孩子端点读/展示时才发现——**孩子版 I1/C2 的失败会归因到"资料推不出来"** |

#### 域 E 讨论（2026-09-24）

> **讨论起点**：家长端的计划工具是**最多的一组**（18 个），提示词只写了其中 3 类。
> **核对结论**：**"每天排课"这一主线（E1–E4、E7）工具与提示词都齐；"规则与自动化"这一支（E5、E6、E8）工具齐、提示词为零——全靠工具描述兜。**

**一、18 个工具的分工（一眼看清）**

| 支 | 工具 | 提示词覆盖 |
|---|---|---|
| **学习计划** | `sources` + `create` / `list` / `get` / `update` | ✅ 段里有 |
| **生活计划** | `create` / `list` / `update` | ✅ 段里有 |
| **考核排期** | `create` / `list` / `cancel` | ✅（cancel 薄） |
| **重复规则** | `recurrence_create` / `_list` / `_update` | ❌ 无 |
| **自定义定时任务** | `scheduler_task_create` | ❌ 无 |
| **孩子**（复用） | `list_children` / `child_create` / `child_update` | 部分（见域 A） |

**二、E5（重复规则）与 E2（逐天排）是同一件事的两种做法，提示词必须教"什么时候用哪个"**

| | 逐天排（`parent_study_plan_create`） | 重复规则（`parent_recurrence_create`） |
|---|---|---|
| 适合 | 一次性的、有具体日期的安排 | **长期固定项**（"每天""每周一三五"） |
| 落库 | 一天一行 | **一条规则**，系统每天自动展开 |
| 改 | 一行一行改 | **改规则**（改完影响未来所有展开） |
| 风险 | 排一个月＝30 行，改起来痛苦 | 家长以为"删了规则"其实历史行还在 |

⇒ **不写这段口径，模型会在"家长说'每天'时逐天排 30 行"**（这不是猜测：工具描述里虽然写着"无需逐天排"，但**模型先看到的是提示词**）。**建议在计划域那一段里补一小节「长期固定项用重复规则」。**

**三、E6（自定义定时任务）是全篇最"危险"的工具，提示词却一个字都没有**

- 它是**唯一一个"家长说完、系统日后自动执行自然语言指令"**的工具（无头 agent 到点跑）；
- 它的**能力白名单**（可查天气 / 可建提醒 / 可读写 daily；**不能碰积分、考核、学习计划**）**只写在工具描述里**；
- 它的失败语义（**当天失败不重试**）**也只写在工具描述里**。

⇒ 家长很自然会说「每天帮我提醒孩子做眼保健操」「每周日汇总一下这周」——**落错工具（用错 API）或写了超出白名单的指令，都会静默失败**。

**四、E 域待你定（2 条）**

#### 域 F 讨论（2026-09-24）

> **讨论起点**：说明书 §3.7 把家长助手的第一个能力域写成「**配置管理（Control）**：查看/修改配置（默认模型、资料上限、定时任务、孩子档案）」。
> **核对结论**：**这四件事里只有"孩子档案"有工具**（`parent_child_create/update`）；**默认模型、资料上限、定时任务配置一件都改不了**——属"**文档承诺、实现没有**"，与孩子版 H1（界面文案承诺"直接对 AI 伙伴说"、实际无工具）**同类，建议同样按回归处理**。

**一、逐项对照（说明书 vs 实现）**

| 说明书承诺（§3.7 Control 域） | 实现 | 结论 |
|---|---|---|
| 查看 / 修改**默认模型** | 无工具；`app_settings` 改动走界面「设置」 | ❌ 回归 |
| 查看 / 修改**资料上限** | 无工具 | ❌ 回归 |
| 查看 / 修改**定时任务** | 只有"**新建**自定义任务"（`parent_scheduler_task_create`）；**改/删/停用/查看现有任务全无工具** | ⚠ 半条 |
| 查看 / 修改**孩子档案** | ✅ `parent_child_create` / `parent_child_update` | ✅ |

**二、为什么这条值得当回归（而不是"顺手补个功能"）**

- **家长的使用预期已经被文档建立了**：家长会直接说"把默认模型改成 XX"，agent 只能答"我没有这个能力"——**体验断裂点与孩子版 H1 一模一样**；
- **代价不对称**：补两条工具（读配置 / 写配置白名单 + 复述确认）成本不高；而"改文案"要动的是产品说明书的功能边界；
- **风险口径现成**：写配置属于**高影响动作**，正好套用现有的"**先复述 → 再执行**"范式（`parent_delete_material` 的 dryRun 先例）。

**三、F2/F3 的口径缺口也是"账本口径"问题**

积分这件事在系统里是**四条链路**（每日结算 → 档位命中 → 门控解锁 → 兑换扣减），**家长问"她这分怎么算的"时，模型手上只有流水行**。孩子端已定 G1/B6 的解释口径（"必须完成项达标才解锁加分"），**家长侧应有同一份口径**（可与域 D 的"积分报告工具"合并解决）。
