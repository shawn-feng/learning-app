### ⚠️ 一个必须说明的口径问题（否则命中率会虚高）

场景技能是**会话内幂等缓存**：一个技能在会话里 `load_skill` 过一次，后面就不用再加载。所以整轮 20 条跑在**同一个会话**里时，"后面几条没再 load_skill"多数是**缓存命中**，不是"没读说明书就动手"。
⇒ 因此另做了一次**重置会话后单独跑 course 四条**（`--profile course`，用讨论稿原文措辞），专门量 course 场景的真实首次命中率。

## 3. 结论与建议（按优先级）

### ✅ 先说成立的
1. **场景守卫真的在拦，而且拦完能自愈**：只读工具也被拦（`parent_library_courses`），模型收到"请先 load_skill"后自己加载并继续——机制按设计工作。
2. **会话内幂等缓存正确**：同一个场景不会重复加载；**跨场景连读**（#15）在同一会话里无缝接上，缓存前缀不动。
3. **负向口径可靠**：#17（配置改不了）、负1（没天气工具）、负2（认证/删除红线）三条都**如实说明 + 指路界面 + 零越权工具调用**——P6 新加的那句工作原则是有用的。
4. **P4 三把工具的触发准确**：#1 走 `exam_report`、#3/#2 走 `mastery_report`、#15 走 `points_report`，没有一次去"查表"（已经没得查了）。
5. **P5 端到端通过**（详见 §4）。

### ❌ 真缺陷（建议下一批修）

| # | 缺陷 | 证据 | 建议修法 |
|---|---|---|---|
| **1** | **"定位某门课在哪 / 看某课内容"的工具**场景归属太窄**：`parent_library_courses`、`parent_library_course_content` 只归 `course`，而 `progress` 场景也要用 | #3 里模型为了找《静夜思》在哪门课，**连撞两次守卫**，被迫加载了 course + materials 才继续 | 把这两把加进 `parent-scene-progress` 的 `tools`（多场景工具任一放行，守卫天然支持）；并在 progress 技能里加一句「要定位某门课在哪 → `parent_library_courses`」 |
| **2** | **course 场景的"先核对、后复述、再写"没被执行到位**：① 核对现有结构用了 progress 的进度工具而不是课程名册；② C6 里**没复述就建了主题** | #5 / C5 的工具选择；C6 的写入 | course 技能开头把"第一步：`parent_library_courses` 看现有结构 → 复述方案 → 家长确认 → 再写"写成**编号步骤**；并在铁律 A7 里把"建主题 / 建课 / 发资料"也点名为"写库"（现在列举的是"改排期/建考核/落库课程内容/写库"） |
| **3** | **"先列清单再问哪一份 / 哪一场"没执行**：#10（这份资料不要了）与 #13（那场考核取消吧）都直接反问，没先 `parent_list_materials` / `parent_exam_plan_list` | #10 #13 工具列为空 | 在 materials / plan 技能里把这两句写成**显式第一步**（"家长没点名具体对象时，先把清单拉出来再问"）；工具 description 第一句也点一下"不带参数=先列清单" |
| **4** | **单轮太慢 / 长任务没有前台反馈**：单轮 6–124s，`parent_build_material` 那条 >150s | #3 124s、C7 >150s | 属体验问题：① `build_material` 类工具在技能里提醒"先说一句'我去生成，可能要一两分钟'再调"；② 客户端侧可考虑长任务进度提示 |

### ⚠️ 样本本身要改的地方（下次跑更准）
- **必须每轮重置会话**（或明确接受"缓存命中"口径），否则首次命中率被低估、绕远被掩盖。
- **#6 / #7 我改写过措辞**（比讨论稿更含糊，如"把这门课的资料改成…"），使"反问确认"变成合理行为；**下次用讨论稿原文**。
- #2 期望里写的 `parent_library_topics` 没被调用（模型直接用掌握报告就够了）——**这条期望本身可能多余**，建议把期望收窄成"至少命中 mastery_report"。
