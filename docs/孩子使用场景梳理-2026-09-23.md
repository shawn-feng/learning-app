## 0. 一句话结论

孩子端共梳理出 **53 个场景**，归入 **11 个场景域**。以场景为轴对齐工具与提示词后，五条主线结论：

1. **对话是天然表达方式的场景 30 条（过半）**；
2. **29 条需要提示词来满足**（"怎么说、按什么顺序做"决定成败），涉及工具的场景 24 条——但**提示词是三层叠出来的、只有中间一层能改，而改它的入口现在丢了**（§2）；
3. **最扎眼的不是缺工具，而是"有数据、没提示词"**：B6（为什么没加分）、G1（积分怎么少了）、F4（我学得怎么样）、**E7（这次错在哪）**四条**数据全都可读**，只是**没有解释口径、也没被引导去查**——其中 **E7 的数据最全**（逐题结果、每题得分、AI 评语、录音全在孩子库里，`child_exam_result` 一次读完），**提示词一个字都没有**；另有 **5 条**场景**孩子在对话里说得很自然、却只有界面出口**（§7）——本轮 **H1（提醒）与 E4（考考我）已定案**，**I4（放视频）单独立项**。
4. **提示词本身就是 agent 的操作规范**——定案：①基底**按域 → 按场景**组织，与本文档 §4 的场景表一一对应（§2.7）；
5. **通用读写工具不是"场景需要的能力"，是"缺专用工具时的兜底"——已按此撤掉并换成场景专用工具**（§3.3）：`child_points_report`（积分 → B6/G1）、`child_mastery_report`（掌握与学习情况 → F4/C1）、`child_exam_result`（考核逐题 → E7）三个**业务语言只读工具**已落地，`child_db_describe` / `child_db_read` / `child_db_write` 已撤（细节 `ISSUE-142`）。**后续遇到没覆盖到的场景，继续按"先补专用工具"的方式加，不再开通用通道。**

## 1. 梳理口径（五条规则）

1. **场景 = 一次「有触发 + 有期望结果」的最小交互单元。** 触发可以是孩子说一句话、点一个入口，也可以是一个到点的自动动作。
2. **一个功能可能承载多个场景，一个场景也可能横跨多个界面**。本文按**孩子的行为**切，不按功能模块切。
3. **形态** = 孩子用哪种方式表达：**对话**（说给 AI 听）/ **界面**（去点去看）/ **系统**（不经过孩子，自己发生）。
4. **每条场景都要回答三件事**：这个场景**用哪些工具**、**用哪些提示词**、**提示词怎么管**。工具名以 §3 台账为准。
5. **提示词管理代码**（详见 §2）：
   - **① 基底** = 写在程序里，**谁都改不了**（随版本走）；
   - **② 家长自定义层** = **唯一可改的一层**（按孩子存、留 50 版、改完要重开会话才生效）；
   - **③ 运行时自动注入层** = 系统自动拼装（日期/姓名/课程上下文…），不需要人写；
   - 状态标记：**✅ 已具备** / **❌ 缺** / **⚠ 缺口径或方向相反** / **— 无需**。

## 2. 提示词如何管理（跨域共用口径）

> 本节是**所有域共用**的机制。各域讨论小节**只写增量**：该域哪些场景需要提示词、落在哪一层、现状与缺口——不在这里重复。

### 2.1 什么场景「需要提示词」

| 判定 | 判据 | 例子 |
|---|---|---|
| ✅ **需要** | 孩子的期望靠"**怎么说、按什么顺序做**"达成——取决于口吻、边界、先共情还是先推进、结果怎么解释，而**不是查一条数据就能满足** | A3 隔几天回来、A4 情绪、A5 闲聊人设、C3 打断提问、C4 带读、C8 体面中断、D1/D3 场景课、F1 共情 + 悄悄记录 |
| ✅ **需要（与工具配对）** | 既要**查/写数据**，又要按固定口径**组织表达**、把握时机与边界 | B1 问今日安排、B4/B5 自建与改自己的计划、**E6 自建考核**、F2 生字、F4 学得怎么样、**F5 错题重考**、I5 造小游戏 |
| ❌ **不需要（界面自带）** | **纯界面动作**：点击、查看、录入——交互本身就把事做完了 | B2 点课进入、C5 点读、C6 划词、E1–E3 考核页、F3 错题本、G2/G3 兑换、I1/I3 资料与作品、J1/J2 设置 |
| ❌ **不需要（无对话）** | **纯系统自动**：孩子不发起、也不说话，只是感受到 | H2 到点提醒、I2 资料自动到达、K2 自动新会话、K4 积分结算 |
| ⚠️ **走另一份提示词** | **后台任务**由服务端自己的任务提示词驱动（**不是**孩子会话那份，家长也改不到） | K1 每日总结、K3 生活计划完成判定 |

> 一句话口诀：**"说得好不好"看提示词，"能不能做到"看工具，"点得到点不到"看界面。**

### 2.2 提示词是三层叠出来的，只有中间一层能改

| 层 | 内容 | 谁能改 |
|---|---|---|
| **① 基底** | 身份定位（现在写死为"学习伙伴"）、数据规则、教学风格（含"不闲聊、跑题拉回"）、场景主持人规范 | **谁都改不了**（写在程序里，随版本走） |
| **② 家长自定义层** | 家长为孩子追加的一份「额外规范」，**按孩子分开保存**；孩子会话与场景会话都会带上 | **家长**（这是**唯一**可编辑层） |
| **③ 运行时自动注入层** | 今天的日期与时间、孩子的姓名、当前课程的教学上下文、可选数据清单、错题待复习摘要 | 系统自动（每次建会话时拼装） |

⇒ **判断一个提示词需求的落点，先问"该进①还是③"**：凡是**由数据/配置决定**的（伙伴名字、性格、课程上下文），正确落点是 **③ 自动注入**，不该要求家长手写；凡是**表达口径与边界**（怎么共情、允许聊什么、什么时候查计划），落点是 **①②**。

### 2.3 家长在哪设 —— 通道还在，入口丢了

- **底层通道是齐的**：读、保存、看历史、回滚四个操作都在，按孩子隔离；**存空 = 恢复默认**。
- **但当前没有界面**：孩子详情页 8 个页签（进度/计划/日常/主题/复习/考核/积分/账号）里**没有"提示词"**，全仓没有一处调用这条通道；家长助手里也没有对应工具；孩子端只有「AI 伙伴设置」（名字/Emoji/性格，**不碰提示词**）。
- 旧版客户端里曾有一个「**编辑 AI 提示词**」弹窗（标题还用伙伴名字命名），重构后没被带过来 ⇒ **入口丢了、通道还在**：今天想改孩子的提示词，只能绕过界面。

### 2.4 管理机制（通道本身的规则）

| 维度 | 规则 |
|---|---|
| 真源与隔离 | 服务端是唯一真源；按「孩子 + 对象」分开存，互不可见 |
| 版本 | 每次保存，**旧版本自动进历史（最多 50 版）**，可回滚到任意历史版本 |
| 恢复默认 | 保存空内容 = 删掉自定义 → 回到①基底 |
| **生效时机** | 会话建立时读一次 ⇒ **改完必须重开会话才生效**（孩子退出重进 / 跨天自动新会话 / 主动重置）；对**已开着的会话不生效** |
| **作用范围** | 同一份自定义规范**注入孩子的全部会话**——主会话、课程会话、英语场景会话（改一处，三处都变） |
| **改不到的** | ①基底、③自动注入层、后台任务的提示词（每日总结、生活完成判定）——家长与孩子都碰不到 |
| 家长 vs 孩子 | 家长自己的提示词**只能追加、不能整体替换**；**孩子的可以整体定制**（程序里的默认稿当编辑底稿） |
| 谁能改 | 只有家长（且目前无界面）；孩子改不了，AI 自己也不能改 |

### 2.6 三个容易混的边界

1. **工具清单不由提示词决定**——工具面服务端按「会话类型 × 设备能力」装配（§3），写多少提示词也不会多出一个工具；反过来，工具再全，没有提示词也会用错时机。
2. **后台任务不受家长自定义影响**——每日总结、生活计划完成判定用的是服务端自己的任务提示词，家长改的那份**只作用于孩子的交互会话**。
3. **"改了不生效"通常不是 bug**——自定义层在**建会话时读一次**，改完不重开会话就不会体现在当前对话里。

### 2.7 提示词的组织结构（定案 · 2026-09-23：按域 → 按场景写，它就是 agent 的操作规范）

> **决定**：①基底**不再按"数据规则 / 教学风格"这类主题分段**，改为**按域 → 按场景**分段。每个"需要提示词"的场景在基底里有自己的一节；**不需要提示词的场景完全不出现**。
> **定位**：这份基底**就是 agent 的操作规范**——文档 §4 的场景表与它**一一对应**（场景表"用到的提示词"那一列，引用的就是这里的节）。

**为什么按场景、而不是按主题**

| | 现在（按主题） | 定案（按场景） |
|---|---|---|
| 分段依据 | 「数据规则」/「教学风格」两段（场景课另起一份） | **A~K 各域 → 域内只写"需要提示词"的场景** |
| 一条规则放哪 | 混在「数据规则」里（B 域规则与课程、错题、家长库并排写） | **挂在它最直接服务的那个场景下**，一条规则只出现一次 |
| 新增一个场景 | 只能往「数据规则」里塞，越塞越糊 | 往对应域加一节；跨场景共用的抽到「通用」节 |
| 覆盖度怎么查 | 查不了 | **与 §2.5 表逐节对账**：该域"需要提示词 N 条"就该有 N 节，对不上就是漏 |
| 家长要追加规范 | 无从下手（一整块尾附，没有锚点） | 有锚点：挂到对应域 / 场景下 |

搬完会**自然暴露三个空位**：**B6、F4、G1**——骨架上有位置、却写不出内容（数据全可读、解释口径未定）。位置空着是**好事**：它是可见的待办，而不是像现在这样"藏在数据规则里看不见"。

**与三层的关系 / 一处机制前提**

- **①基底** = 上面的骨架；**③运行时注入**结构不变；
- **②家长自定义层**现在是**一整块纯文本，追加在末尾**（每孩子一份，`getAgentPrompt(dataDir,"child",childId)`）。要做到"按域挂"**不必改机制**：家长按同样的域标题书写即可（追加文本原样落在末尾，节标题可识别）；若要做到**按域分别编辑 / 校验 / 回滚**，才需要把自定义层拆成按域的键——**这属机制变更，可后置**。

**收益 / 代价**

- **收益**：落点唯一（新增场景不再往"数据规则"里塞）；覆盖度可对账（§2.5 当检查清单）；家长有锚点；文档与提示词双向可查。
- **代价**：基底会略长（多了节标题）；这是一次**提示词重排**，**改完必须重开会话才生效**（§2.4）；A4/A5 与 B6/F4/G1 的**内容**仍要等口径定了才能填。

### 3.1 三个 `*_plan_list` 到底能拿到哪些字段（2026-09-23 核实）

> **⚠ 时效说明（2026-09-23 晚，ISSUE-142）**：本节与 §3.2 写作时孩子侧还有通用读 `child_db_read`（可读任意表任意列）。**该工具随后已撤**——文中「要拿只能绕 `child_db_read`」的地方，现在应理解为「由 §3.2 改造后的三个 `*_plan_list`，或 §3.3 落地的三个专用报告工具（`child_points_report` / `child_mastery_report` / `child_exam_result`）承担」。

**结论：不是"全部字段"，也不是"随便写死了几个"——是三层依次收窄，而且最大的一刀砍在最后一层。**

| 层 | 发生了什么 | 三个工具是否一致 |
|---|---|---|
| **① SQL 取列** | 学习/考核计划是**手写列清单**（显式 AS 别名）；生活计划是 **`SELECT *`** 全取 | **不一致**（见下表） |
| **② 渲染成文本** | 把行拼成"一句人读的清单"，只放 4~6 个字段 | 一致（都这么干） |
| **③ 返回体** | 只回 `text`，`details` 是空的——**没有任何结构化字段** | 一致 |

所以问题不在①而在②③：**连①里取了的数据，②不打印就等于没取到。**

| 工具 | 表 | 表列数 | ① 取了 | ② 实际打印 | ③ 损失 |
|---|---|---|---|---|---|
| `child_study_plan_list` | `study_plans` | 23 | **7 列**（id / course_name / mode / creator / status / start_at / due_at） | id 前 8 位、日期、课名、新学或复习、已学或待学、"（自己）"标记 —— **6 项** | ①丢 16 列；且 **`due_at` 取了也没打印** |
| `child_exam_plan_list` | `exam_plans` | 24 | **6 列**（id / title / status / score / start_at / due_at） | id 前 8 位、日期、标题、状态（已完成含分数）—— **4 项** | ①丢 18 列；**`due_at` 取了没打印**；`score` 仅"已完成"时显示 |
| `child_life_plan_list` | `life_plans` | 19 | **19 列（`SELECT *`）** | id 前 8 位、日期、标题、必须完成项或加分项、完成态、"📋 顺延" —— **6 项** | 取了 19 列只用 6 列；**`due_at` 同样没打印** |

**① 被丢在 SQL 之外、② 又不可能补回来的字段里，有几条是"有实际影响"的：**

- **`due_at`（截止时刻）三个 list 全部不显示** —— 而孩子说"我 20:30 前做完"时，这个时刻正是落在 `due_at`。孩子问"几点前要做完"，AI 答不出。
- **`study_plans.result_summary`（本次学习结果概要，掌握闭环的产物）读不到** —— 影响"我学得怎么样 / 这门课上次学了什么"。
- **`study_plans.points` / `count_in_rate` / `task_type` 读不到** —— 也就是**单条计划的"算不算分、算多少分"**（B6「为什么没加分」的第一手依据）不在 list 里。
- **`exam_plans.scope_json`（考哪些知识点、各几题）读不到** —— 这个字段正是 `child_exam_plan_create` 精心展开写进去的，**写进去了却读不出来**，孩子问"这次考什么"只能靠猜。
- **`exam_plans.retake`（当天重考标准）读不到** —— 「为什么还要重考一次」答不出。
- **`status` 被折叠成两态**：学习/考核/生活的 `started`（**已开始但没完成**）在 list 里分别显示成「待学 / 待考 / 待完成」，**中间态对 AI 不可见**——孩子考到一半来问，AI 会误判成"还没开始"。
- **行 id 只回前 8 位** —— 改删够用（按前缀匹配），但**不足以做精确引用**。

**那"全字段"从哪里来？** 三张表都在孩子的**可读**数据清单里（逐列登记、可选列 / 等值条件 / 排序 / 分页，默认 50 行、最大 200 行），所以 `child_db_read` **能拿到 list 丢掉的一切**。但它有两条硬限制：

1. **只支持等值条件**，做不了 `start_at <= 今天 <= due_at` 这种**日期窗口比较**；
2. 行数上限 200，且返回体超预算会被截断。

⇒ 所以三个 list 与 `child_db_read` **不是纯冗余**：**"今天是哪几件事"这种窗口语义只有 list 能给，"这条计划的分数规则 / 考核范围 / 结果概要"只有 `child_db_read` 能给**。两者是"视图 + 明细"的分工（§3 台账里"与三个 list 读面重叠"的措辞据此修正）。

**这条结论的性质**：三个 list 是**刻意做成"给 AI 念一段人看的清单"**（所以按人读数挑字段、折叠状态），**不是漏写**。代价是**被折叠/丢弃的字段必须再开一次 `child_db_read` 才拿得到**——而**当前提示词没有告诉 AI 要这么做**（这正是 §0 / §附 反复出现的「有数据、没口径」模式）。

⇒ 结论：**计划域工具需要改造**——让它能读**任意字段**、能按**时间范围**查。方案见 **§3.2**（**2026-09-23 已定案**）。

### 3.2 计划域工具改造：读任意字段 + 按时间范围查询（2026-09-23 定案）

> **⚠ 时效说明**：同 §3.1 —— 本文提到的「绕 `child_db_read`」现已由本节改造后的 list + §3.3 的三个专用报告工具承担。

> **动机（用户明确）**：后续需要工具**读取计划里的任意字段**。现在三个 `*_plan_list` 只回一段固定的人读清单（§3.1）——绝大多数列读不到，要拿只能绕 `child_db_read`，而那条路受"只有等值条件、每次约 2.7 万字符"拖累。
> **定案口径**：**不建白名单、不做预先设置**——**表里有的列就一定能取**；并且**支持按时间范围查询**。

**一、两件事都能做**

| 能力 | 怎么做 |
|---|---|
| **读任意列** | 取数用 **`SELECT *`** —— 表有什么列就拿到什么，**自动跟随表结构**。需要列清单时用 **`PRAGMA table_info(表名)`** 动态读，**不维护任何硬编码列清单**。模型指名了表里没有的列，就**按表结构运行时给可读原因**（"该表没有此列，实际有：…"），而不是拿一份预设名单去挡 |
| **按时间范围查** | 本来就是范围条件（`start_at <= ? AND due_at >= ?`）。要按其它时间列查区间，直接写 `时间列 >= ? AND 时间列 <= ?` 进 SQL（现在 `from`/`to` 是**拉回内存再筛**，一并下沉到 SQL） |

**已核实**：三张计划表的登记**本来就是全列**——`study_plans` 23/23、`exam_plans` 24/24、`life_plans` 19/19，**没有任何列被排除**；原登记只是**列含义的说明书**，不是闸门。⇒ 按上面做，字段上**不会少任何东西**。

**二、参数（三个 list 各加，均可选）**

| 参数 | 形态 | 语义 |
|---|---|---|
| `fields` | `string[]` | 只要这几列（**无白名单**，按表结构运行时校验） |
| `full` | `boolean` | 要**全部列**（不枚举列名的快捷方式） |
| `timeField` | `string` | 按哪个时间列做范围；缺省 = `start_at`/`due_at` 的**当天窗口**（即现在的行为） |
| `from` / `to` | `string` | 范围起止（`YYYY-MM-DD`） |

**不传任何参数 = 完全等于今天**（人读清单、今天窗口），现有提示词与场景**零改动**。

**三、返回体两档**

- **默认档**（不传 `fields`/`full`）：`text` = 现在的人读清单，**一字不改**。
- **明细档**（传了 `fields` 或 `full`）：`text` = **紧凑 JSON，表头只出现一次**：

```json
{"columns":["id","course_name","start_at","due_at","points","task_type"],
 "rows":[["3f9c…","静夜思","2026-09-23 00:00:00","2026-09-23 23:59:59",5,"required"]]}
```

> **为什么表头只写一次**：`child_db_read` 是每行重复列名（~550 字符/行）；**表头一次 + 行是数组**，同样 6 列每行降到 ~80–150 字符，**行数越多省得越多**。结构化内容放 **`text`**（模型读的就是 text），`details` 不动。

**四、上限**

保留 120 行 + 字符预算（照 `child_db_read` 的 40k）；超限**截断并明说**「已返前 N / 共 M 行，请收窄范围或减少 `fields`」——**不静默**（静默截断会重演"AI 以为查完了"）。

**五、明细档给原值（不折叠）**

`id` 给**全 id**（默认档仍前 8 位）；`status` 给**原始值**（`pending`/`started`/`done`/`missed`，让中间态对 AI 可见）；`parent_id`/`child_id` 照给。

**六、改造后（与 `child_db_read` 的关系）**

| | list（改造后） | `child_db_read` |
|---|---|---|
| **过滤** | **时间范围**（当天窗口 / 任意时间列区间） | 只有**等值** |
| **字段** | 默认精简视图 / **任意列** | 任意列 |
| 上限 | 120 行 + 字符预算 | 200 行 + 40k |

⇒ §3.1 列的缺口（B6 的分数规则、F4 的结果概要、"这次考什么"的考核范围、`due_at` 精确时刻）**在工具层直接消失**：**一次调用**就能连带拿回来，**不再需要提示词教模型绕道**。

**七、落点**

1. 三个 list 的 SQL 统一改 `SELECT *`，**窗口条件保留**；
2. 抽一个共用 helper：`projectRows(rows, {fields, full})` → 列筛选 + 组表头/行数组 + 截断提示（列名从行对象取或 `PRAGMA table_info` 动态读）；
3. **工具描述**补一句用法（跟工具同源、调用时必看；`child_mistake_log` 把判据写在工具描述里已达标，是同一先例）；
4. **参数还原无需额外处理**——`fields: Type.Array(...)` 已被 `defineTool` 的 `prepareArguments` 统一还原（`tool-kit.ts`，ISSUE-134），不会踩"数组被序列化成字符串"的坑。

**顺带可做（可选、后置）**：三个工具合并为一个 `child_plan_list(type: study|exam|life, …)` —— 工具数 28→26、三处口径天然统一；代价是改工具名并联动提示词与场景表引用。

### 3.3 通用读写 `child_db_read` / `child_db_write` 到底有没有场景需要？（2026-09-23）

> **✅ 已落地（2026-09-23 当晚）**：用户拍板"**既然梳理了场景，就针对场景设计工具或优化现有工具，不用通用工具了；如果再遇到没有考虑到的场景，就再增加工具**"。据此按**路线 A** 实施完毕：**新增** `child_points_report` / `child_mastery_report` / `child_exam_result`（`server/src/agent/child-report-tools.ts`）、**扩展** `child_mistake_log(action=list)` 返回（补关联课程 / 知识点 / 有无原题）、**撤掉** `child_db_describe` / `child_db_read` / `child_db_write`。工具总数仍是 **28**（删 3 加 3），但**语义全部变成业务语言**。落地明细与验收见 **`ISSUES/ISSUE-142.md` §九**。

> **讨论起点（用户提出）**：**"从使用场景看，`child_db_write` 和 `child_db_read` 没有需要。"**
>
> **核实结论**：**写侧"基本成立"（但原因不是冗余，而是那条链路整体没通）；读侧"不成立"——删掉会直接丢 5 个场景的一半。** 但**方向是对的**：这两个工具**不是"场景需要的能力"，是"缺专用工具时的兜底"**。

**一、写侧：`child_db_write`（白名单两表）**

| 白名单表 | 场景里谁在用 | 核实结论 |
|---|---|---|
| `daily_entries`（增改删） | **没有场景** | **冗余**：写 daily 的**正规通道是 `kb_insert` / `kb_update`**（带语义解析 + 去重 + 计划联动三件事，db write 都没有）。工具描述里已有 `redemption_requests` 的"请用 child_db_write"措辞，但 daily **从不提示走它** |
| `redemption_requests`（只能新增） | **G2 / G3 兑换** | ⚠ **它是孩子侧唯一活着的兑换通道——但这条链路整体是半成品**（见下） |

**（关键实测）"兑换"这条链路目前的真实状态**：

1. **上游断了**：`redemption_items`（可兑换商品表）**全仓没有任何写入点**——只有建表 SQL（`server/src/db/kb.ts:322`）、表登记与引用校验。**家长没有"发布可兑换奖励"的入口**，商品表永远是空的；
2. **孩子端没有界面**：`src/`、`web/src/`、`electron/` **全仓搜不到兑换相关交互**，只有 `RewardPanel.tsx` / `TodoModal.tsx` 里"已兑换"的**展示**。⇒ 文档 §4 里 G2/G3 写的"**界面自带**"**是错的**（本轮修正）；
3. **有一条服务端接口，但没人调**：`POST /api/v1/rewards/:childId/redeem`（`server/src/routes/plans-rewards.ts:659`）要求 **家长 JWT**（`authParent`），且**当场扣分并写流水**——与 §6 硬约束 #6"现实权益扣分发生在**家长履约时**，不是孩子申请时"**互相矛盾**；且客户端**零调用点**；
4. ⇒ **孩子侧唯一能落下兑换申请的，就是 `child_db_write` 的 `redemption_requests` 白名单**（只写申请、不扣分、等家长审批——语义反而是对的）。

**所以这条要换个说法**：不是"`child_db_write` 冗余"，而是**"兑换（G2/G3）在两个端都没有出口，只剩 agent 这条半截通道"**。删掉 write = 承认 G2/G3 目前**彻底没有出口**（要恢复就得先做界面或开通接口）。

**二、读侧：`child_db_read` 删不掉——4 类数据、5 个场景只有它能读**

| 要读的数据 | 相关场景 | 为什么别的工具读不到（已核实） |
|---|---|---|
| **积分三表**（`points_ledger` / `points_balance` / `reward_daily_stats`） | **B6**（为什么没加分）**G1**（积分怎么少了） | **没有任何积分类工具**；`kb_query` 的 5 种查询（daily / topics / progress / course / tags）**不含积分** |
| **掌握四列 + 学习结果**（`courses.mastery_level / mastery_desc / teaching_advice / mastery_updated_at`、`study_plans.result_summary`） | **F4**（我学得怎么样）**C1** | `kb_query(progress)` 的 course 分支**只 select 五列**（`topic/topic_key/title/status/last_review`，`worker/kb-tools.ts:215`），**不含 mastery 四列**；三个 `*_plan_list` 只回人读文本、**不含 `result_summary`** |
| **考核逐题三层**（`exam_plan_courses` / `exam_course_results` / `knowledge_point_records`） | **E7**（这次错在哪） | **没有任何"读考核结果"的工具**；三个 `*_plan_list` 只给"考了没、几分"这一层 |
| **错题本关联字段**（`course_ref` / `knowledge_point_name` / `question_id`） | **F5**（错题重考） | `child_mistake_log(action=list)` 的返回**不含这三列**（`child-db-tools.ts:262-268`） |

**三、这次核实的真正收获：它是"兜底"，不是"能力"**

`child_db_read` 的设计是**一张注册表 + 一套受控 SQL（22 张表全登记）**——这是**服务端实现方便**的产物（一次覆盖所有读需求），**不是"孩子需要会读 SQL"**。所以正解不是"删"，而是**把兜底变成专用**：

| 路线 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | **先补 4 个专用只读工具，再删 `child_db_read` + `child_db_describe`**：`child_points_report`（余额/流水/当日结算/门槛 → 顺带解决 B6/G1"有数据没口径"）、`child_mastery_report`（掌握四列 + 学习结果 → F4/C1）、`child_exam_result`（某场考核逐题 + 每课概要 → E7）；错题关联字段**直接扩 `child_mistake_log(list)` 返回**（比新工具自然，已在 `ISSUE-137`） | 要写 3 个新工具；**收益**：每个出口自带口径，安全面收窄，"有数据没口径"问题在工具层消解 |
| **B（省事）** | **只删 `child_db_describe`**——它与 ③ 自动注入的表清单**重复**（读之前不必先调它）；`child_db_read` 暂留 | 收益小但零风险 |
| **C（激进）** | 现在就删 `child_db_read` | **直接丢 5 个场景的一半**（B6 G1 F4 E7 F5 的"读出数据"），只剩提示词无济于事 |

**四、顺带两条**

1. **§3.2 改造会吃掉 read 的一部分地盘**：三个 `*_plan_list` 改成"可读任意列 + 时间范围"后，read 在"计划细则"这一块的唯一价值（拿回 list 折叠掉的字段）**自动消失**——届时它的不可替代范围**只剩上表 4 类**；
2. **`child_db_write` 有 30 行/5 行的熔断上限**（`rowLimit`），本身是克制的；真正该收的是 **"daily 那一半"**（与 kb 通道重复，且没有语义解析/去重/计划联动）。

> **完整方案（含影响面、替代工具契约、验收）见 `ISSUES/ISSUE-142.md`。**

  - 会话是持久缓存的，换设备重连会按新能力重建。
- ⇒ **家长改不了工具面**（既不能加也不能删），这是设计边界，不是缺口。

| **③ 运行时自动注入** | 今天的日期 + 当前时间（B 域判断"今天"的基准）、孩子姓名、可选数据清单、错题待复习摘要 | 系统自动 |

- **管理粒度现状**：B 域规则**没有独立章节**，是**混在"数据规则"那一段里**、与课程教学、错题、家长库的内容并排写的。

**四、缺口：B6（为什么达标了却没加分）**

数据其实**能读**：奖励规则里有门槛（任务完成率下限、考核得分下限），每日统计里有「是否过门槛 / 完成率 / 结算积分」，流水里每笔都有原因。但**提示词既没写门控口径、也没引导去查** ⇒ AI 只会泛泛安慰，答不出真正原因。**这是"有数据、没口径"型的缺口，不是缺工具。**

> **补充（2026-09-23 字段核实，详见 §3.1）**：B6 的"单条计划算不算分、算几分"落在 `study_plans.task_type / count_in_rate / points` 三列上，而**这三个字段三个 list 一个都不返回**——AI 想按计划逐条解释"这条为什么不加分"，**必须再开一次 `child_db_read`**。所以 B6 的补齐要写两步口径：**①门控规则怎么说；②细节字段去哪查**（现在这两句都没有）。

#### 域 C 讨论（2026-09-23 · 专项：掌握概况与学习结果 ＋ 学完即写方案 ＋ db 读写核实）

> **讨论起点**：学习进度表里新增了「课程掌握概况」，每次学习计划后新增了「学习结果」——这两个字段**什么时候写入？有对应的工具吗？**
> **一句话结论**：**写入不靠"学完就写"，靠一个每天跑一次的定时任务批处理**——家长没添加这个任务，两处**永远是空**；**工具确实有（4 个 `mastery_*`），但只装在后台任务上，孩子 agent 一个都没有。**（第七节记录了把"学完即写"做成工具的备选方案，**本轮只记录、不实施**。）

**一、两个字段是什么、在哪**

| 俗称 | 实际字段 | 位置 | 语义 |
|---|---|---|---|
| 课程掌握概况 | `courses` 的 `mastery_level` / `mastery_desc` / `teaching_advice` / `mastery_updated_at` **四列** | 孩子库 `courses`（学习进度表） | 档位（`not_started`/`learning`/`needs_review`/`mastered`）+ 累计掌握叙述（最开始 → 中间 → 最新）+ 下次教学建议 + 刷新时间 |
| 学习结果 | `study_plans.result_summary` | 孩子库 `study_plans`（一行 = 一次学习/复习计划） | **这一次学习**的课程级结果概要（≤400 字） |

> 建表注释里写的「由每日 progressAnalysis 任务（第 3 环）写入」是 ISSUE-135 方案期的叫法；**落地后的实际承载是下面这个自定义任务**，全仓没有另一个叫 progressAnalysis 的任务。

**二、什么时候写 —— 归「学习情况分析」定时任务管**

- **承载**：家长在「定时任务」页**显式添加**的模板任务（默认每天 **21:30**，名字/时刻可改，指令也可改）。**0.5.8 起不再自动播种** ⇒ **家长没加，这两个字段就没人写**。
- **执行流程（三步）**：
  1. **`mastery_todo_list` 定范围**——① **已完成、但还没有知识点掌握记录的学习计划**（`status='done' AND active=1` 且无 `source='study'` 的知识点流水），回看天数缺省 **3**（传 0 = 全部历史，用于补跑）；② **最近 3 天有学习或考核动静的课程**（有学习计划动的 + 考核结果表里有记录的）。
  2. 逐个计划用 **`mastery_plan_context`** 取素材（该计划窗口内的学习记录 + 这门课的知识点清单 + 历史掌握 + 错题本未掌握点）→ 判断每个知识点的 outcome（`solid`/`partial`/`weak`）→ **`mastery_save_records`** 写回：知识点流水 + **`study_plans.result_summary`**（仅 `source='study'` 且给了值才 UPDATE）。
  3. 逐门课用 **`mastery_save_course_mastery`** 写回：**`courses` 那四列** + 各知识点的 level 与累计叙述。
- **性质**：**批处理 + 幂等**——按计划/课程**覆盖式**写，**同一天重复跑不会重复累计**；跑完由任务自己用两三句话向家长汇报（结果落在「定时任务 → 运行记录」）。
- **所以时点上**：孩子今天学完一门课，**白天不会立刻出现"掌握概况"**，要等当天任务跑完（默认 21:30 之后）。考核交卷同理——它只是把课程标成"待刷新"，**写入仍然在任务里**。

**三、有对应的工具吗 —— 有 4 个，但只给后台任务**

| 工具 | 读/写 | 干什么 |
|---|---|---|
| `mastery_todo_list` | 读 | 看待归纳的计划 / 待刷新的课程（定范围） |
| `mastery_plan_context` | 读 | 取某个计划的素材（学习记录 + 知识点 + 历史掌握 + 错题） |
| `mastery_save_records` | **写** | 知识点掌握流水 + **`study_plans.result_summary`** |
| `mastery_save_course_mastery` | **写** | **`courses` 掌握四列** + 知识点累计掌握 |

装配范围（已核实）：这 4 个只出现在 **`worker/custom-tasks.ts`** 的工具集里（与 `kb_*`、家长数据 agent 工具、天气、提醒同批装配）；**孩子 agent 的 28 个工具里没有它们**（§3 台账）。

**四、孩子 / 家长各自能不能碰这两处**

| | 读 | 写 |
|---|---|---|
| **孩子 agent** | ✅ **能读**：`courses` 与 `study_plans` 都在孩子的可读表清单里，掌握四列与 `result_summary` 都已逐列登记 | ❌ **写不到**：`kb_update(course)` 的字段白名单只有 `状态 / 最近复习 / 复习次数 / tags` 四项，**掌握四列不在内**；`study_plans` 的三个 `*_plan_update` 只有删 / 改期；`child_db_write` 白名单只有 `daily_entries` + `redemption_requests` |
| **家长助手 / 家长界面** | ✅ | 只能经 `mastery_*`（且仅在该定时任务内）；**界面上没有直接改这两处的入口** |

⇒ 定性：**这两处是"系统生成、只读给孩子"的字段**——与"完成态不手动勾、积分不可写"属同一类硬约束。

**五、落到 C 域的两条影响**

1. **C7 的"进度自动记下"其实是两件事**：*学没学过*由系统**即时**记（`courses.last_review`、`study_plans.status`）；*学得怎么样*（掌握概况 / 学习结果）**依赖当晚任务**。所以「我刚学完，掌握概况怎么还是空的」**是正常的，不是 bug**——而提示词对此**零口径**，AI 要么答"系统还没更新"、要么干脆瞎猜。
2. **这两处字段只被"读"过，从没被"讲"过**：孩子的可读清单里有掌握四列与 `result_summary`，但**没有任何提示词说明它们是什么、什么时候才有值、空值该怎么回**——属 §0 的「**有数据、没口径**」，与 B6 / G1 / F4 同源。

**六、顺带记下两个小问题**

- **`teaching_advice` 的"增补"名不副实**：列注释与工具描述都写"只增补"，实际代码是 `SET teaching_advice = ?` **整列覆盖**。"增补"的原意是"不改家长手写的方法字段"，字面容易被模型误读成"追加"——口径建议改成"**覆盖本列，但不碰家长库的方法字段**"。
- **这两处本来是给家长看的话术，不是给孩子的分数**：该任务的默认指令明确要求"**不要输出「掌握度 0.8」这类内部数字**"。所以孩子若在 C7 / F4 里问"我这门课怎么样"，**应转述掌握叙述、不能照读档位/分数**——这一层口径同样没有。

**七、方案记录：把「学完即记录」打包成一个工具，夜间定时任务降为兜底（2026-09-23 记录 · 暂不实施）**

> **来源**：用户提出——「也可以打包成一个工具，在学完后就做好记录，晚上的定时任务算是一次兜底。这个现在先不做，只是写到文档里。」
> **性质**：**本轮只记录方案，不改任何代码**。它是一个产品取舍（即时可见 vs 调用成本），不是缺陷修复。
> 现行机制（无这个方案时）见上一节：**掌握与学习结果只有一个产生时间点 = 当晚任务**。

**7.1 现状 = 纯批处理（只有"离线"一条腿）**

| 事实 | 后果 |
|---|---|
| 写入只发生在每晚任务里 | 孩子白天学完，**掌握概况/学习结果必然是空的**（见本节第五条第 1 点） |
| 任务由家长**显式添加**（0.5.8 起不自动播种） | **家长没加，这两处永远是空** |
| 交卷只标"待刷新" | 考核结果也要等当晚 |

**7.2 目标形态 = 在线优先 + 离线兜底**

| | **在线腿**（新增） | **离线腿**（现有夜间任务，保留） |
|---|---|---|
| 触发 | 一次学习**收尾时**，由孩子会话调用新工具 | 定时（默认 21:30） |
| 写什么 | **本次这一条计划**：`result_summary` + 该计划的知识点流水 + 刷新该课掌握四列 | 全部待归纳计划 + 待刷新课程 |
| 角色 | **快**：学完就能问"我刚学得怎么样" | **兜底**：补在线腿漏掉的（对话被中断、写库失败、考核链路、跨天回看） |

**7.3 打包成"一个工具"的形态**

- **新增 1 个工具**（暂名 `record_study_result`），**装给孩子会话**；现有 4 个 `mastery_*` 不动，继续留后台任务。
- **入参尽量小**：`{ plan_id（或 course_name）、summary、knowledge_points:[{kp, outcome, note}] }`——**"归纳"由模型在收尾那一轮完成**（它本来就要说一句总结），**工具只负责落库**。
- **内部** = 「`mastery_save_records` + `mastery_save_course_mastery` 的单计划即时版」：写知识点流水（`source='study'`）+ `result_summary`（≤400 字）+ 按同语义刷新课程四列。
- **与兜底天然兼容**：夜间任务的定范围判据正是「**已完成、且还没有 `source='study'` 知识点流水的学习计划**」⇒ **即时写过就不在范围里**，天然不重复；课程那条（最近 3 天有动静）会再覆盖刷一次，**幂等无害**。
- ⚠ **边界（重要）**：这条**不破**"孩子不可写掌握"的硬约束——**孩子仍然没有"随手改掌握"的能力**。新工具只接受"**本次学习结果**"这一个语义、由服务端按固定规则落库，与 `child_db_write` 那种通用写是两回事。

**7.4 顺带解决 / 需要注意的点**

| | 内容 |
|---|---|
| ✅ | **不再依赖家长是否添加定时任务**——在线腿在会话里发生，任务没加也能产出掌握 |
| ✅ | 「我刚学完，掌握怎么是空的」**消失**（C7 与 F4 立刻有值） |
| ⚠ | **触发点要定**：不该是"孩子说结束"，应是**系统把该学习计划判成已完成之后**的收尾（K3 的学习判定）——否则"学了 3 分钟就走"也会被当一次学习写进去 |
| ⚠ | **考核那条链路接不进来**：考核是另一条链路、孩子 agent **零工具**，交卷只标"待刷新" ⇒ **考核后的刷新仍然只能靠夜间任务**——这是"兜底腿必须留着"的第二个理由 |
| ⚠ | **成本与延迟**：现在是"一次调用处理 N 条计划"，改成在线是"每条计划一次调用"；孩子端会**多一轮收尾推理**（换来的是即时可见） |
| ⚠ | **中断与失败**：中途关窗、写库异常 ⇒ 本次没即时写 → **由夜间任务接住**（这正是"兜底"的意义） |

- 机制上**没有阻断**：幂等口径现成、落库逻辑现成（两个 save 合成一个）、触发点也现成（计划判定完成之后）。
- 属于**产品取舍**（即时可见 ↔ 调用成本与复杂度），**本轮不做，只记录**。
- 将来若要做，落点 = **上面 7.2 的"在线腿" + 现有夜间任务原样保留**；同时 C7 / F4 的两条待拍板（下表第 1、2 条）**由它一并回答**——有在线腿，"当晚才生成"这句口径就不必再写。

**八、C 域要不要 `child_db_read` / `child_db_write`？（2026-09-23 核实）**

> **问题**：C 域有需要用到 db write 和 db read 的吗？工具是不是已经能读取所有必须信息了？
> **一句话结论**：**写——一个场景都用不上（C 域里 `child_db_write` 是冗余的）；读——现有 8 条设计里也不需要，唯一例外是「掌握概况 / 学习结果」这两处（只有 `child_db_read` 读得到）。**

**8.1 写侧：C 域不用 `child_db_write`**

写 daily 有**两条通道**，C 域该走 kb 那条：

| | `kb_insert` / `kb_update`（C 域的正规通道） | `child_db_write` |
|---|---|---|
| 能写的表 | daily 记录（+ course 部分字段） | `daily_entries`（增改删）+ `redemption_requests`（**仅新增**） |
| 输入形态 | `### 标题` + 字段行文本，**自动解析** | **必须自己给 `raw`**、自己拼格式 |
| 附带能力 | 标签自动解析、`planId`/`planOutcome` **联动生活计划状态**、**重复自动跳过** | 无 |
| 熔断 | — | 单次命中 **30 行**即报错、要求收窄条件 |
| C 域用途 | **C7 记录学习条目 ✅** | **用不上**（它是 G 域"兑换申请"那条在用的） |

⇒ C 域**没有任何一条场景**需要 `child_db_write`，把它从 C 域口径里去掉不丢任何能力；而且 **kb 通道更安全**（语义解析、去重、计划联动这三件都是它有、db write 没有的）。

**8.2 读侧：现有 8 条不需要 `child_db_read`**

C 域的读需求只有三件——**学到哪了 / 下一课是什么 / 有哪些课**，加 C7 的**今天记过什么**。这些被 `kb_query` 的视图**全覆盖**，而且**自带聚合与计算**：

| C 域要读什么 | 谁提供 | 要 db read 吗 |
|---|---|---|
| 学到哪了、**下一课是什么** | `kb_query(topics / progress)` → 进度视图（已学 / 总数 / **下一课** / 更新时间） | ❌ |
| 有哪些课、什么状态 | `kb_query(progress)` 的课程清单（名称/状态/标签）；`kb_query(course)`（名称/状态/**最近学习**） | ❌ |
| 家长定的教法与资料 | `parent_content` | ❌ |

⇒ **"读到某一次考核的所有题目的考核结果"这条需求，工具已经具备、不需要新工具**：`exam_plans` 先定位那一次（`status=done` 按 `done_at` 倒序，或孩子直接点名）→ `exam_plan_courses` 按 `plan_id` 过滤 + 按序号排序**一次读完**（单次预算 50 行 / 4 万字符 / 单元格 4000 字符——一次考核的题量通常远在预算内）。

**二、老实话：考前读不到题、标准答案也读不到（而且这**应该**保持读不到）**

| 想读的 | 孩子侧现状 | 结论 |
|---|---|---|
| **课程** | 孩子库 `courses`（含掌握四列）+ 逐题行里的课程名 | ✅ 完整 |
| **知识点** | 只有**考过/学过的**（流水与累计表里的名称快照 + 档位 + 描述）；**全量知识点清单与详细描述读不到**（`knowledge_points` 只在家长库，孩子侧无表、也无工具） | △ 部分 |
| **题目** | **考后**逐题快照全有 ✅；**考前**读不到（出题在"开始考核"时才抽，落库在评分后） | △ 部分 |
| **标准答案 / 评分标准** | 读不到（`question_bank.answer` / `scoring` 只在家长库） | **✗ 且建议保持读不到** |

**为什么"答案不给"是刻意的、不是缺口**：孩子 agent 一旦能读题库答案，孩子只要问一句"那道题答案是什么"就能套出来，考核的检验意义直接归零。而**讲错题并不需要原答案**——题干、朗读/背诵题的原文（就在逐题行里）、AI 评语，加上课程资料与 AI 自己的知识，足够讲清"为什么错、正确应该怎样"。

⇒ 若要让讲解更有依据，**优先开放的是 `knowledge_points.detail`（考核要点 / 教学内容），不是 `answer`**——那是"该讲什么"的骨架，不是"答案"。

**三、重考：三种，别混**

| 想做的 | 现状 | 能做吗 |
|---|---|---|
| **同一场考核再考一次** | 家长设的 `retake`（如"错两题以上当天原题重考"）→ 服务端评分后**自动**生成当天重考计划；孩子**没有**自己发起"再来一次"的出口 | ❌ 孩子侧没出口（要不要开，待定） |
| **围绕错题另排一次考核** | `child_exam_plan_create`（**与 E6 同一个工具**，按知识点级建） | ✅ 能，但考的是**同知识点的题**、不保证原题（= F5 路线 B） |
| **锁定原题重考** | scope 没有题目维度（最细到「知识点 × 题数」、池内随机抽） | ❌ 需协议级改造（= F5 路线 A，二期） |

**四、缺口只有一个：提示词（怎么分析错题）**

E 域现在**没有任何一条**讲复盘的口径。规格按三段式给（完整版见 **`ISSUES/ISSUE-139.md`**）：

- **孩子会说**：「我这次考得怎么样？」「哪几题错了？」「帮我讲讲错的那几题」「错的我想再考一遍」
- **怎么做**：① 先定位那一次（默认"最近一次已完成的"，孩子点名了就按他说的）；② 读逐题结果，**先给整体**（考了几题、对几题、错集中在哪个知识点）；③ **一次只讲一两题**，挑**最基础 / 错得最集中**的先讲；④ **先问"你觉得这题卡在哪"**，再讲正解——不要直接灌答案；⑤ 讲完给一道**同类小练习**；⑥ 孩子说要重考 → 转 `child_exam_plan_create`（同 F5）
- **边界**：**一次不倾倒全部错题**（孩子会崩）；不报内部数字（掌握度只转述叙述，与 F4 同口径）；**不承诺"重考考原题"**（如实说"同类题再练一遍"）；**不给孩子看标准答案**；**不出现"考得差"这类评价**，只讲事实 + 下一步

#### 域 F 讨论 · 补（2026-09-23）：**针对错题创建一次考核**

> **讨论起点（用户提出）**：F 域里要考虑一个场景——**针对错题创建一次考核**。但现状有两条约束：①**创建考核必须挂课程**，而**错题不一定关联课程**；②考核**只能指定到知识点**，**无法指定到题目**。这个场景怎么处理？

**一、先把"错题"分三类（决定能不能做）**

| 来源 | 谁写的 | `course_ref` | `question_id` | 知识点 | 能不能进考核 |
|---|---|---|---|---|---|
| **考核错题**（交卷自动同步） | 提交路由（`source=exam`） | ✅ 有（课名） | ✅ 有 | ✅ 有 | **可以**（现状只能做到知识点级） |
| **对话口述错题**（"这道题我做错了"） | `child_mistake_log` | ⚠ 可选（模型给了才有） | ❌ 无 | ❌ 无 | **不行**（连课程都可能没有） |
| **生字 / 薄弱点** | 同上 | ⚠ | ❌ | ⚠ | 不该考（生字不是题） |

**二、三个卡点（逐个核实）**

| # | 卡点 | 实测 |
|---|---|---|
| 1 | **课程是必填的顶层维度** | `exam_plans.scope_json.courses = [{title, kps:[{name,count}]}]`；创建时（工具与 REST 同口径）先按课名落到孩子库 `courses` → 家长库 uuid → 知识点。**没有课程直接建不出来** |
| 2 | **最细只到"知识点 + 题数"** | scope 的 `kps` 只有 `{name, count}`；出题按知识点取**池、池内随机抽前 N 道**——**没有题目维度** |
| 3 | **错题可能连知识点都没有** | 口述错题只写 content/detail（+ 可选课名）；**只有考核同步的错题**才带 `question_id` 与知识点 |

⇒ 所以"针对错题建考核"按现状**最多只能做到**"按错题所在知识点建一次考核"，而且**抽到的题不一定是那道错题**。

**三、那个"必须挂课程"其实不是死结（关键洞察）**

只要错题带了 **`question_id`**，课程与知识点就能**反查**出来——题目活在题库里，天然属于某课程的知识点。所以真正的问题不是"错题有没有课程"，而是"**错题有没有 `question_id`**"：

- **有 `question_id`** → 课程 / 知识点 / 原题**三样全能定位**（只差"锁原题"这个能力）；
- **只有知识点名快照** → 能定位到知识点，但课程要靠名字匹配（改名/重建就断）；
- **什么都没有（口述错题）** → **建不了，也不该硬建**。

**四、三条可选路线**

| 路线 | 做法 | 能考到原题吗 | 代价 |
|---|---|---|---|
| **A 题级锁定**（新增能力） | scope 增加题目维度（如 `questions:[question_id]`）：出题时**按 id 直取、跳过随机池** | ✅ 就是那道错题 | 改 `scope` 契约 + 出题装配 + 校验（题目被删/被改要报错）+ 端到端测试——**属协议级改造** |
| **B 知识点级**（零改造） | 用现有 `methodSpec.require = {「错题所在知识点」: N}` 建考核 | ❌ 抽到的是**同知识点的随机题** | 不用改代码；**卖点要如实说成"同类题再练"** |
| **C 不进考核** | 错题重做走**错题本自己的复习闭环**（`ISSUE-114` 已设计：讲解 → 重做 → 标"会了"） | ✅ 可对着原题讲/重做 | 无场次、无分数、无报告——语义是**复习**不是考试 |

**五、建议（推荐 B 先行、C 为主、A 留二期）**

1. **"错题"这件事的主导权该在错题本，不在考核**：错题本已有"重做 → 标会了"的闭环设计（路线 C）；考核是**重流程**（场次/计分/成绩报告/加分项判定），为几道错题拉一场考核并不划算。
2. **确实要"考一次"时，先做 B**：零改造、当场可用，**话术必须诚实**（"我把你错的那几个点再考一遍"，不承诺"考原题"）。
3. **A 留二期**：真要做"错题原题重考"，必须给 scope 加题目维度，属协议级改动，且要处理题目被家长删改的情况。
4. **口述错题（无课程）不建考核**：交给 F1（共情 + 讲解 + 悄悄记录），把"重考"引导为"这几道题我现在给你讲一遍"。
5. **顺带一个数据缺口**：`child_mistake_log` 只收 `content/detail/course`，**收不到知识点/题目**——想让口述错题也能进复习或考核闭环，**得给它加一个"关联到哪门课/哪个知识点"的可选参数**（模型能确认时才填）。

   —— 连带一条：**`child_mistake_log` 要不要加"知识点 / 课程关联"参数**（不加的话，口述错题永远进不了闭环）。

`POST /api/v1/scheduler/reminders`（创建，必填 `childId/name/text` + **`time`(HH:mm)**；`frequency ∈ once｜daily｜weekly｜interval`，`weekly` 需 `weekday`、`interval` 需 `intervalMinutes`、**`once` 需 `fireAt`**；`voice` 默认 true）→ `GET /api/v1/scheduler/reminders`（**客户端每分钟轮询**取到期项并**就地标记已触发**）→ 到点**语音播报 + 横幅**；列举走 `/reminders/list`。库层 `db/task-runs.ts`（`createReminderTask` / `listChildReminders` / `takeDueReminders`），落 `scheduler_tasks(type='reminder')` + `scheduler_task_assignments`。

**三、工具：已有 `create_reminders`，但它是"家长那个"**

`create_reminders`（`worker/custom-task-tools.ts`）只装给**家长自定义定时任务的执行会话**：**批量数组**、`owner='parent'`、带 `source_task` 滚动替换与精确去重。**语义与孩子侧不同**（孩子是"对我说的一件小事"，家长任务是"批量生成播报窗口"），**不建议直接复用** → 孩子侧**新增 3 个小工具**（单条创建 / 列举 / 取消）。

**四、如何记录（本轮的真正难点）**

「提醒我明天带跳绳」**里没有时刻**，而库层 `time` **必填**。所以规则是：

1. **先取时间**（`get_date` 拿"今天几号几点"），**不许凭印象算日期**；
2. **没时刻就问**（"明天几点提醒你？"）；模糊词（"早上"）→ 给建议时刻并**复述确认**；
3. **日期 → 频率映射**：今天/明天/后天/下周X → `once`（`fireAt`）；每天 → `daily`；每周X → `weekly`；**每隔 N 分钟 → `interval`**；
4. ⚠ **`interval` 是"每隔 N 分钟一直提醒"，不是"过 N 分钟后提醒一次"**：「**半小时后**提醒我喝水」= `once`+`fireAt`；「**每隔半小时**提醒我喝水」才是 `interval`；
5. **一次说多件事 = 建多条**（循环调用）；
6. **建完回执 + 给出路**（"到点我会喊你，想改点 🔔 我的提醒"）。

**五、边界**：**不许口头答应不落库**；建不成**如实说**（缺时刻 / 这条已存在 / 超上限）；只能给自己建；**不把学习计划改成提醒**；**只在孩子在设备上时播报**（不承诺"我一定会提醒你"）。

> 完整方案（参数、上限、验收）见 **`ISSUES/ISSUE-140.md`**。

#### 域 I 讨论（2026-09-23）：**孩子 agent 的工作区与文件能力**

> **讨论起点（用户提出）**：I 域里要让孩子 agent 也能有**同样的操作场景**——agent 要**知道工作区的目录架构**，要**能操作文件**。

**一、工具侧：四件套已经在手，缺的是"知道在哪儿、该干什么"**

| | 家长 agent | 孩子 agent |
|---|---|---|
| 文件工具 | `read` / `write` / `edit` / `ls` | **同一套（`read` / `write` / `edit` / `ls`）** ✅ |
| 根目录 | `workspaces/<家长id>/`（含 `materials/` 资料真源、`uploads/`、`scratch/`、各孩子目录） | `workspaces/<家长id>/<孩子id>/`（**只在自己这一格**） |
| 越界防护 | `resolveWithin`：`..` 逃逸 / 绝对路径 / 符号链接外逃**一律报错** | **同一实现**（一处防线覆盖四个工具） |
| 提示词里对工作区的描述 | 一句：「你的工作区：X（read/write/edit/ls 只能在此目录内）——用于放临时产出，正式资料请用 `parent_put_material` 发布到真源」 | **也只有一句**：「你的工作区：X（read/write/edit/ls 只能在此目录内操作）」 |

⇒ **"能操作文件"已经成立**（工具与沙箱都在），**"知道目录架构"没有**——提示词里只有一个绝对路径，模型不知道里面应该有什么、产出该放哪、什么不该碰。

**二、工作区实际长什么样（实测 `workspaces/<pid>/<cid>/`）**

```
workspaces/<家长id>/<孩子id>/            ← 孩子 agent 的根（read/write/edit/ls 只能在这棵树里）
├─ outputs/                              ← ★ 孩子的"作品柜"：产出的 HTML / 清单都放这儿
│   ├─ 论语子路篇第四章.html                （create_html_lesson 缺省就写 outputs/<标题>.html）
│   └─ test.txt
├─ scratch/.pi/…                         ← 编程 agent 的运行区（自动生成，不是学习产物）
└─ .pi/<孩子id>-main/                    ← 孩子自己的会话数据（历史/槽位）⚠ 不是学习内容
```

三条要点：
1. **`outputs/` 是唯一"正式"位置**——`create_html_lesson` 缺省落这里；`display_content` 也按 **`outputs/` 前缀**区分"这是孩子工作区里的文件"（其它相对路径按家长资料库解析）；
2. `scratch/` 与 `.pi/` 是**运行区 / 会话数据**，不是学习产物，**不该给孩子看、也不该被当成作品**；
3. 现在提示词**一个字都没提这三层**——模型只知道"根在哪"，不知道"该往哪写、哪不能读"。

**三、⚠️ 顺带一个实现级发现：`ls` 会把 `.pi/` 列出来**

`ls` 的目录遍历**不过滤隐藏目录**（`ls .` 会连 `.pi/` 一起列）。`.pi/<孩子id>-main` 里是**孩子 agent 自己的会话数据**（含上下文、系统提示词）。风险两面：**上下文污染**（模型去读自己的历史/提示词，浪费预算还可能自相矛盾）与**隐私面**（系统数据不是"孩子的作品"）。
⇒ 建议（低风险改动）：**`ls` 默认跳过 `.pi`（或所有点号目录）**，并在提示词里写明"`.pi/`、`scratch/` 是运行区，不要读、不要展示"。**属实现细节，见 `ISSUE-138`。**

**四、孩子**读不到**家长资料库的文件内容——这是有意边界，不是缺口**

| 想做的 | 孩子侧现状 |
|---|---|
| 看**今天有哪些资料** | 只能看资料面板（界面）；**对话里没有"列资料"的工具**（家长侧的列资料能力不对孩子开放）→ **I1 在对话里没有出口** |
| 打开**某一课的 html 资料** | ✅ 能：`parent_content(type=htmlPath, topic, course)` 拿到相对路径 → `display_content` 展示（**必须按"主题 + 课程名"点名**，不能浏览） |
| **读**资料文件的内容（把 md/文本读进来讲） | ❌ 不能（文件工具根在孩子工作区，资料库在**另一棵树**） |
| 往**资料库写**东西 | ❌ 不能（孩子产出只能落自己 `outputs/`；`materials/` 前缀的写入是家长侧行为） |

⇒ 建议维持现状：**孩子对家长资料库"能按课程取、能展示"，但不能浏览、不能写**——与"资料真源由家长掌握"一致。要做到"能列出资料清单"，需新开一个**只读列举**能力（待拍板）。
